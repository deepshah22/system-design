Security Fundamentals
Opening the Vault the Doorman Guards

Yesterday's gateway checked badges at the door. But two questions were left hanging: what makes a badge trustworthy? and what is behind the door worth protecting? Today we open the vault. Security isn't a feature you bolt on at the end — it's a property you design in, because on the public internet there is always an adversary. We'll build the whole foundation from scratch: the CIA triad (the three things you're protecting), the three cryptographic tools you must never confuse — encryption (reversible, keeps secrets), hashing (one-way, for passwords and integrity), and digital signatures (prove who and unaltered) — how symmetric and asymmetric keys and certificates let total strangers trust each other (the machinery inside TLS and the mesh's mTLS), how to store passwords so a database leak isn't game over, the security principles every senior engineer designs by, and the common threats each layer is built to stop.

Visual Memory Anchor

🏰 🛡️ 🔐

Picture this

Picture a medieval castle protecting a treasure. A naïve castle has one wall — climb it once and you own everything inside. A real castle protects the treasure in layers: a wide moat (you can't even get close), then a tall outer wall with archers, then an inner wall, then armed guards who check who you are, and finally the treasure itself locked inside a vault. An attacker must defeat every layer; defenders only need one layer to hold. That is defense in depth — never trust a single wall. Now look at what's inside that vault. Three things are written on its door, and together they are everything security tries to protect: Confidentiality (only the right people can read the treasure), Integrity (no one can secretly swap a gold bar for a lead one), and Availability (the rightful owner can actually get in when they need to) — the CIA triad. And how does the guard know a visitor's badge is real and hasn't been forged? By the castle's seal: a mark only the king can make, that anyone can recognize but no one can fake (a digital signature), stamped by a trusted royal authority (a certificate). Burn in the image: security is a castle with many layers, not one wall (defense in depth); the vault protects three things — Confidentiality, Integrity, Availability (CIA); and trust between strangers is carried by an unforgeable seal from an authority everyone already trusts (signatures & certificates).

The Story

Plaintext Pat launched a promising little app and, at first, security felt like a distant problem for "big companies." Users signed up, and Pat stored their passwords the obvious way: in a database column called password, exactly as typed — hunter2, right there in plain text. Logins were fast and simple. What could go wrong?

A lot, all at once. First, Pat's app talked to users over plain HTTP. One afternoon a user logged in over café Wi-Fi, and someone on the same network simply read the password off the wire — no hacking, just listening (eavesdropping). Pat's fix was the right one: serve everything over HTTPS, so traffic is encrypted in transit and a listener sees only gibberish. One threat down.

Then the real disaster. A forgotten backup of the database leaked. Because every password was stored in plain text, the attacker instantly had every user's password — and since people reuse passwords, they walked straight into those users' email and bank accounts too. Pat learned the rule the hard way: you should never be able to read your users' passwords, not even you. The fix wasn't to encrypt them (encryption is reversible — whoever steals the key steals the passwords). The fix was hashing: run each password through a one-way function so the database stores a fingerprint you can verify a login against but can never turn back into the password.

But Pat's first attempt at hashing was still broken. Using a plain fast hash (like a bare SHA-256) meant two users with the same password got the same fingerprint, and an attacker with a precomputed lookup table (a rainbow table) could reverse millions of common passwords in seconds. The real fix had two parts: add a random salt to every password before hashing (so identical passwords look different and precomputed tables are useless), and use a deliberately slow hash built for the job — bcrypt, scrypt, or argon2 — so that even one guess costs the attacker real time, turning "millions per second" into "a handful per second."

The attacks kept coming, each teaching a lesson. A login form that pasted the username straight into a database query let someone type ' OR 1=1 -- and log in as anyone (SQL injection) — fixed by never mixing user input into a query, using parameterized queries instead. A comment box that echoed text back onto the page let someone post a <script> that ran in other users' browsers (XSS) — fixed by escaping output. Bots tried millions of stolen username/password pairs from other breaches (credential stuffing) — blunted by rate limiting and multi-factor authentication. Slowly, Pat stopped thinking of security as one wall to build and started thinking in layers: assume any single defense can fail, so stack several, give every component only the access it truly needs, and trust nothing by default. Pat had discovered, one incident at a time, the fundamentals we're about to learn on purpose.

What should stay in your head
Security protects three things — the CIA triad: Confidentiality (only authorized people can read data), Integrity (data can't be secretly altered), and Availability (authorized people can actually use the system). You reach those goals with three cryptographic tools that do completely different jobs, and confusing them is the #1 beginner mistake: encryption is reversible and keeps secrets (scramble with a key, unscramble with a key); hashing is one-way and proves integrity or stores passwords (you can verify a match but never recover the input); a digital signature proves authenticity — who created something and that it wasn't altered. Encryption comes in two flavors — symmetric (one shared key, fast) and asymmetric (a public/private key pair, which lets strangers who share no secret still communicate securely) — and certificates bind a public key to an identity so you know whose key it is; that's the machinery inside TLS and the mesh's mTLS. Over all of it sit the principles: defense in depth (layers, never one wall), least privilege (grant the minimum access), zero trust (verify every request, even internal ones), fail closed (when unsure, deny), and don't roll your own crypto (use audited libraries). Security is not a feature you add last — it's a property you design in, because there is always an adversary.

The CIA Triad — What You're Actually Protecting

Before any tool or threat, name the goal. Every security control in existence is trying to protect one (or more) of three properties. If you can say which of the three an attack breaks and which a defense protects, you understand it.

🔒 Confidentiality

Only authorized people can read the data.

Secrets stay secret. Broken by eavesdropping, a database leak, or over-broad access.

Protected by encryption (in transit & at rest), access control, and least privilege.

✅ Integrity

Data can't be altered without detection.

What you read is what was written — no silent tampering. Broken by injection, a man-in-the-middle rewriting data, or a corrupted message.

Protected by hashing / checksums, digital signatures, and MACs.

🌊 Availability

Authorized people can use the system when needed.

The service is actually up. Broken by DDoS, resource exhaustion, or a failure that takes the system offline.

Protected by rate limiting, redundancy (Day 22), autoscaling, and DDoS mitigation.

Notice that Availability ties security back to all of Week 4 — a denial-of-service attack is a deliberate version of the overload and failures you learned to survive in Days 22–25. Security isn't a separate island; it's the adversarial lens on everything you've already built. (Some models add Authentication, Authorization, and Non-repudiation — proving you can't later deny an action — but CIA is the load-bearing core.)

The Three Cryptographic Tools — Never Confuse Them

Almost every security misconception comes from mixing up these three. They sound similar ("scramble the data") but do fundamentally different jobs. Learn the one-line difference for each and you're ahead of most engineers.

TOOL 1 · TWO-WAY

🔐 Encryption — keeps secrets

Scramble data with a key; unscramble it with a key. It's reversible by design — the whole point is to get the original back. Protects Confidentiality. Use it for data in transit (TLS) and at rest (disk/DB encryption). Never use it for passwords — reversible means a stolen key = stolen passwords.

TOOL 2 · ONE-WAY

# Hashing — proves integrity

Run data through a function that produces a fixed-size fingerprint and cannot be reversed. Same input → same hash; a tiny change → a totally different hash. Use it to verify integrity (did this file/message change?) and to store passwords (store the hash, compare hashes on login). You can check a match without ever knowing the original.

TOOL 3 · ONE-WAY + IDENTITY

✍️ Digital signature — proves who

Sign data with your private key; anyone can verify with your public key. It proves two things at once: authenticity (it really came from you) and integrity (it wasn't altered). It's the unforgeable royal seal. The cousin for two parties sharing a secret key is a MAC / HMAC — same integrity+authenticity guarantee, but symmetric.

ToolDirectionAnswers the questionClassic examples
EncryptionReversible (two-way)"Can only the right person read this?"AES (symmetric), RSA / ECC (asymmetric), TLS
HashingOne-way"Has this changed? / does this password match?"SHA-256 (integrity), bcrypt / scrypt / argon2 (passwords)
Signature / MACOne-way + verify"Who made this, and is it unaltered?"RSA / ECDSA signatures, HMAC

The interview-killer question: "How should you store passwords — encryption or hashing?" The answer is hashing (salted and slow), precisely because encryption is reversible and you never want to be able to recover a user's password. Say "encrypt the passwords" and you've revealed you've mixed up tools 1 and 2.

Keys & Certificates — How Strangers Trust Each Other

Encryption needs keys, and there are two families. The difference between them is the single most important idea in practical cryptography, because it's what makes secure communication on the open internet possible at all.

Symmetric vs asymmetric keys

🔑 Symmetric — one shared key

The same secret key encrypts and decrypts.

Very fast — great for bulk data. The catch: both sides must already share the secret, and getting that key to the other party safely is the hard part (the key distribution problem).

e.g. AES. Used for the actual data once a connection is set up.

🗝️ Asymmetric — a key pair

A public key (share freely) + a private key (never share).

Anything encrypted with the public key can only be opened by the private key — so strangers who share no prior secret can still communicate. Slower, so it's used to bootstrap, not for bulk data.

e.g. RSA, ECC. Used to exchange a symmetric key and to sign.

The beautiful part is how they combine: real protocols use asymmetric to safely agree on a symmetric key, then switch to fast symmetric encryption for the rest. You get the stranger-friendliness of asymmetric and the speed of symmetric — the best of both. This "handshake then bulk encrypt" is exactly what happens every time you see the padlock in your browser.

Certificates & PKI — whose public key is this, anyway?

Asymmetric crypto has one gap: a public key is just a number. If an attacker hands you their public key and claims it belongs to your bank, you'd encrypt secrets straight to the attacker (a man-in-the-middle). The fix is a certificate: a document that binds a public key to an identity (a domain name), signed by a Certificate Authority (CA) — a trusted third party your device already trusts. Your browser trusts a small set of CAs; anything they vouch for, it trusts by extension. This web of trust is PKI (Public Key Infrastructure), and it's the missing piece that turns "math that scrambles data" into "I can trust this is really my bank."

What actually happens when you see the 🔒 (TLS handshake, simplified)
# 1. Browser connects to bank.com and asks for its certificate client → server: hello, what's your certificate? server → client: certificate # contains bank's PUBLIC key, # signed by a CA the browser already trusts # 2. Browser verifies the CA's signature on the cert — proves the key is really bank.com's verify(cert.signature, CA.public_key) → ✅ trusted # 3. Both sides use asymmetric crypto to agree on a fresh SYMMETRIC session key shared_key = key_exchange() # neither an eavesdropper nor a MITM can derive it # 4. This is the machinery behind HTTPS (Day 4's topic, now demystified) and behind the service mesh's mTLS from yesterday — "mutual" just means both sides present certificates, so each proves its identity to the other. Same tools, pointed at internal traffic.

Storing Passwords Safely — The Canonical Example

Password storage is where all three tools and the whole "assume you'll be breached" mindset collide. It's the most common interview question in this space, and Plaintext Pat already lived every wrong answer. Here's the correct ladder, rung by rung.

ApproachWhat happens when the DB leaksVerdict
Plain text (hunter2)Every password stolen instantly; users' other accounts fall too.🔴 Catastrophic — never
Encrypted passwordsReversible: whoever steals the key (often nearby) steals every password.🔴 Wrong tool — never
Fast hash (bare SHA-256)Rainbow tables + billions of guesses/sec crack common passwords fast; identical passwords share a hash.🟠 Not enough
Salted fast hashSalt defeats precomputed tables, but a fast hash still allows billions of guesses/sec.🟡 Better, still weak
Salted + slow hash (bcrypt / scrypt / argon2)Each guess is deliberately expensive; salt makes every hash unique. Cracking becomes infeasible at scale.🟢 Correct
🧂
Salt — a random value per password. Generated fresh for each user and stored alongside the hash. It makes two users with the same password get different hashes and makes precomputed rainbow tables useless (the attacker would need a separate table per salt).
🐌
Slow by design. bcrypt/scrypt/argon2 have a tunable work factor — you make each hash take, say, a quarter-second. Invisible to one honest login, but it turns an attacker's "billions of guesses per second" into a crawl. (argon2 is also memory-hard, blunting GPU/ASIC attacks.)
🌶️
Pepper (optional). A secret value added to every password, stored separately from the database (e.g. in a secrets manager / HSM). Even if the DB leaks, the pepper doesn't, adding one more layer — defense in depth for the hash itself.
🔁
Rate limit + MFA on top. Good hashing protects a leaked database; rate limiting and multi-factor auth protect the live login form against brute-force and credential stuffing. You need both — storage hardening and login hardening.

The one-sentence answer: store a per-user salt plus a slow hash of the password (bcrypt, scrypt, or argon2) — never plain text, never merely encrypted — and defend the login form separately with rate limiting and MFA. Notice every principle from this lesson appears: the right tool (hashing, not encryption), defense in depth (salt + slow + pepper + rate limit + MFA), and "assume the database will leak."

The Security Principles Seniors Design By

Tools stop specific attacks; principles shape how you design the whole system so that attacks you didn't anticipate are contained. These are the mental defaults that separate a secure architecture from a checklist.

PRINCIPLE 1

🧅 Defense in depth

Never rely on one wall. Stack independent layers so that if one fails, another still holds. The castle's moat, walls, guards, and vault — an attacker must beat them all.

PRINCIPLE 2

🔑 Least privilege

Give every user, service, and token the minimum access it needs, and nothing more. A compromised component can only reach what it was granted — this shrinks the blast radius (Day 22).

PRINCIPLE 3

🚫 Zero trust

Trust nothing by default — verify every request, even internal ones. "It's behind the firewall" is how breaches spread laterally. This is exactly what the mesh's mTLS (Day 27) automates.

PRINCIPLE 4

🔒 Fail closed

When something is uncertain or breaks, deny rather than allow. An auth check that errors out should reject the request, never wave it through. Safe defaults, not convenient ones.

PRINCIPLE 5

🎯 Minimize attack surface

Every open port, endpoint, dependency, and feature is a way in. Expose only what you must, patch what you keep, and delete what you don't use. Less surface, fewer doors to guard.

PRINCIPLE 6

🧪 Don't roll your own crypto

Use audited, battle-tested libraries (TLS, argon2, a mature auth provider). Hand-written crypto is subtly, silently broken. Security through obscurity is not security — assume the attacker knows your design.

The Hard Parts

Security is full of tradeoffs, and the senior skill is holding the tension honestly rather than chasing "maximum security," which usually means an unusable system nobody can ship.

Security vs usability

Every control adds friction. Force a 32-character password rotated weekly plus three MFA prompts per action and users will write passwords on sticky notes and route around you — making things less secure. The art is proportionate security: strong where the stakes are high (money, health data), light where they're not, and as invisible as possible (TLS, passkeys, risk-based MFA that only challenges when something looks off).

You can't prove you're secure — only that you're not yet breached

Defenders must cover every path; an attacker needs one. There's no "done" — security is continuous: patching dependencies, rotating keys and secrets, threat modeling new features, and assuming a breach will happen (which is why you also invest in detection and response, not just prevention). "We passed the audit" is a snapshot, not a guarantee.

Encryption isn't free, and key management is the real problem

Encryption adds CPU and latency, and — more importantly — moves the problem to the keys. Encrypted data is only as safe as the key protecting it, so now you must generate, store, rotate, and revoke keys safely (secrets managers, HSMs, KMS). A common failure isn't broken crypto — it's a private key or API secret committed to a public git repo. The math is rarely the weak point; the humans and the key handling usually are.

The weakest link is almost always people

The strongest crypto in the world is defeated by a convincing phishing email, a reused password, or a social-engineering call to the help desk. That's why MFA, least privilege, and a security-aware culture matter as much as any algorithm — you're defending a socio-technical system, not just code.

The through-line: security trades friction, cost, and complexity for protection of confidentiality, integrity, and availability against an adversary who only needs to be right once. You design in depth, assume breach, use proven tools, and make the secure path the easy path.

Active Recall

❓ A junior engineer says: "For our new app I'll store passwords encrypted with AES so we can help users recover them, and since we're on HTTPS we're basically secure." Point out every mistake, give the correct password-storage design, and name the principle that explains why "we're on HTTPS" isn't enough. (click to reveal)
Three mistakes, one good design, one principle. (1) Wrong tool for passwords. Encryption is reversible — if you can decrypt passwords to "help users recover them," so can anyone who steals the key (which usually lives near the data). The goal is that no one, including you, can read them. Passwords must be hashed, not encrypted. "Password recovery" should mean a reset flow (email a one-time link), never revealing the old password. (2) Wrong kind of hash matters too. The correct storage is a per-user random salt plus a deliberately slow hash — bcrypt, scrypt, or argon2 — with a tuned work factor. The salt makes identical passwords hash differently and kills rainbow tables; the slowness turns an attacker's billions of guesses per second into a crawl. Optionally add a pepper stored separately (a secrets manager) for one more layer. Then defend the live login separately with rate limiting and MFA against brute force and credential stuffing. (3) "We're on HTTPS" ≠ secure. TLS protects data only in transit — it does nothing against a leaked database, SQL injection, XSS, broken access control, or weak passwords. Believing one control makes you secure is exactly the mistake. The principle: defense in depth. Real security is overlapping layers — TLS and salted-slow hashing and parameterized queries and output escaping and rate limiting and least privilege — because an attacker only needs one gap, so you must make sure a gap in any one layer is covered by another. And you design it in from the start, assuming a breach will eventually happen.

Real-World Engineering

🔓 The plaintext-password breaches

Real companies have leaked hundreds of millions of plaintext or weakly-hashed passwords. The pattern is always the same: a database leaks (they always eventually do), and because storage wasn't salted-and-slow-hashed, every credential is instantly usable — and reused across users' other accounts. It's the single most expensive version of Plaintext Pat's mistake, and the reason salted slow hashing is non-negotiable.

🔒 Let's Encrypt — TLS for everyone

Let's Encrypt is a free, automated Certificate Authority that issues the certificates behind HTTPS. By making certs free and one-command, it helped move the web from mostly-HTTP to nearly-all-HTTPS in a few years — a huge, quiet win for confidentiality and integrity at internet scale, built entirely on the PKI machinery in this lesson.

🧂 Argon2 & the password-hashing competition

The industry ran an open Password Hashing Competition; argon2 won and is now the recommended default — deliberately slow and memory-hard, so even GPU and custom-hardware attackers can't parallelize their way through. It's the modern answer to "how do I store passwords," and a great example of "don't roll your own — use the vetted winner."

🏦 Zero trust at Google (BeyondCorp)

Google's BeyondCorp famously threw out the "trusted internal network" model: every request is authenticated and authorized regardless of where it comes from, with no privileged network. It's zero trust at massive scale, and the same philosophy the service mesh's mTLS (Day 27) automates for service-to-service traffic.

Flashcards (Spaced Repetition)

Q: What is the CIA triad?
A: The three things security protects: Confidentiality (only authorized people can read data), Integrity (data can't be secretly altered), and Availability (authorized people can use the system when needed). Every attack breaks one of these; every control protects one.
Q: Encryption vs hashing vs digital signature — one line each.
A: Encryption = reversible, keeps secrets (two-way, needs a key both ways). Hashing = one-way fingerprint, proves integrity and stores passwords (can't be reversed). Digital signature = proves who made it and that it's unaltered (sign with private key, verify with public key).
Q: How should you store passwords, and why not encryption?
A: A per-user random salt plus a deliberately slow hash (bcrypt / scrypt / argon2). Not encryption, because encryption is reversible — a stolen key means stolen passwords; you never want to be able to recover a password. Salt kills rainbow tables; slowness kills brute force. Add rate limiting + MFA on the login.
Q: Symmetric vs asymmetric keys, and how do certificates fit in?
A: Symmetric = one shared key, fast, but both sides must already share the secret. Asymmetric = public/private key pair, lets strangers communicate with no shared secret, but slower. Real protocols use asymmetric to agree on a symmetric key, then bulk-encrypt symmetrically. A certificate (signed by a trusted CA) binds a public key to an identity so you know whose key it is — the basis of TLS/HTTPS and mTLS.
Q: Name four security principles seniors design by.
A: Any of: defense in depth (layers, never one wall), least privilege (minimum access), zero trust (verify every request, even internal), fail closed (deny when unsure), minimize attack surface, and don't roll your own crypto (use audited libraries; security ≠ obscurity).

If you only remember one thing: security is a property you design in — protecting Confidentiality, Integrity, and Availability (the CIA triad) with the right tool for each job and overlapping layers, because there's always an adversary who only needs one gap. Never confuse the three cryptographic tools: encryption is reversible and keeps secrets, hashing is one-way and proves integrity or stores passwords, and a digital signature proves who made something and that it's unaltered. Use asymmetric keys and certificates to let strangers trust each other and bootstrap a fast symmetric session — the machinery inside HTTPS and mTLS. Store passwords salted and slowly hashed (bcrypt / scrypt / argon2), never plain, never merely encrypted, and defend the login separately with rate limiting and MFA. Above the tools, design by the principles: defense in depth, least privilege, zero trust, fail closed, minimize attack surface, and don't roll your own crypto — and assume a breach will happen.
