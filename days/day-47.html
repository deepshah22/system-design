Design WhatsApp / a Chat System
Deliver One Message to One Person

Yesterday a tweet fanned out to the whole world. Today we do the opposite: deliver a single message to one specific person — reliably, in order, in a fraction of a second — and discover that chat is a completely different shape of problem. The web you grew up on is request–response: the browser asks, the server answers, and the server can never speak first. But chat needs the server to push a message to Ben the instant Ana sends it, whether Ben asked for it or not. So we build around three ideas: a persistent connection (a WebSocket) held open at a connection server, a session registry that knows which server is holding Ben's socket right now, and an offline inbox for when Ben's phone is dark. Then we add the two things that make chat feel like chat: message ordering (a per-conversation sequence number, so messages never arrive scrambled) and the ticks — sent, delivered, read — which are really a tiny state machine with acknowledgements flowing back. You'll run both live: a delivery router that queues a message when the recipient is offline and flushes it on reconnect, and a lifecycle demo that reorders out-of-order arrivals by sequence number and dedupes a retried message.

Picture this

Picture an old telephone switchboard room. Ana wants to reach Ben. She doesn't dial Ben directly — she speaks to the operator sitting at the switchboard. The operator keeps a board of sockets, and a little card index that says, in real time, which socket each person is currently plugged into. That card index is the session registry: not “where does Ben live,” but “which line is Ben on right now.”

When Ben's line is plugged in (his phone is open, holding a live connection), the operator grabs a patch cord and connects Ana's message straight through — it lands on Ben's phone instantly. That patch cord is the WebSocket: a connection the operator can speak down without Ben asking first. But when Ben's line is unplugged (offline), the operator can't push anything. So she drops the note into Ben's pigeonhole — a little mailbox behind the board — and the moment Ben plugs back in, she hands over everything waiting there, in the order it arrived. That pigeonhole is the offline inbox.

Two more details make it feel like real chat. First, every note gets a numbered ticket as it passes the desk — ticket 1, 2, 3 — so even if two notes race and arrive out of order, Ben reads them in ticket order. That's the sequence number. Second, the operator sends a little return-receipt card back to Ana: one check when the note reached the desk, two checks when it reached Ben's phone, and the checks turn blue when Ben actually reads it. Those are the ticks. Hold the whole picture: an operator with a live socket board, a card index of who's plugged in where, a wall of pigeonholes for the absent, numbered tickets, and return-receipt cards. That room is a chat system.

The switchboard room: plugged in → patch straight through (WebSocket push); unplugged → drop in the pigeonhole (offline inbox) and hand over on reconnect; numbered tickets keep order; receipt cards are the ticks.

The Story

Mara built her first chat feature the way she'd built everything else on the web: the client asks, the server answers. To receive new messages, the app polled — “any new messages?” every two seconds. It worked for a demo. Then reality arrived: with a million users each asking every two seconds, the servers drowned in a flood of mostly-empty “nope, nothing new” replies — and messages still felt laggy, arriving up to two seconds late. Polling was burning enormous resources to deliver nothing, most of the time.

Her mentor reframed it. “You're using a pull tool for a push problem. The server knows the instant a message arrives — let it tell the recipient, instead of making the recipient ask over and over.” The fix was a persistent connection: each online phone holds a WebSocket open to a connection server, and the server pushes messages down it the moment they arrive. No polling, no lag. But that raised a sharp new question: with millions of sockets spread across thousands of connection servers, when Ana sends to Ben, which server is holding Ben's socket?

That became the heart of the design: a session registry — a fast, in-memory map (Redis) from user → connection server, updated every time someone connects or disconnects. Ana's message goes to her connection server, which asks the registry “where's Ben?”, routes the message to Ben's connection server, and that server pushes it down Ben's socket. And when Ben is offline — no socket at all — the message is written to his offline inbox and delivered the moment he reconnects.

Two subtler problems nagged. First, order: two messages could take different paths and arrive scrambled. Mara had the server stamp each message with a per-conversation sequence number, so the client could buffer and display them in order no matter what the network did. Second, reliability: on a flaky mobile network, the client resends a message it isn't sure got through — so the server had to dedupe using a client-generated message ID, making the send idempotent. By the end, Mara hadn't built a faster poll. She'd built a switchboard: live sockets, a registry of who's where, pigeonholes for the absent, tickets for order, and receipts for trust. Which is, almost exactly, how WhatsApp works.

What should stay in your head
A chat system is targeted, server-pushed delivery of a message to a specific recipient — the opposite of Twitter's broadcast. Because HTTP is request–response (the server can't speak first), each online client holds a persistent WebSocket to a connection server. To route a message you need a session registry (user → which connection server holds their socket, in Redis): the sender's server looks up the recipient, forwards the message to the recipient's connection server, which pushes it down the socket. If the recipient is offline, the message is stored in a durable offline inbox and delivered on reconnect (plus a mobile push notification via APNs/FCM to wake the app). Two guarantees make it feel right: ordering — the server stamps each message with a per-conversation sequence number so clients can reorder out-of-order arrivals; and receipts — the ticks (sent → delivered → read) are a tiny state machine driven by acknowledgements flowing back. Reliability on flaky networks comes from idempotency: the client attaches a unique message ID so a retried send is deduped, not duplicated. One-line test: hold a socket open, know who's on which server, push if online or stash in an inbox if not, number every message for order, and ack it back for receipts.

Why This Problem Exists

“Design WhatsApp” is a classic interview because it breaks the one assumption every web app is built on: that the client always starts the conversation. In a normal request–response world the server is a waiter — it only ever speaks when spoken to. Chat inverts that: the server must be able to tap the recipient on the shoulder the instant a message arrives. Four requirements fall out of that, and none of them is how the ordinary web works:

📡 Server-initiated push

The server must deliver without the client asking. Polling (“anything new?”) wastes resources and lags; you need a connection the server can speak down — a WebSocket (Day 20).

🎯 Targeted routing

Not broadcast to the world (Day 46) — delivery to one specific person who is connected to one of thousands of servers. You must know which.

🔢 Ordering

Messages must appear in the order they were sent, even when the network reorders them. That needs a per-conversation sequence, not wall-clock timestamps.

📬 Offline + receipts

Phones go dark constantly. Messages must survive until the recipient returns (offline inbox), and senders expect delivered/read feedback.

A chat message is also small, frequent, and intensely latency-sensitive — a 300 ms delay is the difference between “instant” and “broken.” And the connection itself is now stateful: unlike a stateless web request, a WebSocket is a long-lived thing pinned to one server, which changes how you load-balance, scale, and recover. That combination — push, targeted routing, ordering, offline durability, and millions of stateful long-lived connections — is why chat gets its own design, and why “just add a database” doesn't cut it.

The Design, Step by Step

Follow one message from Ana's thumb to Ben's screen. The surprise is how much of the system is about the connection, not the database.

The pieces

1
Connection servers (a.k.a. gateway / WebSocket servers) hold the millions of open sockets. Each online client keeps one long-lived WebSocket to one of these. They are the only stateful tier.
2
A session registry (Redis — Day 7/40) maps user → connection server. On connect you write your entry; on disconnect you remove it. This is how anyone finds where you are right now.
3
A message service assigns each message a per-conversation sequence number, dedupes by client message ID (idempotency), and writes it to the message store.
4
A message store (a partitioned wide-column store like Cassandra — Day 52, keyed by conversation) is the durable log of every message, ordered by sequence. It doubles as the offline inbox.
5
A push-notification service (APNs for iOS, FCM for Android) wakes the app when the recipient is offline and has no socket to push down.

The core move: separate the stateful connection tier (sockets, pinned to servers, tracked in a registry) from the stateless message tier (assign sequence, store, route). The connection servers are dumb pipes that hold sockets and forward; the message service owns ordering, idempotency, and durability. That split is what lets you scale sockets and logic independently.

The Heart: The Connection + the Registry

Everything hard about chat flows from one fact: you can't push to someone you can't find. So the two load-bearing pieces are the persistent connection and the session registry that locates it.

Why a WebSocket, and not polling or long-polling

To receive a server-initiated message you need a channel the server can write to at any time. Three options, in order of how much they waste:

ApproachHow it worksVerdict for chat
Short pollingClient asks “anything new?” every N seconds.❌ Wasteful (mostly empty replies) and laggy (up to N seconds late).
Long pollingClient asks and the server holds the request open until a message arrives.➖ Works, lower latency, but one in-flight request per message and reconnection churn.
WebSocketOne long-lived, bidirectional TCP connection; server pushes anytime.✅ The default — true push, minimal overhead, both directions.
SSEServer-sent events: server→client push over HTTP, one direction.➖ Great for feeds/notifications; chat wants two-way, so WebSocket wins.

The catch: a WebSocket is stateful. A stateless web request can hit any server behind a load balancer; a socket is pinned to the exact connection server that accepted it. That one fact ripples through everything — load balancing (you route the handshake, then the connection sticks), scaling (a server holds, say, tens of thousands of sockets; add servers to add capacity), and failure (if a connection server dies, all its clients must reconnect — and re-register).

The session registry — the switchboard's card index

Because sockets are scattered across thousands of connection servers, routing needs a live directory. The session registry is an in-memory map (Redis) of user_id → connection_server_id (plus presence: online/last-seen). It's written on every connect/disconnect and read on every send. It is the single thing that turns “deliver to Ben” into “forward to the exact server holding Ben's socket.” When Ben isn't in the registry at all, he's offline — so the message goes to his inbox and a push notification wakes his phone.

In one line: online ? push down the socket on their connection server : store in the inbox + send a push notification. The registry is how you tell which case you're in — and it must be fast, because every single message does a lookup.

Ordering, Receipts & Idempotency

Delivery is half the job. The other half is making messages trustworthy: in the right order, acknowledged, and never duplicated.

Ordering — a per-conversation sequence number

Two messages sent a millisecond apart can take different paths and arrive out of order. You cannot order by client timestamps — phone clocks drift and lie. Instead, the message service assigns a monotonic sequence number per conversation as it stores each message. The client holds a small buffer and renders strictly by sequence, so a late-arriving #2 slots in before the #3 that beat it across the network — exactly what the Message Lifecycle widget shows. Ordering is per conversation, not globally: you only need messages within one chat to agree, which is far cheaper than a global order across all chats (a theme you'll meet again in message ordering and logical clocks, Day 35).

Receipts — the ticks are a state machine

The single/double/blue ticks are a tiny state machine driven by acknowledgements flowing backward:

StateShownTriggered when…
Sent✓The server received & stored the message (acks the sender).
Delivered✓✓The message reached the recipient's device, which acks back.
Read✓✓The recipient actually opened the chat; the device sends a read receipt.

Each tick is just an ack traveling the reverse path. That's also why receipts can be turned off (privacy) — the client simply withholds the read ack.

A message's life: the ticks are a state machine driven by acks flowing back; ordering is handled by the client re-sorting on the server-assigned sequence number; a retried message carries the same ID and is deduped.

Idempotency — safe retries on a flaky network

Mobile networks drop. If Ana's phone doesn't see the ✓, it will resend — and now the server might get the same message twice. The fix is idempotency: the client attaches a unique message ID (a UUID or Snowflake ID, Day 46) to each message. The server treats the ID as a dedupe key: if it has already stored that ID, it re-acks but does not store a second copy. “Send” becomes safe to repeat — the retry in the widget bumps the deduped counter, not a second bubble. At-least-once delivery + idempotent handling = exactly-once effect, which is the realistic target (true exactly-once delivery is effectively impossible over an unreliable network).

The trust trio: per-conversation sequence (order) · acks flowing back (sent/delivered/read ticks) · client message ID as a dedupe key (idempotent retries). Order, receipts, and no duplicates — the three things that make chat feel solid.

Groups, Presence & Push

Three features turn one-to-one messaging into a real product — and each has a scale twist.

Group chat — fan-out, but small

A group message is delivered by fanning out to each member: look up every member in the registry, push to the online ones, inbox the offline ones. This is the same fan-out idea as the feed (Day 45) and Twitter (Day 46) — but groups are small (tens, maybe a few hundred), so write-time fan-out is fine; there's no celebrity-sized explosion. The sequence number is now assigned per group, so all members see the same order. Very large broadcast groups (tens of thousands) start to look like the Twitter problem again and may switch strategies.

Presence — the “online / last seen” storm

Showing who's online sounds trivial and is secretly one of the hardest parts. If every status change (online, offline, typing…) were broadcast to everyone who might care, a popular user toggling presence would trigger a fan-out storm of updates. Real systems tame it: update presence in the registry with a heartbeat + TTL (miss a few heartbeats → marked offline), and only push presence to the small set of people currently looking at that user's chat, often throttled (you don't need millisecond-accurate “last seen”). Presence is best-effort and approximate on purpose.

Push notifications — reaching the dark phone

When the recipient is offline, there's no socket to push down, but you still must reach them. The message service hands off to a push-notification service → Apple's APNs or Google's FCM → the OS wakes the app, which reconnects its WebSocket and pulls everything after its last-seen sequence from the inbox. (Designing that notification system in its own right is Day 50.)

🧵 Stateful connections scale apart

The socket tier scales by connection count; the message/storage tier scales by throughput. Keep them separate so a socket spike doesn't stall writes.

📏 Estimate first (Day 30)

Billions of messages/day, but the headline number is concurrent connections — tens of millions of open sockets — which is a connection-count problem, not a QPS one.

The Hard Parts

“Hold a socket, route via a registry, number for order, ack for receipts” is the clean 80%. These edges are where chat-at-scale really lives.

Millions of persistent connections (the C10M problem)

A web server is tuned for short requests; holding tens of millions of idle-but-open connections is a different beast — each costs memory and a file descriptor, and every one sends periodic heartbeats to prove it's alive and to keep NATs/firewalls from closing it. Connection servers are specially tuned for this, and because a socket is pinned, a server restart or crash forces a reconnection stampede you must spread out (jittered backoff) so clients don't all slam back at once.

Presence at scale

As above: naïve presence fan-out melts. The real answer is heartbeats + TTL in the registry, subscribe-only-to-who-you're-looking-at, and heavy throttling. Accept that “last seen” is approximate — exactness isn't worth a fan-out storm.

Multi-device sync

You read on your phone; the web app must update too. Now a “conversation” has several endpoints, and a message (and its read state) must sync to all of a user's devices and stay consistent. The sequence number helps — each device tracks its own last-seen seq and pulls the gap — but reconciling reads and deletes across devices is genuinely fiddly.

End-to-end encryption

In apps like WhatsApp and Signal, the server routes ciphertext it cannot read (the Signal protocol). That constrains the design: the server can't index message content, do server-side search, or inspect for ordering by content — it orders and routes envelopes, not contents. Features like search move onto the device. Security and routing pull in opposite directions, and E2E is a deliberate trade of server-side capability for privacy.

The through-line: persistent socket → registry lookup → push or inbox is the skeleton; doing it with sequence-numbered ordering, ack-driven receipts, idempotent retries, heartbeat-based presence, graceful reconnection, multi-device sync, and (optionally) end-to-end encryption is the craft. Get those right and a message crosses the planet in 100 ms and feels like it was never in doubt.

Real-World Engineering

💬 WhatsApp

Famous for running hundreds of millions of connections on a famously small team, built on Erlang/BEAM — a runtime designed for millions of lightweight, long-lived processes (one per connection). Messages are end-to-end encrypted (Signal protocol): the server routes ciphertext envelopes and stores them only until delivered.

✈️ Signal

The Signal protocol is the gold standard for E2E chat (also used by WhatsApp and Messenger's secret chats). The server is deliberately kept ignorant — it can't read messages — so features like search and backup live on the device, a clean illustration of the privacy-vs-capability trade.

💼 Slack

Uses WebSockets for real-time events and a session/presence layer to route them. Slack's scale twist is channels (group fan-out) plus rich presence and typing indicators, with heavy use of throttling and per-workspace sharding.

🎮 Discord

Pushes real-time events over WebSockets to tens of millions of concurrent users, with a gateway tier for connections and (famously) Cassandra/ScyllaDB for the message store — a textbook “connection tier + wide-column message log” split, exactly the shape of this lesson.

Flashcards (Spaced Repetition)

Q: In one sentence, what is the core architecture of a chat system?
A: Each online client holds a persistent WebSocket to a connection server; a session registry (user → connection server, in Redis) lets the sender route a message to the recipient's server, which pushes it down the socket — or, if the recipient is offline, stores it in an offline inbox and sends a push notification.
Q: Why a WebSocket instead of polling or a normal HTTP request?
A: Chat needs server-initiated push — the server must deliver without the client asking. Polling wastes resources and lags; a WebSocket is a long-lived, bidirectional connection the server can write to at any time. The cost: it's stateful, pinned to one connection server.
Q: How do you guarantee messages appear in the right order?
A: The server assigns a per-conversation sequence number as it stores each message (never trust client timestamps). The client buffers and renders strictly by sequence, so out-of-order network arrivals are reordered correctly. Ordering is per-conversation, not global.
Q: What do the sent / delivered / read ticks actually represent, and how do retries avoid duplicates?
A: The ticks are a tiny state machine driven by acks flowing back: ✓ = server stored it, ✓✓ = reached the device, blue ✓✓ = read. Retries are made safe by idempotency: the client attaches a unique message ID the server uses as a dedupe key, so a resend is acked but not stored twice.
Q: Why is presence (online / last-seen) secretly one of the hardest parts?
A: Broadcasting every status change causes a fan-out storm. Real systems use heartbeats + TTL in the registry (miss heartbeats → offline), push presence only to people currently viewing that chat, and throttle it — accepting that “last seen” is approximate.

If you only remember one thing: chat is targeted, server-pushed delivery — the mirror image of Twitter's broadcast. Because the web is request–response, each online client holds a persistent WebSocket to a connection server, and a session registry (user → connection server, in Redis) lets the sender route a message to the recipient's server to be pushed down the socket — or, if they're offline, stashed in a durable inbox and followed by a push notification. Three guarantees make it feel solid: a per-conversation sequence number for order, acks flowing back for the sent/delivered/read ticks, and a client message ID as a dedupe key for idempotent retries. The real difficulty is operational — millions of stateful long-lived connections, presence without fan-out storms, multi-device sync, and routing ciphertext you can't read.
