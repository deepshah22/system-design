REST API Design
A Small Vocabulary for an Endless World

For two weeks you built the machinery behind the wall — replication, sharding, the hash ring. Today you build the front door: the API every other program will speak to. Left alone, that front door grows a thousand bespoke doorbells — getUser, getUserOrders, createOrderAndChargeAndEmail — until nobody can guess how anything works. REST is the quietly brilliant fix: treat everything as a noun with an address, act on it with a fixed handful of verbs, answer with honest status codes, and keep every request stateless so the front door scales as easily as the database behind it.

Visual Memory Anchor

🏨🛎️

Picture this

Imagine a vast hotel. Every thing in it has a stable address — room 302, reservation 8817, the guest in suite 42: /rooms/302, /reservations/8817, /guests/42. Those addresses are nouns, and there are millions of them. But the service card on every desk lists only a tiny, fixed set of actions, and they're the same everywhere: VIEW a thing, BOOK a new one, REPLACE it, AMEND it, CANCEL it. You never invent a weird new verb like "checkOutAndBillAndEmailReceipt" — you just apply the five standard actions to the right nouns. Millions of nouns × five verbs covers everything, and a guest who has stayed at one hotel instantly knows how to use any hotel. That combination — noun-addresses plus a fixed verb vocabulary — is REST.

The Story

Database Dave had spent a fortnight taming storage — replicas, shards, a hash ring humming along. Now the mobile team, the web team, and two partner companies all wanted to reach that data. So Dave did the obvious thing: for every screen someone described, he added an endpoint. /getUser. /getUserProfile. /getUserOrders. /getUserRecentOrders. /createOrder. /createOrderAndCharge. /cancelOrderAndRefundAndEmail. Six weeks later the API had 412 endpoints, no two of them shaped alike, and onboarding a new engineer meant reading a 90-page document just to learn the verbs Dave had personally invented.

The breaking point came when the payments partner asked a simple question: "Your /createOrder returns 200 OK with {"error":"card declined"} in the body — so our retry system thinks every failed charge succeeded. Which of your 412 endpoints actually tell the truth about whether they worked?" Dave didn't have an answer. His API looked like it did a lot; it just didn't mean anything consistent.

A senior engineer wiped the whiteboard and drew a hotel. "Stop inventing verbs," she said. "You have a handful of things — users, orders, payments — give each a stable address, a noun. Then use the verbs HTTP already gave you: GET to read, POST to create, PUT/PATCH to change, DELETE to remove. Creating an order is POST /orders. Fetching a customer's orders is GET /customers/42/orders. Filtering to shipped ones is ?status=shipped — not a whole new endpoint. And when something fails, say so in the status line: 404, 409, 422 — so a machine on the other side knows without reading your prose." Dave's 412 endpoints collapsed into about a dozen resources. The partner's retry logic started working the same day. That collapse — from a sprawl of invented verbs to a small, honest, predictable vocabulary — is what REST buys you.

What should stay in your head
A good API doesn't grow one endpoint per feature — it exposes resources (nouns with stable addresses) and acts on them with a fixed set of HTTP verbs whose meaning everyone already knows. The verb carries the intent, the URL carries the target, the status code tells the truth about what happened, and every request stands stateless on its own so any server can answer it. Fewer things to memorize, more things you can guess.

What REST Actually Is (It's a Set of Constraints)

REST — REpresentational State Transfer — isn't a protocol, a library, or a spec you install. It's a set of constraints Roy Fielding described in 2000 for how to build systems on top of HTTP so they stay simple, scalable, and evolvable. An API that follows them is "RESTful." Four of those constraints do almost all the work in practice:

1. Resources & a uniform interface.Everything worth talking about is a resource with a stable address (a URL). You manipulate resources through the same small set of methods everywhere — so once you know how one resource behaves, you can guess how all of them do. This is the "nouns + fixed verbs" idea, made a rule.
2. Statelessness.Each request carries everything the server needs to handle it — identity, parameters, body. The server keeps no per-client memory between requests. This is the constraint that makes the front door scale: any of your load-balanced, replicated servers (Days 2 & 5) can answer any request, because none of them is holding a private conversation.
3. Cacheability.Responses declare whether they can be cached and for how long. Because GET is safe (it changes nothing), a CDN or reverse proxy (Day 4) can serve it without ever touching your servers. REST bakes caching into the design instead of bolting it on.
4. Client–server & layered.The client and server evolve independently as long as the interface holds, and you can slip layers between them — load balancers, gateways, caches — without either side knowing. That's why you can put a CDN in front of a REST API and nothing breaks.

Notice what these have in common: they're all about being predictable and composable. REST's real gift isn't any single rule — it's that a well-designed REST API is guessable. If GET /orders/8817 works, you can bet GET /orders/8817/items and DELETE /orders/8817 work too, without reading a single doc.

The Verbs, the Status Codes, and Two Words That Matter: Safe & Idempotent

HTTP gives you a small set of methods. Two properties decide how you can safely use each one. Safe means "reading only — calling it changes nothing on the server." Idempotent means "calling it once or five times leaves the server in the same state" — which is exactly what lets a client retry after a dropped connection without fear.

MethodMeansSafe?Idempotent?Example
GETRead a resource✅ yes✅ yesGET /orders/8817
POSTCreate a new resource (or a non-idempotent action)❌ no❌ noPOST /orders
PUTReplace a resource entirely❌ no✅ yesPUT /orders/8817
PATCHPartially update a resource❌ no➖ usually notPATCH /orders/8817
DELETERemove a resource❌ no✅ yesDELETE /orders/8817

The one that bites people is POST: it's not idempotent, so a dropped connection after "create order" leaves the client unsure whether the order exists — retry blindly and you might double-charge. The fix is an idempotency key: the client sends a unique Idempotency-Key header, and the server remembers "I already processed that key" so a retry returns the original result instead of creating a second order. (Stripe's payments API is built on exactly this — and we'll go deep on it in Day 71.)

Status codes: tell the truth in the status line

The status code is a machine-readable summary of what happened — it must be honest, because retry systems, caches, and monitoring all read it before they read your body. Learn the families, not all 60 codes:

FamilyMeansThe ones you'll actually use
2xxIt worked200 OK, 201 Created (+ a Location header), 202 Accepted (queued), 204 No Content
3xxGo look elsewhere301 moved, 304 Not Modified (your cache is still fresh)
4xxYou (the caller) made a mistake400 bad request, 401 not authenticated, 403 not allowed, 404 not found, 409 conflict, 422 validation failed, 429 rate-limited
5xxWe (the server) broke500 internal error, 503 unavailable, 504 upstream timeout

The single most important line to internalize: a 4xx means "don't retry this identical request, it'll fail again — fix the request." A 5xx means "we broke, retrying might work." Returning 200 OK with an error hidden in the body — Dave's original sin — throws that entire signalling system away.

Design Rules That Age Well

Name resources with plural nouns./orders, /customers — not /getOrder or /order-list. The collection is /orders; a member is /orders/8817. Consistency is the whole point.
Nest to show relationships, but shallowly./customers/42/orders reads beautifully. Stop at one or two levels — /customers/42/orders/8817/items/3/tax is a maze. Once a resource has its own ID, address it directly: /orders/8817.
Filter, sort, and paginate with query params — never new endpoints.GET /orders?status=shipped&sort=-created&page=2&limit=50. Every "give me a subset" is a query on the same collection, not a bespoke /getShippedOrdersSortedByDate.
Always paginate collections.Never return "all orders" — that query gets slower every day until it takes down the database. Use cursor-based pagination (?after=<cursor>) for large, changing datasets; it's stabler than ?page=N offsets.
Version from day one./v1/orders (or an Accept header). The day you must change a response shape in a breaking way, v1 lets old clients keep working while new ones move to v2. Retrofitting versioning onto a live API is painful.
Return structured, consistent errors.Pair the right status code with a machine-parseable body — the application/problem+json shape ({ "type", "title", "status", "detail" }) is a good default. Same error shape everywhere means clients write error handling once.
Make writes safe to retry.Networks drop. Support Idempotency-Key on POSTs that must not double-execute, and lean on the natural idempotency of PUT/DELETE. This ties directly to the retries and circuit breakers you'll meet in Days 23–25.

How "RESTful" Is It, Really? (Maturity & Alternatives)

REST is a spectrum, not a checkbox. The Richardson Maturity Model is the usual way to talk about how far up the ladder an API has climbed:

Level 0 — one URI, one verb

Everything is POST /api with an action buried in the body. It's "HTTP as a tunnel." This was Dave's 412-endpoint mess in disguise — technically over HTTP, RESTful in no way.

Smell: POST /api {"action":"getOrders"}

Level 1 — resources

You've split the world into addressable nouns (/orders, /customers) but still do everything with one verb. Half the idea, and already a big improvement in clarity.

Smell: POST /orders/getById

Level 2 — HTTP verbs & status codes

Verbs mean what they say, status codes are honest, caching works. This is where the vast majority of good "REST APIs" live — and it's plenty. Stripe, GitHub, and most of the web sit comfortably here.

The practical target for almost every API.

Level 3 — HATEOAS (hypermedia)

Responses include links to the next possible actions, so a client can navigate the API like a website. Elegant in theory, rare in practice — most teams find the payoff isn't worth the cost.

Aspirational; skip unless you have a real reason.

REST isn't the only front door, either. Tomorrow's GraphQL (Day 16) lets clients ask for exactly the fields they need in one round trip — great for rich, nested UIs, at the cost of harder caching. gRPC (Day 17) uses binary Protocol Buffers over HTTP/2 for blistering service-to-service speed, at the cost of human-readability. REST's enduring advantage is that it's boring in the best way: it rides plain HTTP, caches for free, is trivial to debug with curl, and every tool on earth already speaks it. Reach for the others when REST's constraints genuinely hurt — not by default.

Common Mistakes & Misconceptions

The misconceptionThe reality
"Put verbs in the URL — /getUser, /createOrder."The HTTP method is the verb. The URL is the noun. GET /users/42 and POST /orders already say "get" and "create" — repeating it in the path is the #1 tell of a non-REST API.
"Return 200 OK and put errors in the body."This blinds every machine downstream — retry logic, caches, monitoring all read the status code first. Use the right 4xx/5xx. A 200 means "it worked," full stop.
"PUT and POST are basically the same."POST creates and is not idempotent (retry → maybe two orders). PUT replaces at a known URL and is idempotent (retry → same result). That difference decides whether a retry is safe.
"REST means using JSON over HTTP."Format isn't the point. You can serve JSON from a deeply un-RESTful API (Level 0). REST is about resources, uniform verbs, statelessness, and honest status — JSON is just a common representation.
"Statelessness means the API can't have a database."Statelessness is about session state living on the server between requests, not stored data. The database is fine — what's forbidden is the server remembering "this client is halfway through step 3." Put that in the request (e.g. a token), not in server memory.
"We'll add versioning later if we need it."By then you have clients you can't break. Ship /v1 from the first release — it costs nothing up front and saves an agonizing migration later.

Active Recall

❓ A mobile client sends POST /orders to place an order. The network drops after the server created the order but before the client got the response. The client's retry logic fires the same POST /orders again. What's the risk, and exactly how do you prevent it while keeping retries safe? (click to reveal)
The risk is a duplicate order (and possibly a duplicate charge): because POST is not idempotent, the server has no way to know the second request is a retry of the first — it happily creates a second order. The fix is an idempotency key: the client generates a unique key (e.g. a UUID) once for the logical operation and sends it as an Idempotency-Key header on both the original and the retry. The server records "I've processed key abc-123 → order 8817" the first time; when the retry arrives with the same key, the server skips creation and returns the original 201 response. Now the client can retry as many times as it likes and get exactly one order. This is precisely how Stripe makes payments safe to retry — and why idempotency (Day 24) is a load-bearing idea in every payment and ordering system you'll design.

Real-World Engineering

💳 Stripe

The reference-quality REST API. Clean plural-noun resources (/v1/charges, /v1/customers), honest status codes, cursor pagination, and famously first-class idempotency keys so a dropped network never double-charges a card. Whole teams study it as the template.

🐙 GitHub

A huge, deeply nested REST API (/repos/{owner}/{repo}/issues/{n}/comments) with strict verb/status semantics, ETag-based caching (304 Not Modified), and rate limiting via 429 + headers. Also ships a GraphQL API alongside — a real-world "REST and GraphQL" story you'll appreciate after Day 16.

🎬 Netflix

Netflix ran one of the largest public REST APIs, then evolved toward gateway + GraphQL federation as its device fleet exploded — a living example of why teams reach past plain REST when one response shape can't fit a TV, a phone, and a browser at once.

☁️ Amazon S3

Object storage as pure REST: a bucket and key are a URL, and PUT/GET/DELETE on that URL are the entire interface. Idempotent PUT means uploading the same object twice is harmless — REST semantics doing real work at exabyte scale.

Flashcards (Spaced Repetition)

Q: In one sentence, what is REST?
A: A set of constraints for building APIs on HTTP where everything is a resource (a noun with a stable URL), you act on it with a fixed set of HTTP verbs (GET/POST/PUT/PATCH/DELETE), the status code honestly reports the outcome, and every request is stateless — making the API predictable, cacheable, and easy to scale.
Q: What's the difference between "safe" and "idempotent"?
A: Safe = the method changes nothing on the server (only GET). Idempotent = calling it once or many times leaves the same state, so retries are harmless (GET, PUT, DELETE are; POST is not). Idempotency is what makes retrying after a dropped connection safe.
Q: Why is returning 200 OK with an error in the body a bug, not a style choice?
A: Machines (retry systems, caches, proxies, monitoring) read the status code before the body. A 200 tells all of them "success," so failures get cached, retries stop, and dashboards look green while things burn. Use the correct 4xx/5xx so the status line tells the truth.
Q: How do you fetch just the shipped orders for customer 42, the RESTful way?
A: GET /v1/customers/42/orders?status=shipped — a filter (query param) on an existing nested collection, not a new endpoint like /getShippedOrders. Filtering, sorting, and pagination are always query params on the same resource.
Q: Which REST constraint makes horizontal scaling possible, and why?
A: Statelessness. Because the server keeps no per-client session state between requests, every request carries all it needs, so any load-balanced server can answer any request. A stateful API pins a client to one server and can't be freely spread across a fleet.

If you only remember one thing: a great API isn't a pile of clever endpoints — it's a small vocabulary. Nouns get stable addresses, a fixed handful of verbs act on them, status codes tell the truth, and every request stands alone (stateless) so the front door scales like everything behind it. Get those four right and your API becomes guessable — the highest compliment an interface can earn.
