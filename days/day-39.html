Design a Key-Value Store
Opening the Storage Box We Used Yesterday

Yesterday the URL shortener leaned on a key-value store as a black box — "store code → longUrl, look it up fast." Today we open that box and build the store itself, the kind that powers Amazon's cart, Netflix's viewing history, and half the internet's session data: Amazon DynamoDB, Apache Cassandra, Riak, Redis. The data model is the simplest in all of computing — put(key, value) and get(key), a giant dictionary. The hard part is making those two calls survive across thousands of machines that crash, drop packets, and fall behind — without losing your data and without ever going down. Here's the beautiful part: we don't need a single new idea. We assemble the whole thing from tools we already own — consistent hashing (Day 14) to spread keys, replication (Day 12) to survive failure, the CAP tradeoff (Day 10) expressed as a tunable quorum where R + W > N buys strong-enough consistency, vector clocks (Day 35) to untangle conflicts, and Merkle trees + gossip (Day 37) to heal replicas that drift. You'll place real keys on a live hash ring, kill nodes and watch keys remap, and dial N/R/W to see consistency and availability trade off in real time.

Picture this

Imagine a nationwide chain of smart parcel lockers — thousands of little automated depots in gas stations and supermarkets across the whole country. You want to drop off a package so a friend can collect it later. Every package has a tracking code (that's the key); the package itself is the value. The obvious question: which depot do you take it to? You can't search all thousand depots, and you can't keep one giant depot in the middle of the country or everyone would drive there at once. So the company uses a simple rule: a sorting machine feeds your tracking code into a hash, and the hash points at exactly one depot on a big circular map. Your friend, holding the same code, runs the same hash and drives to the same depot. No central directory needed — the code computes its own home.

But a single depot can burn down or flood. So the company never stores your package in just one place: it drops a copy in the depot the hash chose and in the next two depots clockwise on the map — three copies in all. Now your package survives any one depot vanishing. When your friend picks up, the courier doesn't trust a single depot either; it checks two of the three and takes the freshest package. When you dropped it off, the system waited until two of the three depots had it before saying "done." Two written, two read — because 2 + 2 is more than 3, the read and the write are guaranteed to share a depot, so your friend can never collect a stale package. That little bit of arithmetic is the whole secret of staying consistent without a boss.

And the depots are chatty. If one was closed for repairs and missed a delivery, a neighbor temporarily held the package with a sticky note — "belongs to Depot 7, hand over when it reopens." All day long, depots whisper short inventory summaries to a few random neighbors and compare tiny checklists, so any copy that drifts out of date gets quietly repaired. That whole picture — a code that hashes to its own home, three copies around a ring, pick-two/drop-two, and gossiping depots that heal each other — is a distributed key-value store. Hold onto it; everything today is just making this locker network work for billions of packages.

The Story

Omar was handed a deceptively small ticket: "The shopping-cart service keeps going down during sales. Build us something that just stores a cart by user ID and never, ever loses it or goes offline." A cart is about as simple as data gets — a key (user:8831) and a value (a blob of items). Omar shrugged and put it in a single big database. It worked beautifully in testing.

Then Black Friday arrived. The single database maxed out its disk and its CPU at the same time: too many carts to fit and too many requests to serve. Omar's first instinct was to buy a bigger machine — but there's always a biggest machine, and he was already near it. The real fix was to spread the carts across many machines. "How do I decide which machine holds user:8831?" he wondered. Hashing the key mod the number of servers worked — until he added a server and nearly every key suddenly mapped somewhere new, a stampede of data movement. A teammate pointed at an old lesson: "consistent hashing (Day 14) — put the servers on a ring, and adding one only moves the keys near it." Problem one solved: the keyspace was partitioned.

Relief lasted a week. Then a single machine died at 2 a.m. and every cart it held vanished — exactly the thing he'd promised would never happen. Omar realized partitioning spreads load but offers no safety: one key still lives on one machine. The answer was replication (Day 12) — keep every cart on N = 3 machines (the node the ring chose, plus the next two). Now any one machine could die and no cart was lost. But a new, subtler monster appeared: if a write reached two replicas and a read hit the one that missed it, a customer saw an old, empty cart and re-added everything — or worse, two app servers wrote to the same cart at once on different replicas and the versions disagreed. Omar had wandered straight into the CAP theorem (Day 10).

His senior engineer drew the elegant knob on a whiteboard. "You don't have to choose consistency or availability forever — you tune it per request. Keep N = 3 copies. Require a write to be acknowledged by W of them and a read to gather R of them. Make R + W > N and the set you read always overlaps the set you last wrote — so a read can't miss the latest value. Pick R = W = 2, N = 3: you tolerate one dead node on both paths and still stay consistent." For the rare case where two writes truly raced, they attached a vector clock (Day 35) so the system could tell "newer" from "concurrent" and either auto-resolve or hand both versions back to merge. And to repair replicas that silently drifted — a node that was down for an hour — they let nodes gossip and run Merkle-tree anti-entropy (Day 37) in the background. By the next sale, the "little cart store" hadn't gone down once. Omar had, without naming it, rebuilt Amazon's Dynamo — and used nearly every tool from the last six weeks to do it.

What should stay in your head
A distributed key-value store is one giant dictionary — get(key) and put(key, value) — spread safely across many machines. Three decisions define it. (1) Partition: which node owns a key? Use consistent hashing (Day 14) — hash the key onto a ring and walk clockwise to the first node, so adding/removing a node moves only nearby keys. (2) Replicate: store every key on the next N nodes around the ring (e.g. N = 3) so no single failure loses data. (3) Tune consistency: a write must be acked by W replicas and a read must gather R — and the magic rule is R + W > N, which forces the read set to overlap the write set so you never read a value older than the last successful write. That single inequality is the CAP theorem (Day 10) turned into a dial: big W = safe, slow, fragile writes; big R = safe, slow reads; small values of both = fast but eventually consistent. Everything else is cleanup for the messy real world: vector clocks (Day 35) to detect concurrent writes, hinted handoff so a temporarily-down node's writes aren't lost, and Merkle trees + gossip (Day 37) to heal replicas that drift. One-line test: a KV store is consistent hashing for placement, N-way replication for durability, and an R + W > N quorum for the consistency/availability dial.

Why This Problem Exists

A key-value store is the simplest possible database — no joins, no schema, no query language, just "here's a key, give me back the value I stored under it." That simplicity is exactly why it scales where a relational database struggles: with no cross-row relationships to honor, you're free to scatter keys across as many machines as you like. Almost every large system has a KV store hiding inside it: user sessions, shopping carts, feature flags, product catalogs, the code → URL map from yesterday, caches, user profiles. When you need massive scale and always-on availability more than you need rich queries, a KV store is the tool.

But the moment your data outgrows one machine, two brutal problems appear that a single-box database hid from you. First: placement. With a billion keys spread over hundreds of nodes, which node holds a given key — and how do you avoid reshuffling everything every time a node joins or leaves? Second: failure. At that scale a machine is always dying somewhere; the store must lose no data and keep serving through it. These are the same two questions behind yesterday's shortener — spread the load, survive the failures — but now they are the whole product. The KV store is the purest place to learn the distributed-systems playbook, because there's nothing else in the way.

The Design, Step by Step

Same discipline as yesterday: scope it, size it, sketch the API, then draw the boxes. The data model is trivial, so almost all the design effort goes into the distributed behavior — which is the whole lesson.

Step 1 — Scope the requirements

✅ Functional

get(key) → value (or "not found").

put(key, value) → store / overwrite.

Values are small (≤ ~1 MB); no range scans or joins.

🎯 Non-functional

Highly available — accept writes even during failures.

Scalable — add nodes to grow capacity linearly.

Durable & low-latency — lose nothing; single-digit ms.

🤔 Clarify early

Consistency: strong, or is eventual OK?

Value size and read:write mix?

How to resolve conflicts — LWW or app merge?

Step 2 — Size it (back-of-the-envelope, Day 30)

Suppose 1 billion keys, each key+value ~1 KB, at 100,000 reads/sec and 10,000 writes/sec, with replication factor N = 3.

# storage (remember: every key is stored N times) raw = 1,000,000,000 keys × 1 KB = ~1 TB stored = 1 TB × 3 replicas = ~3 TB # → many nodes; one box won't hold it # traffic — each logical op fans out to replicas reads = 100,000/sec → gather R each = up to ~200–300k replica reads/sec writes = 10,000/sec → push to N, ack W = ~30k replica writes/sec # nodes — if one node serves ~10k ops/sec and holds ~100 GB… nodes ≈ 3 TB / 100 GB AND traffic/throughput → dozens of nodes, scaling horizontally

The sizing already dictates the shape: 3 TB can't live on one machine, so we must partition; a machine in that fleet will die weekly, so we must replicate; and 100k reads/sec with replica fan-out means the consistency knob (how many replicas each op touches) directly controls both latency and cost. No boxes drawn yet, and the architecture is already decided.

Step 3 — Sketch the API

PUT /v1/keys/{key} request value (bytes/JSON) # optional: ?w=2 to override the write quorum response 200 OK { "version": "<vector-clock>" } # after W replicas ack GET /v1/keys/{key} response 200 { "value": …, "version": "…" } # newest of R replica responses or 409 { "siblings": [ v1, v2 ] } # concurrent writes — you reconcile or 404 not found

Two endpoints, mirroring the two methods. The only exotic bit is that a GET can return siblings — multiple conflicting versions the store couldn't auto-order — which the client (or a merge function) resolves. That 409 is CAP honesty: under a partition the store chose to accept both writes rather than reject one.

Step 4 — Draw the architecture

Any node can take any request and acts as the coordinator for it: it finds the key's replicas on the ring, fans the request out, waits for the quorum, and replies. In the background, nodes gossip membership and repair drift.

1
Client → any node (coordinator). There's no master. A load balancer (Day 5) sends the request to any node; that node coordinates it. (Smart clients can even skip a hop by hashing the key themselves.)
2
Locate replicas via the hash ring (Day 14). The coordinator hashes the key, walks clockwise to find the owner, and takes the next N − 1 nodes as replicas — the "preference list" for that key.
3
Write path. Send the value to all N replicas; once W acknowledge, tell the client "done." A down replica's write is parked on a neighbor via hinted handoff and delivered when it returns.
4
Read path. Ask all N replicas; once R reply, return the newest version. If replicas disagree, do a read repair — push the newest value back to the stale ones so the next read is clean.
5
Anti-entropy in the background (Day 37). Nodes gossip who's alive and periodically compare Merkle trees to find and repair any keys that have silently drifted between replicas.

The Heart: Partition, then Replicate

Two moves turn a dictionary into a distributed store. They're independent, and you always do them in this order: first decide where a key lives (partition), then make copies of it (replicate).

Partitioning — consistent hashing (Day 14), revisited

The naïve idea, node = hash(key) % numberOfNodes, is a trap: change the node count and almost every key remaps, triggering a cluster-wide data stampede. Consistent hashing fixes it by hashing both keys and nodes onto a circular keyspace. A key belongs to the first node you meet walking clockwise. Add a node and only the keys between it and its predecessor move; remove one and only its keys shift to the next node. In practice each physical node is placed at many points on the ring — virtual nodes — so load spreads evenly and a departing node's keys scatter to many successors instead of dumping onto one.

Replication — N copies around the ring (Day 12)

Partitioning spreads load but gives zero safety: each key still lives on exactly one node. So we store every key on N nodes — the owner plus the next N − 1 distinct nodes clockwise. This ordered list of N nodes is the key's preference list. With N = 3, any single node can die and every key it held still exists on two others. Replication is what converts "a machine died" from a data-loss catastrophe into a non-event.

✔ Partition = scale, Replicate = safety — consistent hashing answers "which node?" and minimizes movement when the cluster changes; N-way replication answers "survive how many failures?". You need both: partitioning alone loses data on any crash; replicating without partitioning doesn't scale.
✘ Don't confuse them — more virtual nodes makes placement smoother; a bigger N makes data safer (and storage more expensive). They're separate dials.

Tunable Consistency: The Quorum Dial

Now the real decision. We have N copies — but copies can disagree, because a write might reach some replicas before others (or during a network partition, Day 10). How do we read a correct value without a central coordinator forcing everyone to agree on every write? The answer is a quorum: don't talk to all N, just talk to enough that the math guarantees overlap.

Define two numbers per operation: a write waits for W replicas to acknowledge, and a read waits for R replicas to respond (returning the newest version among them). The single most important inequality in this entire lesson:

R + W > N  ⇒  the R nodes you read and the W nodes you last wrote must share at least one node  ⇒  your read is guaranteed to see the latest write.
Pigeonhole principle: if two sets drawn from N elements have sizes summing to more than N, they can't be disjoint.

That one line is the CAP theorem (Day 10) made adjustable. You trade consistency, latency, and availability by choosing R and W:

Setting (N = 3)What you getGood for
R = 2, W = 2
R + W = 4 > 3		 Strongly consistent, balanced. Tolerates 1 dead node on both reads and writes. The sensible default — Dynamo's classic choice.
W = 3, R = 1
R + W = 4 > 3		 Consistent; very fast reads (ask one node), but writes need all replicas → slow, and no write if any replica is down.Read-heavy data that rarely changes.
W = 1, R = 3
R + W = 4 > 3		 Consistent; very fast, always-available writes (one ack), but reads must gather all replicas → slow. Write-heavy logging/ingest.
R = 1, W = 1
R + W = 2 ≤ 3		 Eventually consistent. Blazing fast and maximally available, but a read can return stale data (sets may not overlap).Caches, counters, "good enough" data.

This is the lesson's deepest idea: consistency is not a property of the database, it's a property of the request. The same store can serve a strongly-consistent read and an eventually-consistent one microseconds apart, just by changing R and W. There is no universally "best" setting — only the right trade for this data.

The Hard Parts

Quorums keep reads fresh, but the real world is messier than "write W, read R." Four edges separate a toy from DynamoDB.

Concurrent writes → conflicts (vector clocks, Day 35)

Two app servers update the same cart at the same time and hit different replicas first. Now two versions exist and neither is "newer." The lazy fix is last-write-wins (LWW): stamp each write with a timestamp and keep the latest — simple, but it silently throws away one of the two updates, and clock skew can pick the wrong one. The honest fix is a vector clock (Day 35) attached to each value: it lets the store tell whether one version descends from the other (keep the newer) or they're truly concurrent (keep both as siblings and let the client merge — e.g. union the two carts). Dynamo famously chose "never drop a write," returning siblings rather than guessing.

Temporary failures → hinted handoff & sloppy quorums

If a replica is down when you write, do you fail the write? For an always-available store, no. With hinted handoff, the coordinator writes the value to a different, healthy node with a "hint" that it really belongs to the down node; when that node returns, the hint is delivered and deleted. A sloppy quorum is the same idea for the whole operation — count the first W healthy nodes, not strictly the "right" ones — trading a little consistency for staying up during failures. It's CAP, live: lean toward A, repair C afterward.

Permanent drift → anti-entropy (Merkle + gossip, Day 37)

Hints get lost; nodes stay down for hours. Replicas silently diverge. Yesterday's healing tools fix it: nodes gossip to track who's alive and run Merkle-tree anti-entropy to compare their data cheaply — swapping tree-root hashes, descending only the branches that differ, and shipping just the keys that are actually out of sync. This is the background janitor that guarantees replicas converge even after the quorum and the hints have failed.

Hot keys & big partitions

One wildly popular key (a celebrity's profile, a flash-sale item) can swamp the three nodes that hold it, no matter how big the cluster is — the classic hot-key problem. Mitigations: cache the hot key (Day 7), replicate it more widely, or shard a single logical key into sub-keys. Likewise, one hash range can accumulate too many keys (a "hot partition"); virtual nodes and good hashing spread the load, but monitoring for skew is a permanent chore.

The through-line: get/put is trivial; keeping the promise under failure is the whole discipline. Partition for scale, replicate for safety, quorum for the consistency dial, and then layer vector clocks, hinted handoff, and anti-entropy to survive the messy reality of real networks. Every one of these patterns reappears in the bigger designs ahead.

Common Mistakes & Misconceptions

The misconceptionThe reality
"Partitioning gives me durability — my data is spread out."Partitioning spreads load, not risk. Each key still lives on one node until you replicate. Spreading and copying are two separate jobs.
"Use hash(key) % N to pick the node."Modulo hashing remaps almost every key when N changes, causing a cluster-wide data stampede. Consistent hashing moves only the keys near the changed node.
"A quorum means a majority (more than half)."Not necessarily. R and W are tunable; W can be 1. What matters is R + W > N for strong reads — that guarantees overlap, not "majority."
"More replicas (bigger N) means stronger consistency."N is about durability/availability, not consistency. Consistency comes from R + W vs N. You can have N = 100 and still read stale data if R + W ≤ N.
"Last-write-wins safely resolves conflicts."LWW silently discards one concurrent update and depends on synchronized clocks. For correctness, use vector clocks and reconcile real conflicts (or keep siblings).
"A KV store is just a hash map on a server."The hash map is the easy 5%. The other 95% is partitioning, replication, quorums, conflict resolution, hinted handoff, and anti-entropy — surviving failure.

Active Recall

❓ You're designing a distributed key-value store for shopping carts: it must never lose a cart and must keep accepting writes during failures. (1) How do you decide which node holds a given key, and why not just hash % N? (2) With replication factor N = 3, what R and W would you pick to stay strongly consistent while tolerating one dead node, and what's the rule? (3) Two app servers update the same cart concurrently on different replicas — how does the store avoid losing an item? (click to reveal)
(1) Placement. Use consistent hashing (Day 14): hash keys and nodes onto a ring; a key belongs to the first node clockwise, with virtual nodes for even spread. Plain hash % N is rejected because changing the node count remaps nearly every key — a massive, needless data migration.

(2) Quorum. Pick R = 2, W = 2. The rule is R + W > N (2 + 2 = 4 > 3), which forces the read set to overlap the write set, so a read always sees the latest successful write (strong consistency). With W = 2 you can still write with one node down (survives N − W = 1 failure), and with R = 2 you can still read with one down — exactly the fault tolerance asked for.

(3) Conflicts. Attach a vector clock (Day 35) to each value. If one version descends from the other, keep the newer; if they're truly concurrent, keep both as siblings and let the client/app merge them (e.g. union the two carts) — never silently drop one as naïve last-write-wins would. Background Merkle + gossip anti-entropy (Day 37) and read repair re-sync any replicas that drifted.

Real-World Engineering

🛒 Amazon DynamoDB

The design in this lesson is Dynamo. The original 2007 paper gave us consistent hashing with virtual nodes, N/R/W quorums, vector clocks, hinted handoff, and Merkle anti-entropy — prioritizing availability ("always writeable") so a shopping cart never rejects an add-to-cart, even during a partition.

🗄️ Apache Cassandra

Took Dynamo's ring + replication + tunable consistency (you literally set the consistency level — ONE, QUORUM, ALL — per query, which is R/W in action) and added a richer column data model. The go-to for write-heavy, always-on workloads at massive scale.

⚡ Redis & Memcached

In-memory KV stores built for speed over durability — the preview of Day 40. Redis Cluster shards keys across nodes with hash slots (its flavor of consistent hashing) and replicates for failover, showing the same ideas tuned for a cache.

🔑 Riak & etcd

Riak is a faithful open-source Dynamo (N/R/W, vector clocks, siblings). At the other extreme, etcd (and ZooKeeper) are KV stores that choose strong consistency via consensus (Raft, Day 32) over availability — the CAP opposite, used for config and coordination.

Flashcards (Spaced Repetition)

Q: What are the three core design decisions in a distributed key-value store?
A: (1) Partition keys across nodes with consistent hashing; (2) Replicate each key onto N nodes for durability; (3) Tune consistency with a quorum (R read, W write) where R + W > N gives strong consistency.
Q: Why is R + W > N the magic rule, and what does it guarantee?
A: If the read set (R) and write set (W) together exceed N, they must overlap on at least one node (pigeonhole), so a read is guaranteed to see the latest successful write — strong consistency without a central coordinator.
Q: Why use consistent hashing instead of hash(key) % numNodes?
A: Modulo remaps almost every key when the node count changes (a full reshuffle). Consistent hashing moves only the keys near the added/removed node, and virtual nodes keep load even.
Q: Two concurrent writes hit different replicas. How do you avoid losing one?
A: Use vector clocks to detect whether versions are ordered or concurrent. If concurrent, keep both as siblings and let the app merge them — don't blindly last-write-wins (which drops an update).
Q: What is hinted handoff?
A: When a target replica is down, the coordinator writes the value to another healthy node with a hint about where it belongs; when the real node recovers, the hint is delivered and removed. It keeps writes available during temporary failures.

If you only remember one thing: a distributed key-value store is three decisions — partition, replicate, and dial the quorum. Place keys with consistent hashing so the cluster can grow without a stampede; copy every key onto N replicas so no single failure loses data; and control consistency per request with R and W, where R + W > N forces the read and write sets to overlap and guarantees fresh reads. That inequality is the CAP theorem turned into a knob. Everything else — vector clocks for concurrent writes, hinted handoff for temporary failures, Merkle + gossip anti-entropy for permanent drift — is keeping those promises when real networks and disks misbehave.
