Design a Twitter-like System
One Write, Many Reads

Yesterday you built a feed in isolation. Today you build the whole product around it — and discover that “design Twitter” is a trick question, because Twitter isn't one system. It's five systems wearing a trench coat: a tweet write path, a follow graph, a home timeline (the hybrid fan-out from Day 45), search, and trending — each with a wildly different read pattern. The idea that holds them together is deceptively simple: write the tweet exactly once, then build many read-optimized views from that single event. The timeline, the search index, the trending board, the like counts — none of them is “the” database; each is a materialized view fed from the same stream of tweets. Along the way you'll meet the two pieces that make Twitter uniquely Twitter: the Snowflake ID — a 64-bit number that is globally unique and sorts by time with zero coordination, which you'll build bit by bit — and trending — a real-time, approximate, windowed top-k over a firehose, which you'll run live: inject a surge and watch a hashtag rocket up the board, then decay out of the window.

Picture this

Picture a live broadcast control room. A reporter files a single story — a short line of text — and hands it to the desk. The very first thing the desk does is slap a timecode on it: a stamp that is unique and that says, precisely, when this story arrived, so every board downstream can sort by it. That stamp is the tweet's ID. The story is written down once, in the master log, and never copied again.

Then the magic: from that one desk, the same stamped story is routed to four different boards at once. It's pushed onto the personalized channels of everyone who follows the reporter (📺 the home timelines). It's filed into the station's giant archive so anyone can later search for its words (🔎 the search index). Its hashtag is tallied on the “trending now” ticker crawling along the bottom of the screen (📈 trending). And every time a viewer claps, a running applause meter ticks up (❤️ the like/retweet counts). One story in; four synchronized boards out — each board shaped completely differently, each kept up to date from the same incoming feed.

Hold the whole picture: one reporter files one stamped story (a tweet, written once, with a Snowflake ID), and a control desk routes it to four read-optimized boards — timelines, archive, trending ticker, applause meter. Nobody tries to make one board do all four jobs. That control room is a Twitter-like system: a single stream of tweet events, fanned out into many materialized views, each built for its own kind of reader.

One stamped story in; four read-optimized boards out — timelines, search archive, trending ticker, applause meter — all fed from the same stream.

The Story

Dev was asked the question every senior engineer eventually gets in an interview: “Design Twitter.” He started where everyone starts — a tweets table, a follows table, and a query that joins them to build a timeline. It worked on a laptop. Then the interviewer started adding reality: 500 million tweets a day, search across every tweet ever written, a trending list that updates every few seconds, like counts on posts that get a million likes an hour. Dev's single table buckled under the weight of trying to be everything at once — fast timelines, full-text search, real-time aggregation, and hot-counter writes, all from one place.

The breakthrough wasn't a bigger database. It was a change of shape. “Stop asking one store to serve every read,” his mentor said. “A tweet is just an event. Write it once to a log. Then build a separate, purpose-built view for each way people read.” Suddenly the design unlocked. The tweet gets written once and stamped with an ID. From there it flows onto an event stream, and a handful of independent consumers each build the one thing they're good at: the timeline service fans it out into follower inboxes (exactly the hybrid push/pull from yesterday); the search indexer tokenizes its words into an inverted index; the trending aggregator bumps a windowed counter for its hashtag; the counter service owns likes and retweets.

Two sub-problems still nagged. First, the ID: with tweets being created on thousands of machines at once, a central “give me the next number” counter would be a bottleneck and a single point of failure — yet the IDs needed to be unique and roughly sorted by time so a timeline could order them. Dev reached for Snowflake: pack a timestamp, a machine number, and a per-millisecond sequence into one 64-bit integer. No coordination, no collisions, and because the timestamp sits in the high bits, the numbers naturally sort by time.

Second, trending: you can't GROUP BY hashtag across a firehose of hundreds of thousands of tweets a second and re-sort the whole thing every few seconds. So Dev made it a stream problem — count hashtags in a sliding time window, keep only an approximate top-k, and let old counts fall off the back as the window slides. By the end, Dev hadn't built one clever database. He'd built a pipeline: one write, many reads. Which, it turns out, is exactly how the real Twitter is built.

What should stay in your head
A Twitter-like system is not one database doing five jobs; it's one event (a tweet) written once, fanned into many read-optimized materialized views, each built for a different read pattern. The write path is tiny: store the tweet once, stamp it with a Snowflake ID (a 64-bit integer = timestamp + machine id + per-ms sequence, so IDs are globally unique with zero coordination and sort by time), and emit a “new tweet” event onto a log (Kafka). From that stream, independent consumers build the views: the home timeline (hybrid fan-out — push for normal accounts, pull for celebrities — exactly Day 45); a search index (an inverted index / Elasticsearch over tweet text); trending (a windowed, approximate top-k of hashtags over a stream); and engagement counts (likes/retweets as high-throughput, often approximate, async counters). Reads never touch each other — opening your timeline, searching a word, and checking trending hit three completely different stores. The price you pay is eventual consistency between views (a tweet appears in search or trending a second or two after it's posted) and the operational cost of running many systems. One-line test: write the tweet once, stamp it with a sortable ID, and build a separate purpose-built view for every way people read.

Why This Problem Exists

“Design Twitter” is the classic interview because it forces you to confront a single table's limits. Every read a user does has a different shape, and no one storage engine is good at all of them at once:

📺 Timeline — read by person

“Give me the recent posts from everyone I follow, ranked.” This is a per-user precomputed inbox (Day 45). It wants a cache/Redis, not a scan.

🔎 Search — read by word

“Give me every tweet containing this word.” That's an inverted index over text — a completely different structure (Elasticsearch, Day 55), not a LIKE on a table.

📈 Trending — read by aggregate

“What are the top hashtags right now?” A real-time windowed top-k over a stream. You can't GROUP BY a firehose every few seconds.

❤️ Counts — read by number

“How many likes does this have?” A hot counter that may take a million writes an hour. It wants atomic increments and approximation, not a row lock.

Trying to serve all four from one normalized SQL table means every query fights every other for the same rows and indexes, and each one is on the wrong data structure for its job. The way out is to stop treating the tweet as a row to be queried many ways and start treating it as an event to be projected into many views. The tweet is written once; each read surface gets its own store, shaped for exactly how it will be read. That single reframe — one write, many reads — is why this problem exists and what it's really testing.

The Design, Step by Step

Build it from the write outward. The surprise of Twitter is how small the write path is and how much lives in the views it feeds.

The write path — posting a tweet (tiny)

1
The tweet service takes your text (+ media → object storage + CDN, Day 4) and generates a Snowflake ID locally — no round-trip to a central counter. The tweet is now uniquely, sortably named.
2
It writes the tweet once to the tweet store (a partitioned key-value / wide-column store like Cassandra, keyed by tweet ID — Day 52). This is the single source of truth. Posting returns to you immediately.
3
It emits a “new tweet” event onto Kafka (Day 19). Everything else — timelines, search, trending, counts — happens asynchronously, downstream, off this one event.

The read paths — four independent views

📺 Home timeline Consumer fans the tweet into follower inboxes — push for normal accounts, pull for celebrities (Day 45). Read = your inbox + a small celeb pull, merged & ranked.
🔎 Search index Consumer tokenizes the text and updates an inverted index (word → tweet IDs). Read = look up the word, return matching IDs, rank.
📈 Trending Consumer increments a windowed counter per hashtag. Read = the current top-k over the sliding window.
❤️ Counts Like/retweet events increment per-tweet counters (often in Redis, batched). Read = the counter value (approximate is fine).
One write, many reads: the tweet is stored once and emitted to a stream; independent consumers build four read-optimized views, each queried on its own read path.
The core move: the tweet store is the system of record; everything else is a derived view you could rebuild by replaying the event stream. That's what makes each read path independently scalable — and it's the same “log + materialized views” idea that underlies event sourcing and CQRS (coming later). A tweet is written once; the timeline, the index, the counters, and the trending board are all just different projections of it.

The Heart: One Write, Many Reads

Everything about designing Twitter follows from refusing to let one store serve every read. Let's say it precisely.

A naïve design makes the tweet table the thing you query four different ways: join it with follows for a timeline, LIKE it for search, GROUP BY it for trending, COUNT it for likes. Every one of those is the wrong access pattern for a row store, and they all contend for the same hardware. A scalable design makes the tweet event the thing, and gives each read its own store:

The payoff is independent scaling and failure isolation: a trending spike can't slow your timeline; a search re-index can't block posting; the like-counter can be eventually consistent without anyone caring. The cost is duplication and eventual consistency — the same tweet now lives, in different shapes, in four stores, and they converge a beat after the write. For a product where a two-second lag in search or trending is invisible, that's a trade you take every time. The whole art of “design Twitter” is knowing which view each read belongs to, and keeping the write path small enough that it can feed all of them.

The Snowflake ID — A Sortable Name With No Coordinator

Before any view can be built, the tweet needs a name. That name has to satisfy three things at once, and they fight each other:

🔑 Globally unique

Billions a day, generated on thousands of machines at once, must never collide.

⏱ Roughly time-sortable

Sorting IDs should sort tweets by time, so timelines and “since this ID” pagination just work.

🚫 No central coordinator

A single “next number” service would be a bottleneck and a single point of failure at this scale. IDs must be generated locally.

A plain auto-increment column fails #3 (it needs one coordinator). A random UUID fails #2 (random bits don't sort by time) and is bulky. Twitter's answer, Snowflake, is to pack the three requirements into the bits of a single 64-bit integer:

A 64-bit Snowflake ID: a timestamp in the high bits (so IDs sort by time), a machine id (so no two machines collide), and a per-millisecond sequence (so one machine can mint 4096 IDs per ms).

Why this works — read it field by field

  • 41 timestamp bits (milliseconds since a custom epoch) sit in the high bits. Because they dominate the number's magnitude, a later tweet is a larger integer — sorting IDs sorts by time, for free. 41 bits of milliseconds ≈ 69 years of range.
  • 10 machine bits give 1024 distinct generators. Two machines stamping a tweet in the same millisecond still produce different IDs, because their machine field differs — so no coordination is needed to stay unique.
  • 12 sequence bits give 4096 IDs per machine per millisecond. If one machine makes several tweets in the same ms, it just increments the sequence. (Mint more than 4096 in a single ms? Wait for the next ms — a tidy little back-pressure valve.)

The result is a compact 64-bit number that is unique, sortable, and coordination-free — which is exactly what the Try It Yourself builder above demonstrates: stamp two tweets and the second ID is larger; burst five in one millisecond and the sequence field keeps them distinct; switch machines and the same instant yields different IDs.

Snowflake in one line: id = (ms_since_epoch << 22) | (machine_id << 12) | sequence — timestamp high (sortable), machine next (collision-free), sequence low (per-ms headroom). One 64-bit integer, no coordinator.

Trending, Search & the Social Graph

Three of the four views deserve a closer look — each is a classic sub-problem in its own right.

Trending — a windowed, approximate top-k over a stream

You cannot answer “what's trending?” by re-counting every tweet ever. Trending is inherently about now, so it's a stream problem (Day 19 streams; later, Kafka Streams / Flink, Day 59): maintain counts over a sliding time window (say the last few minutes), keep an approximate top-k rather than exact counts for every one of millions of hashtags, and let old counts fall off the back as the window advances — which is exactly why a surging tag climbs and then decays once its burst leaves the window, as you saw in the board above. At real scale the exact per-tag counts are replaced by sketches (count-min sketch, heavy-hitters) so memory stays bounded even with a long tail of hashtags. Trending is “popular recently,” not “popular ever.”

Search — an inverted index, not a table scan

Full-text search over every tweet is the same shape as Day 11's indexing turned inside out: instead of row → words, you store word → list of tweet IDs — an inverted index. The search indexer consumes the tweet stream, tokenizes the text, and appends each tweet's ID to the posting list of every word it contains. A query for “system design” intersects two posting lists and ranks the matches. This is what Elasticsearch (Day 55) is built for; it's near-real-time, so a tweet becomes searchable a second or two after posting.

The social graph — who follows whom

The follow graph is its own store: potentially trillions of edges, read constantly (every fan-out needs “who follows X?” and every profile needs “who does X follow?”). It's typically a sharded store (Day 13) holding both directions of the edge, or a purpose-built graph store (Day 56). Its read pattern — “give me all followers of this account” — is exactly what the timeline fan-out depends on, which is why a celebrity's enormous follower list is what makes pure push explode (Day 45) and why the hybrid pulls them instead.

🧱 Each view scales alone

Timeline cache, search cluster, trending job, counter store, and graph store are separate services — scale, deploy, and fail independently.

📏 Estimate first (Day 30)

~500M tweets/day ≈ 6k writes/sec average (far higher at peak), but reads dwarf writes — timelines, search, and trending are all read-heavy surfaces.

The Hard Parts

“One write, many reads” is the clean 80%. These edges are where real Twitter-scale design lives.

Clock skew and the Snowflake timestamp

Snowflake IDs sort by time only if machine clocks are roughly in sync and never run backwards. If a server's clock jumps backward (an NTP correction), a naïve generator could mint an ID in the “past” and break monotonicity — or worse, collide. Real implementations refuse to generate while the clock is behind the last-seen timestamp, waiting until it catches up. The sortability is “roughly,” not “perfectly,” ordered across machines — good enough for timelines, not a substitute for a true logical clock (Day 35).

Eventual consistency between views

Because the views are fed asynchronously, they disagree for a moment: your tweet is posted (in the tweet store) but not yet in a follower's timeline, not yet searchable, not yet counted in trending. Usually invisible — but it means “I posted it, why can't I find it in search?” is expected for a second or two, and any feature that needs read-your-own-writes has to read the system of record, not a view.

Hot counters and the thundering herd

A tweet that goes viral gets likes faster than a single counter row can be updated safely. You don't take a lock a million times — you shard the counter, buffer increments in memory, and flush periodically, accepting a slightly approximate, slightly delayed count. Nobody needs the like count to be exact to the millisecond; they need it to be fast and roughly right.

Rebuilding a view

Because every view is derived from the tweet stream, you can rebuild it by replaying the log — re-index all of search, or regenerate timelines after a bug. That's a superpower of the “log + materialized views” shape: the system of record is small and durable; the big, complex read stores are disposable and reconstructible. The flip side is operational weight — you're now running Kafka, Cassandra, Redis, Elasticsearch, and a stream processor, each with its own failure modes.

The through-line: write once → stream → many views is the skeleton; doing it with clock-safe Snowflake IDs, windowed approximate trending, near-real-time search, sharded approximate counters, and clear rules about which reads hit the system of record versus a view is the craft. Get those right and one tweet quietly becomes five perfectly-shaped answers.

Real-World Engineering

❄️ Twitter Snowflake

Snowflake is a real Twitter open-source project: 64-bit IDs with a 41-bit timestamp, a 10-bit machine/worker id, and a 12-bit sequence, generated with no central coordinator. It replaced a database auto-increment that couldn't keep up, and the time-sortable property is what lets timelines and “since id X” pagination work. Many companies (Instagram, Discord with its “snowflakes,” Sony) adopted the same idea.

📺 Twitter Timelines

The home timeline is the hybrid fan-out from Day 45 — tweets pushed into per-user Redis-backed timelines, with high-follower accounts merged in at read time to avoid fan-out storms. It's one view among several, not “the database.”

🔎 Search & the Firehose

Tweet search is powered by inverted indexes (Lucene/Elasticsearch lineage), fed near-real-time from the tweet firehose — the same event stream that feeds analytics and trending. A tweet becomes searchable seconds after posting, a visible sign of eventual consistency between views.

📈 Trends

Trending topics are computed as windowed, approximate aggregations over the stream, with signals beyond raw count (velocity/acceleration of a hashtag, personalization by location and interest) so a sudden surge trends even before its absolute count is huge — and fades as the window moves on.

Flashcards (Spaced Repetition)

Q: In one sentence, what is the core architecture of a Twitter-like system?
A: One write, many reads — a tweet is written once (stamped with a Snowflake ID, emitted to a Kafka stream) and projected into several read-optimized materialized views (home timeline, search index, trending counters, engagement counts), each built for its own read pattern and converging via eventual consistency.
Q: What is a Snowflake ID and how is it laid out?
A: A 64-bit integer = timestamp (41 bits) | machine id (10 bits) | sequence (12 bits). Timestamp in the high bits ⇒ IDs sort by time; machine id ⇒ no coordination, no collisions; per-ms sequence (4096) ⇒ bursts on one machine. id = (ts<<22)|(machine<<12)|seq.
Q: Why not use a central auto-increment or a UUID for tweet IDs?
A: A central counter is a bottleneck + single point of failure at Twitter scale. A UUID is unique but doesn't sort by time (and is bulky). Snowflake gets both: unique and time-sortable, generated locally with no coordinator.
Q: How is “trending” computed at scale?
A: As a windowed, approximate top-k over a stream: count hashtags within a sliding time window, keep an approximate top-k (sketches for the long tail), and let old counts decay as the window slides. Trending = popular recently, not ever — you never re-aggregate the whole firehose.
Q: Why can each read surface (timeline, search, trending, counts) scale and fail independently?
A: Because each is a separate materialized view fed asynchronously from the tweet stream — none shares a store with the others. A trending spike can't slow timelines; a search re-index can't block posting. The cost is duplication + eventual consistency, and views can be rebuilt by replaying the log.

If you only remember one thing: a Twitter-like system is one write, many reads — the tweet is written once, stamped with a time-sortable Snowflake ID, emitted to a stream, and then projected into a separate materialized view for every way people read: the home timeline (yesterday's hybrid fan-out), search (an inverted index), trending (a windowed, approximate top-k over the stream), and engagement counts (sharded, approximate counters). The price of the whole design is eventual consistency between views and the operational weight of running many systems; the reward is that each surface scales, fails, and is rebuilt independently.
