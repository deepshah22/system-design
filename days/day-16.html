GraphQL Architecture
Let the Client Draw the Response

Yesterday's REST API is a fixed menu: each endpoint hands back a fixed shape, take it or leave it. That's elegant until a phone on a slow train needs a user's name and their last order's total — and REST forces it to download 40 fields it won't use, then make four more round trips for the rest. GraphQL flips the control: one endpoint, and the client writes a query describing exactly the fields it wants from your data — which GraphQL models as a typed graph. It fixes over-fetching and under-fetching in one stroke — and quietly hands you a new set of problems in return.

Picture this

Yesterday's restaurant served fixed combo meals — each endpoint a numbered plate that always came the same way. Today, walk next door to an à la carte counter. There's no menu of plates; there's a single order slip and a pen. You write down exactly what you want — "the salmon, half a scoop of rice, no sauce, and one of the desserts from the back" — hand it over one time, and a single tray comes back shaped precisely like your slip: nothing you didn't ask for, and everything you did, in one trip. There's only one window (one endpoint), and behind it the kitchen knows how every ingredient connects — which desserts belong to which meals — so it can fetch across the whole pantry in a single pass. That order slip is a GraphQL query: you describe the response, the server draws it. Picture the pen in your hand and the tray that matches your slip exactly — that image is GraphQL.

The Story

Mobile Mika was building one screen: a user's profile header. It needed three things — the person's name, their avatar, and the total of their last three orders. With the REST API next door, she called GET /users/42. Back came a 40-field JSON blob: address, phone, marketing preferences, a 2 KB bio, timestamps she'd never render. She used three fields and threw away thirty-seven. That's over-fetching — and on a phone metered by the megabyte on a slow train, it hurt.

Worse was the orders. GET /users/42 didn't include them, so she called GET /users/42/orders — a second round trip. That returned a list of order IDs, not totals, so now she looped: GET /orders/7, GET /orders/8, GET /orders/9. One little header had become five round trips, each paying the full latency tax of a mobile network. That's under-fetching: no single endpoint gave her exactly what the screen needed, so she stitched it together with a waterfall of calls. The app felt sluggish, and it wasn't the code — it was the shape of the API.

A backend engineer showed her the same data through a GraphQL endpoint. She wrote one query: { user(id: 42) { name avatarUrl orders(last: 3) { total } } } — literally the shape of what she wanted. One request. One response, containing her three fields and nothing else, orders and totals already joined in. Five round trips collapsed to one; the 40-field blob shrank to the three fields she'd asked for. Mika hadn't sped up the network or the database — she'd stopped letting the API decide the shape of her data, and drawn it herself.

What should stay in your head
GraphQL is a query language for your API plus a typed schema that exposes your data as a graph of connected types. There's one endpoint (POST /graphql); the client sends a query that describes the exact fields it wants, and the server returns a JSON response shaped identically to the query — no more, no less. This kills over-fetching (too many fields) and under-fetching (too many round trips) in one move. The price: because every request is a different POST to the same URL, you lose REST's free HTTP/URL caching, and naïve field-by-field resolvers can explode into the N+1 query problem. REST decides the shape for you; GraphQL hands you the pen — and the responsibility.

The Twin Problems GraphQL Was Built to Kill

GraphQL came out of Facebook in 2012, born from a very specific pain: their mobile apps were slow, and the culprit was the shape of their REST API, not the servers behind it. Two symptoms, opposite directions:

Over-fetching — you get more than you need

A REST endpoint returns a fixed representation. GET /users/42 ships every field the designers thought anyone might want. A screen that needs one field still downloads all forty. Multiply that by millions of requests on metered mobile connections and it's real money and real latency — bytes burned rendering nothing.

Under-fetching — you need more than one endpoint gives

The mirror image: no single endpoint has exactly what a screen needs, so the client makes a waterfall of calls — get the user, then their orders, then each order's items — each one waiting on the last. This is the N+1 round-trip problem at the network layer: 1 call to list N things, then N more to hydrate them. On a 150 ms mobile round trip, five sequential calls is three-quarters of a second of pure waiting.

GraphQL dissolves both at once: the client sends a single query naming exactly the fields it wants, across as many related types as it wants, and gets one right-sized response back. The shape of the request is the shape of the response.

Schema, Types & Resolvers — How It Actually Works

Three ideas carry the whole system. Get these and GraphQL stops being magic.

1. The schema is a typed graph — a contract both sides trust

Every GraphQL server starts with a schema: a strongly-typed description of every type, its fields, and how types connect. It's written in the Schema Definition Language (SDL):

type User {
  id: ID!
  name: String!
  email: String!
  orders(last: Int): [Order!]! # a User connects to many Orders
}
type Order {
  id: ID!
  total: Float!
  items: [Product!]! # and an Order connects to many Products
}

Because User.orders points at Order, and Order.items points at Product, your data is literally a graph the client can traverse in one query. The ! means non-null; [Order!]! is a non-null list of non-null Orders. This schema is also the API's living documentation — tools read it to give you autocomplete and validation before a query ever runs. That strong typing is a headline feature: a query asking for a field that doesn't exist fails before execution, not with a runtime surprise.

2. Resolvers — one function per field

The schema says what exists; resolvers say how to fetch it. Each field has a resolver function that returns that field's value. When a query for user { name orders { total } } arrives, the engine resolves user, then name on the result, then walks into orders, then total on each order. The client's query shape becomes a traversal plan over your resolvers. This is the source of GraphQL's power and its most infamous trap — see the N+1 problem below.

3. Introspection — the API describes itself

A GraphQL server can be asked about its own schema at runtime (__schema, __type). This introspection is what powers the interactive explorers (GraphiQL, Apollo Sandbox), auto-generated typed clients, and editor autocomplete. The uniform, typed graph is what makes all that tooling possible — the same way REST's uniform interface enabled OpenAPI (Day 15).

Queries, Mutations & Subscriptions — the Three Verbs

Where REST has five HTTP verbs, GraphQL has three operation types, and they map cleanly onto read / write / stream:

queryRead data. The safe, idempotent read — the GraphQL analogue of GET. Multiple queries in one request run in parallel.
mutationWrite data (create/update/delete). Like POST/PUT/DELETE rolled into named operations (createOrder, cancelOrder). Multiple mutations in one request run sequentially, so ordering is predictable.
subscriptionStream data pushed from the server over a persistent connection (usually WebSockets) — new chat messages, live scores. This is the real-time push we'll dig into on Day 20.

All three share the same schema and the same field-selection syntax — you always name exactly the fields you want back, whether you're reading, writing, or streaming.

What GraphQL Costs You (Nothing Is Free)

GraphQL solves REST's fetching problems by moving flexibility to the client — and every bit of that flexibility becomes a server-side problem you now own. A staff engineer's job is knowing these before you adopt it, not after.

The N+1 problem — power's dark twin

Say a query asks for 100 users and each user's company. The naïve resolver runs 1 query for the users, then 1 query per user for the company — 101 database hits for one API call. This N+1 is the single most common GraphQL performance disaster. The standard fix is batching with a tool like DataLoader: it collects all the company IDs requested in one tick and fires a single WHERE id IN (...) — turning N+1 into 2. If you take one operational lesson from this lesson, it's this one.

Caching gets much harder

REST's superpower was that GET /users/42 is a cacheable URL — browsers, CDNs, and proxies cache it for free (Day 6). GraphQL sends every query as a POST to the same /graphql URL, so URL-based HTTP caching doesn't apply. You recover caching at other layers: persisted queries (register a query, reference it by hash so a CDN can cache it), client-side normalized caches (Apollo, Relay store entities by id), and server-side response caching. It's caching — just not the free kind you got with REST.

A malicious or careless query can be a bomb

Because clients compose their own queries, a single request can ask for a deeply nested, expensive graph: user { friends { friends { friends { ... } } } }. Left unchecked, one query can exhaust your database. Production GraphQL needs guardrails: query depth limiting, complexity analysis (assign a cost to each field, reject queries over a budget), timeouts, and — the strongest control — an allow-list of persisted queries so clients can only run pre-approved shapes. Ordinary per-URL rate limiting (Day 24) doesn't fit, because it's all one URL.

Other rough edges

Errors always come back 200.GraphQL typically returns 200 OK with an errors array in the body, even for partial failures. Your Day-15 instinct — read the status code — doesn't work here; monitoring must parse the payload.
File uploads & binary aren't native.GraphQL speaks JSON. Large file uploads/downloads usually still go through a plain REST/HTTP endpoint alongside it.
More upfront machinery.Schema, resolvers, a GraphQL server, and client tooling are more moving parts than "return some JSON." For a small CRUD service, REST is often simply less to build and operate.

REST vs GraphQL — Choosing the Front Door

✓ Reach for GraphQL when…

• Many clients, each needing different field subsets • Rich, relational data (a graph of entities) • Mobile clients where bytes & round trips hurt • The frontend iterates fast & hates waiting on new endpoints • You're aggregating several backends behind one schema

✗ Prefer REST when…

• Simple, CRUD-shaped resources • You want free HTTP/CDN caching by URL • A public API where cache-ability & simplicity win • File uploads, streaming binaries • A small team that doesn't want the extra machinery

EndpointsMany (one per resource)One (/graphql)
Who picks the response shapeThe server (fixed)The client (per query)

The honest summary: it's not REST vs GraphQL as good vs bad. Many large companies run both — GraphQL for the flexible, client-driven read layer, REST for simple public endpoints and uploads. GraphQL trades REST's free cacheability and simplicity for precise, one-trip field selection. Knowing which pain you have — over-fetching or endpoint sprawl vs caching and simplicity — is the whole decision.

Common Mistakes & Misconceptions

The misconceptionThe reality
"GraphQL replaces REST — it's just better."They're different trade-offs. GraphQL wins for flexible, client-driven, relational reads; REST wins for simple resources, free URL caching, uploads, and low operational overhead. Plenty of systems run both side by side.
"One endpoint means one database query."The opposite risk is real: a naïve resolver turns one query into the N+1 problem — 101 DB hits for 100 users. You must batch (DataLoader) or you'll melt your database.
"GraphQL is automatically faster."It reduces over-fetching and round trips, which helps clients. But it can hammer your backend harder and it throws away REST's free HTTP caching — net performance depends entirely on how you build the resolver and caching layers.
"Clients can ask for anything, so we're flexible."Unbounded flexibility is a denial-of-service vector: a deeply nested query can exhaust your DB. Production needs depth limits, complexity budgets, timeouts, and ideally persisted-query allow-lists.
"A 200 means it worked."GraphQL returns 200 even on partial failure, with the problems in an errors array. Monitoring and clients must inspect the body, not just the status line.
"GraphQL is a database / it queries the DB directly."No — it's an API layer. Resolvers can pull from SQL, NoSQL, other microservices, caches, or third-party APIs. The graph is a view over whatever backends you wire up.

Active Recall

❓ A teammate says: "We switched from REST to GraphQL and our database load tripled, even though the mobile app got faster. How is that possible?" Explain what almost certainly happened and how you'd fix it. (click to reveal)
This is the N+1 problem in the flesh. GraphQL made the client faster by cutting over-fetching and round trips — the app now makes one request instead of five. But on the server, a query like { users { company { name } } } resolves company once per user: 1 query to load the users, then N more, one per user — 101 database hits where REST's fixed endpoint might have done a single join. The response looks clean; the resolver underneath is a hidden loop of queries. The fix is batching: a DataLoader collects every company ID requested during one execution tick and issues a single SELECT ... WHERE id IN (...), turning N+1 into 2. Add query-complexity/depth limits so a client can't request an arbitrarily deep graph, and consider server-side caching for hot fields. The lesson: GraphQL moves flexibility to the client, but that flexibility becomes your problem to bound on the server.

Real-World Engineering

📘 Meta / Facebook

GraphQL was created at Facebook in 2012 and open-sourced in 2015 to fix exactly Mika's problem: their mobile News Feed was slow because REST endpoints over-fetched and forced round trips. The query language is the origin story of client-drawn responses.

🐙 GitHub

GitHub runs a public GraphQL v4 API alongside its REST v3 — a rare, honest side-by-side. They use query cost analysis (each query has a computed point cost against a rate budget) precisely because per-URL rate limiting doesn't fit a single endpoint.

🛍️ Shopify

Shopify's Storefront and Admin APIs are GraphQL-first, letting thousands of third-party apps request exactly the fields they need. They enforce a calculated query cost and throttle on it — a textbook example of bounding client flexibility.

🎬 Netflix

Netflix built a federated GraphQL layer (DGS + a gateway) so a single schema stitches together dozens of backend microservices. Frontend teams query one graph; the gateway routes each field to the owning service — GraphQL as an aggregation front door.

Flashcards (Spaced Repetition)

Q: In one sentence, what is GraphQL?
A: A query language and typed schema that exposes your data as a graph through a single endpoint, where the client sends a query describing exactly the fields it wants and gets back a response shaped identically — eliminating over-fetching and under-fetching.
Q: What are over-fetching and under-fetching?
A: Over-fetching = an endpoint returns more fields than the client needs (download 40, use 3). Under-fetching = no single endpoint has everything a screen needs, so the client makes a waterfall of round trips (N+1 at the network layer). GraphQL fixes both by letting the client request exactly what it wants in one query.
Q: What is a resolver, and what's the N+1 problem?
A: A resolver is a function that fetches the value for one field. The N+1 problem: resolving a list of N items and a related field on each runs 1 query for the list + N queries for the relation (101 DB hits for 100 items). Fix it by batching with a DataLoader (one WHERE id IN (...)).
Q: Why is caching harder in GraphQL than REST?
A: REST's GET /users/42 is a cacheable URL that browsers/CDNs cache for free. GraphQL sends every query as a POST to the same /graphql URL, so URL-based HTTP caching doesn't apply. You recover it with persisted queries (cache by query hash), client-side normalized caches (Apollo/Relay), and server-side caching.
Q: Name GraphQL's three operation types.
A: query (read, like GET), mutation (write — create/update/delete, run sequentially), and subscription (server-pushed real-time stream over a persistent connection, usually WebSockets).

If you only remember one thing: GraphQL hands the client the pen. Instead of the server deciding fixed response shapes (REST), the client sends one query naming exactly the fields it wants across your typed data graph, and gets back a response shaped identically — killing over-fetching and under-fetching in a single trip. The bill for that flexibility lands on the server: no free URL caching, resolvers that can explode into N+1, and queries you must bound before they melt your database. It's not "better than REST" — it's a different trade: precise, one-trip field selection in exchange for cacheability and simplicity.
