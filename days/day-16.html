GraphQL Architecture
Ask for Exactly What You Want

Yesterday REST gave every resource a tidy URL. But a single mobile screen rarely wants a single resource — it wants a user's name, their last three orders' totals, and each order's tracking status, all at once. With REST you either over-fetch (download whole objects to use one field) or under-fetch (make a waterfall of round trips). GraphQL flips who's in control: one endpoint, and the client sends a query describing the exact shape of data it wants — no more, no less — and gets back JSON in precisely that shape.

Picture this

Picture two ways to order lunch. At the REST deli, the menu is a wall of numbered combo meals: Combo #7 is "sandwich, chips, pickle, drink." You wanted just the sandwich and the pickle — but Combo #7 comes as a fixed plate, so you take the chips and drink you'll throw away (over-fetching). And if you also wanted a cookie, that's not in Combo #7, so you get back in line and order a second thing (under-fetching — another round trip). At the GraphQL counter, there are no fixed combos. You hand the clerk one index card: "half sandwich, no cheese, one pickle, one cookie — nothing else." They read your card, walk the kitchen once, and hand back exactly that, in one trip. The index card is your query; the single counter is the one endpoint; the clerk walking to each station is the resolvers fetching each field. Hold that image: REST hands you fixed plates; GraphQL reads your card and builds the plate to order.

The Story

Mobile-team Mei was building a profile screen: a photo, a name, and the titles of the user's three most recent posts with a comment count on each. The backend was a clean REST API — the one Amara built yesterday. So Mei called GET /users/42. It returned the user… and forty fields she didn't need: billing address, password-reset timestamps, notification settings, a giant preferences blob. On a phone on a train, that payload was eight times bigger than the three fields she'd use. Over-fetching.

Worse, the user object didn't contain the posts. So Mei called GET /users/42/posts. That gave post IDs and titles — but not comment counts. So for each of the three posts she called GET /posts/{id}/comments to count them. One screen had become five sequential round trips, each waiting on the last, each adding a slow mobile network's latency. Under-fetching. The screen took two seconds to paint and Mei was writing "stitching" code to glue five responses together.

A backend engineer showed her a different door. "What if you could just… describe what the screen needs, and get back exactly that?" He opened a single endpoint, /graphql, and typed a query that read almost like the JSON Mei wanted: user(id: 42) then, indented underneath, name, avatarUrl, and posts(last: 3) with title and commentCount nested inside. He hit run. One request. Back came a JSON object in exactly that shape — the name, the avatar, three posts, each with a title and a count. No billing address. No second trip. No stitching. Mei stared at it. She hadn't asked the server for a resource; she'd handed it a shape, and the server had filled it in.

What should stay in your head
GraphQL is a query language for your API plus a runtime that answers those queries. Instead of many URLs each returning a fixed shape (REST), there is one endpoint and a typed schema describing every field a client could ask for. The client sends a query whose structure mirrors the JSON it wants; the server runs a resolver for each requested field and returns data in exactly that shape — no over-fetching, no waterfall of round trips. The power (ask for precisely what you need, in one trip) comes with a cost: HTTP caching, rate-limiting, and query-cost control all get harder, and a naïve implementation invites the N+1 problem. You trade REST's rigid simplicity for flexibility — and inherit the job of managing that flexibility.

The Schema & Type System — GraphQL's Beating Heart

REST's contract lives in documentation and tribal knowledge. GraphQL's contract lives in a schema — a strongly-typed, machine-readable description of every type and field your API exposes. The schema is the single source of truth: it's what validates queries, powers auto-complete in tools, and generates documentation for free. Here's a slice of the one behind the explorer above:

schema.graphqltype User { id: ID! name: String! avatarUrl: String email: String! posts(last: Int): [Post!]! } type Post { id: ID! title: String! body: String! commentCount: Int! } type Query { user(id: ID!): User }

Three ideas make the type system click:

Everything has a type, and the graph is literal.A User has a posts field of type [Post!]! — a list of Posts. That is an edge in a graph: from a user node you can traverse to post nodes. Clients navigate this graph by nesting fields, which is where the name "GraphQL" comes from.
The ! means non-null.String! promises the field is never null; String may be null. This is a contract the server must honor, and clients can rely on it — no more defensive null-checking every field "just in case."
Three special root types are the entry points.Query (read), Mutation (write), and Subscription (real-time stream). Every operation starts at one of these three doors and walks down into the graph.

Because the schema is introspectable — you can literally query the API for its own shape — tooling is extraordinary: type-ahead in editors, auto-generated docs, and end-to-end type safety from server to client. The schema is the API's contract, its documentation, and its validation layer, all at once.

Queries, Mutations & Subscriptions — The Three Verbs

REST spread its intent across five HTTP methods. GraphQL narrows it to three operation types, and — a crucial detail — all three normally travel as HTTP POST requests to the single /graphql endpoint. The operation type, not the URL or method, says what you're doing.

query — read

Fetch data. The rough equivalent of a REST GET. Safe and (in principle) idempotent. Multiple fields in one query are fetched in parallel by the server.

query { user(id:42){ name } }

mutation — write

Create, update, or delete — the equivalent of POST/PUT/PATCH/DELETE. Top-level mutation fields run sequentially (not in parallel) so writes have a defined order.

mutation { addPost(title:"Hi"){ id } }

subscription — stream

A long-lived connection (usually over WebSockets) where the server pushes updates as they happen — new comments, live scores. A cousin of the real-time patterns we meet on Day 20.

subscription { commentAdded { text } }

Notice a mutation still asks for a return shape ({ id } above): after you change something, you describe what you want back — often the freshly-updated object — in the same round trip. Write and read-back become one operation.

Resolvers & the Infamous N+1 Problem

A resolver is a function that knows how to fetch one field. When a query arrives, the server walks the query tree and calls a resolver for each field: a User.name resolver, a User.posts resolver, a Post.commentCount resolver. Resolvers are where GraphQL meets your actual databases, caches, and other services — and where the single most famous GraphQL performance trap lives.

The trap

Consider the query "give me 10 users, and for each, their post count." A naïve implementation runs 1 query to fetch the 10 users, then — because the postCount resolver fires once per user — 10 more queries, one per user, to count posts. That's the N+1 problem: 1 query to get the list, then N queries for a field on each item. Ask for 100 users and you've fired 101 database queries to render one screen. It's silent, it passes every test on small data, and it melts the database in production.

✗ N+1 (naïve resolver)

SELECT * FROM users LIMIT 10; -- 1 SELECT count(*) ... WHERE user=1; -- +1 SELECT count(*) ... WHERE user=2; -- +1 ... (8 more, one per user) -- = 11

✓ Batched (DataLoader)

SELECT * FROM users LIMIT 10; -- 1 SELECT user, count(*) ... WHERE user IN (1,2,...,10) GROUP BY user; -- = 2 total

The fix: batch & cache per request

The standard solution is a DataLoader (a pattern Facebook open-sourced). Instead of each resolver hitting the database immediately, it registers the key it needs (user 3's posts). DataLoader waits until the current tick collects all the keys, then fires one batched query (WHERE user IN (1,2,…,10)) and hands each resolver its slice. It also de-duplicates and caches within a single request, so asking for the same user twice hits the database once. The lesson generalizes far beyond GraphQL: whenever you see a per-item fetch inside a loop, look for a way to batch it. This is the same instinct behind cache read-through (Day 6) and why IN queries beat loops of single lookups.

REST vs GraphQL — Choosing, Not Cheerleading

GraphQL is not "REST but better." It's a different set of trade-offs that shine for a specific shape of problem. Reach for it when clients are diverse and data is deeply connected; stick with REST when simplicity, caching, and public reach matter most.

DimensionRESTGraphQL
EndpointsMany, one per resourceOne (/graphql)
Data shapeServer decides (fixed)Client decides (per query)
Over/under-fetchingCommon — fixed payloadsEliminated — ask for exact fields
Round trips for a rich screenOften many (waterfall)Usually one
HTTP cachingEasy — GET + URL + status codesHard — POST to one URL; needs app-level caching
Learning curve / toolingLow; understood everywhereHigher; needs a schema & a server runtime
Error handlingHTTP status codes carry itUsually 200 OK with an errors array in the body
Best fitPublic APIs, simple CRUD, file up/download, heavy cachingRich apps, many client types, deeply related data, rapidly-evolving front-ends

A telling real-world signal: GitHub offers both. Their REST API (v3) is perfect for simple, cacheable, script-friendly calls; their GraphQL API (v4) is what you reach for when you want "this repo's last 5 issues, each with its author's name and label colors" in a single request. Mature systems often run both and let each client pick the door that fits.

The Hard Parts (What GraphQL Makes Your Problem)

The flexibility that makes GraphQL powerful also hands you responsibilities REST solved for free. A principal engineer picks GraphQL knowing this bill comes due:

Caching moves up a layer.REST leaned on HTTP: cache a GET by its URL, revalidate with ETag. GraphQL sends a POST to one URL, so HTTP caches see everything as the same opaque request. You cache at the application layer instead — normalized client caches (Apollo, Relay) keyed by object id, and persisted/whitelisted queries so a CDN can cache by query hash.
Any client can ask for an expensive query.A single query can nest deeply (user → posts → comments → author → posts …) and, unbounded, become a denial-of-service by accident. You defend with query depth limits, complexity scoring (assign a cost per field, reject queries over a budget), and persisted queries that only allow pre-approved shapes.
Rate limiting isn't "requests per minute."One GraphQL request can be trivial or enormous. Counting requests is meaningless; you rate-limit by query cost instead — GitHub literally publishes a point budget per query. (We build the general machinery on Day 24.)
Errors live in the body.Because most responses return 200 OK, clients must inspect an errors array rather than the status line — and a query can partially succeed (some fields resolve, others error), which is powerful but needs deliberate handling.

None of these are reasons to avoid GraphQL — they're the reasons it's an architecture, not just a library. The right question is never "which is better?" but "does my problem look like diverse clients over deeply-connected data, and is my team ready to own caching and cost control?"

Common Mistakes & Misconceptions

The misconceptionThe reality
"GraphQL replaces REST — it's just newer and better."They optimize for different things. REST wins on simplicity, HTTP caching, and public reach; GraphQL wins on flexible, connected data for many client types. Plenty of great systems (GitHub) run both. Pick per problem.
"One endpoint means one database query."The opposite risk is real: a naïve resolver fires the N+1 pattern — 1 query for the list plus 1 per item. You must batch (DataLoader) or you'll issue hundreds of queries per request.
"GraphQL is automatically faster."It reduces over-fetching and round trips, which helps mobile a lot. But an unbatched, deeply-nested query can be far slower than a well-designed REST call. Speed comes from good resolvers, not the protocol.
"You lose all caching."You lose easy HTTP caching, not caching itself. You move it up: normalized client caches keyed by id, and persisted queries a CDN can cache by hash.
"Errors show up as HTTP 4xx/5xx like REST."Most GraphQL responses return 200 OK with an errors array in the body — and can be partially successful. Clients must read the body, not just the status line.
"Exposing the whole schema is free flexibility."It's also an attack surface. Without depth limits, complexity scoring, or persisted queries, a single crafted query can become an accidental DoS.

Active Recall

❓ Your GraphQL API works perfectly in testing, but in production the "team dashboard" page (which lists 50 members, each with their open-task count) is hammering the database with hundreds of queries per page load and timing out. What's happening, and how do you fix it without changing the query the front-end sends? (click to reveal)
This is the N+1 problem. The openTaskCount resolver fires once per member: 1 query to load the 50 members, then 50 more to count each one's tasks — 51 queries for one page. Tests passed because the test team had two members, not fifty. The fix is to batch the per-item fetches with a DataLoader: instead of querying immediately, each resolver registers the member id it needs; DataLoader collects all 50 ids for the current tick and fires a single batched query (SELECT member_id, count(*) … WHERE member_id IN (…) GROUP BY member_id), then hands each resolver its slice. 51 queries collapse to 2, and the front-end's query never changes — the fix is entirely server-side. The general principle: a per-item fetch inside a loop is a batching opportunity in disguise — the same instinct you'll apply to cache reads (Day 6) and any IN-vs-loop decision.

Real-World Engineering

📘 Meta / Facebook

GraphQL was born at Facebook (2012, open-sourced 2015) to solve exactly Mei's problem: news-feed screens needed deeply-nested, per-device slices of data, and dozens of REST round trips were killing mobile performance. DataLoader and Relay came from the same team.

🐙 GitHub

Runs a public GraphQL API (v4) alongside its REST API (v3) — a textbook case of choosing per-use-case. GitHub also pioneered rate-limiting by query cost (a point budget), since counting raw requests is meaningless when one query can be huge.

🛍️ Shopify

Exposes its storefront and admin data through GraphQL so thousands of third-party apps and themes can fetch precisely the fields they need across products, orders, and customers — without Shopify shipping a new REST endpoint for every use case.

🎬 Netflix

Uses a federated GraphQL layer (a single graph stitched from many backend teams' subgraphs) so a client makes one query while dozens of independent microservices each resolve their piece — the "concierge in front of many rooms" pattern we'll formalize at the API Gateway (Day 27).

Flashcards (Spaced Repetition)

Q: In one sentence, what is GraphQL?
A: A typed query language and runtime for APIs where a single endpoint exposes a schema, and the client sends a query describing the exact shape of data it wants — getting back JSON in precisely that shape, eliminating over- and under-fetching.
Q: What problems with REST does GraphQL solve?
A: Over-fetching (REST returns whole fixed objects; you download fields you don't need) and under-fetching (one screen needs many resources, forcing a waterfall of round trips). GraphQL lets the client request exactly the needed fields across resources in one request.
Q: What is the N+1 problem, and how is it fixed?
A: A naïve resolver fetches a list (1 query) then fires 1 query per item for a nested field (N queries) — 101 queries for 100 items. Fix it with a DataLoader: batch the per-item keys into one IN query per request and cache/de-dupe within that request.
Q: Why is caching harder in GraphQL than REST?
A: REST caches GETs by URL using HTTP. GraphQL POSTs every query to one URL, so HTTP caches can't distinguish them. You cache at the application layer instead — normalized client caches keyed by object id, and persisted queries a CDN can cache by hash.
Q: What are the three GraphQL operation types?
A: query (read, like GET), mutation (write — create/update/delete, run sequentially), and subscription (a long-lived stream where the server pushes updates, usually over WebSockets).

If you only remember one thing: GraphQL hands the pen to the client. Instead of many URLs each returning a fixed shape, there's one endpoint and a typed schema, and the client sends a query shaped like the JSON it wants — killing over-fetching and the round-trip waterfall. The price is that you now own caching, cost control, and the N+1 trap (fixed by batching with DataLoader). It's not "better than REST" — it's a different set of trade-offs that wins when clients are diverse and data is deeply connected.
