Rate Limiting & Throttling
The Bouncer at the Door

Yesterday the circuit breaker protected you from a dependency that fails. Today we flip the camera around and protect a service from the callers who hammer it. A single buggy client stuck in a retry loop, a scraper, or a sudden traffic spike can fling thousands of requests a second at servers sized for a fraction of that — and when they do, CPU pegs, connection pools drain, and every user (even the paying, well-behaved ones) starts getting errors. One flood drowns everyone. A rate limiter is the bouncer at the door: it lets requests through only as fast as the service can safely handle, and turns the excess away with a fast, honest 429 Too Many Requests. Today you'll learn the token bucket and its cousins, what to count against (user, API key, IP), how to say "no" gracefully, and the genuinely hard part — enforcing one limit across a whole fleet of servers.

Picture this

Picture a popular nightclub with a fire-code limit of 300 people. Out front stands a bouncer with a little clicker-counter. The club can only safely hold so many, and the bar can only pour drinks so fast — so the bouncer's whole job is to let people in only as fast as the room can absorb them. When a crowd surges the door all at once, he doesn't let the stampede crush the room and ruin the night for everyone already inside. He holds up a hand: "We're at capacity — come back in a few minutes." That's a fast, clear "no," not a three-hour wait in a doorway. Now add one detail that makes the bouncer smart: he keeps a small bucket of entry tokens behind him that refills at a steady rate — say two tokens a second. Each person entering takes a token. If a quiet stretch let the bucket fill up, a small burst of friends can all walk in at once (there are spare tokens). But if the bucket is empty, you wait for it to refill. That bucket is the token-bucket algorithm, and that bouncer is a rate limiter: he protects the party from a stampede before it can start. Burn in the image: a rate limiter is a bouncer with a clicker and a refilling bucket of tokens — it admits traffic only as fast as the service can handle, absorbs a small burst, and turns the rest away fast instead of letting a flood crush everyone inside.

The Story

Flooded Farah ran the public API for a weather app. Traffic was steady and her handful of servers coped easily — until the morning a popular partner shipped a buggy mobile update. A bug in their networking code put the app into a tight retry loop: every phone that opened the app fired the same request over and over, dozens of times a second. Multiply that by a few hundred thousand phones and Farah's API — sized for maybe 150 requests a second — was suddenly taking thousands.

Her servers didn't gracefully shrug it off; they drowned. CPU pinned at 100%, the database connection pool emptied, request queues backed up, and response times climbed from 40 ms to full timeouts. And here's the part that stung: it wasn't just the buggy client that suffered. Every user of the API — the well-behaved apps, the paying enterprise customers, everyone — got the same slow errors, because they were all sharing the same overwhelmed servers. One misbehaving caller had degraded the service for the entire world. This is the noisy-neighbor problem, and it's why "just add more servers" is a losing race: a runaway client can always generate load faster than you can provision hardware.

The fix wasn't more servers — it was a doorman. Farah put a rate limiter in front of the API. Each API key got a token bucket: 100 requests per minute sustained, with room for a burst of 20. Requests within the limit passed straight through; requests beyond it got an immediate 429 Too Many Requests with a Retry-After header telling the client exactly how long to wait. The buggy partner's key hit its ceiling in seconds and got politely bounced — while every other customer sailed through untouched. One bad neighbor could no longer take down the block.

Then Farah met the nuances that separate a toy limiter from a real one. First, she'd deployed the limiter on each of her 10 servers independently, each with its own in-memory counter — so a client hitting a load balancer that spread it across all 10 actually got 10× the intended limit. The counter had to be shared, so she moved it into Redis. Second, she'd first keyed the limit on IP address, which quietly punished thousands of legitimate users sitting behind one corporate NAT (they looked like a single hammering client); keying on the API key / user fixed the fairness. Third, a legitimate dashboard that loaded 15 widgets at once kept tripping a naive per-second limit — and that's exactly what the token bucket's burst allowance is for. By the end, Farah had learned the core truth: a service must decide how much load it will accept — because if it doesn't, its callers will decide for it, and they will choose "too much."

What should stay in your head
A rate limiter caps how many requests a given client may make in a given amount of time, and rejects (or delays) the rest. It exists to protect a service from being overwhelmed — whether by abuse (DoS, credential-stuffing, scraping), an accident (a client stuck in a retry loop), a spike (a thundering herd), or simple unfairness (one noisy neighbor starving everyone else). The mechanism is always the same shape: pick a key (who are we counting — this user? this API key? this IP?), pick a limit (how many per window — 100/min), track usage against that key, and when the limit is exceeded, return a fast 429 Too Many Requests instead of doing the work. The most popular algorithm is the token bucket: a bucket holds up to C tokens (the burst allowance) and refills at r tokens/second (the sustained rate); each request spends one token, and a request that finds the bucket empty is rejected. Two ideas anchor everything: throttling shifts the cost of overload from the server onto the client — a fast, cheap "429, try later" is far better than a slow, expensive collapse that takes everyone down — and it is the exact mirror of yesterday's circuit breaker: the breaker protects you from a dependency you call; the rate limiter protects a service from the callers hammering it.

The Algorithms — Counting Requests Five Ways

Every rate limiter answers one question: "has this key used up its allowance?" The algorithms differ only in how they count. There are five you should know cold — interviewers love asking you to compare them, especially the token bucket and the two window approaches. Start with the star of the show.

🪣 Token Bucket

A bucket holds up to C tokens and refills at r tokens/sec. Each request spends one token; no token → reject. Allows a burst up to C, then settles to the steady rate r.

The default. Flexible, cheap, burst-friendly. Used by Stripe, AWS, most APIs.

🌊 Leaky Bucket

Requests pour into a queue that drains at a fixed rate. Output is perfectly smooth; overflow is dropped. Like a funnel — it shapes bursty input into a steady trickle downstream.

Great when the thing you protect needs a constant, even flow (no bursts).

🪟 Fixed Window

Count requests per fixed clock window ("100 per minute, reset on the minute"). Dead simple and cheap, but has a nasty edge burst: 100 at 12:00:59 + 100 at 12:01:00 = 200 in two seconds.

Fine for coarse limits; the boundary spike is its famous flaw.

📜 Sliding Window Log

Keep a timestamp of every request and count how many fall in the last 60 seconds. Perfectly accurate — no boundary bug — but stores one entry per request, so it's memory-hungry.

Exact, but expensive at scale. Rarely used raw.

⚖️ Sliding Window Counter

The practical compromise: blend the current and previous fixed-window counts, weighted by how far into the window you are. Smooths the fixed-window edge burst using two numbers, not a full log.

Accurate enough, cheap enough — a very common production choice.

The two you'll reach for most are the token bucket (when you want to allow bursts) and the sliding window counter (when you want a clean per-window cap without the fixed-window boundary spike). Here's the whole token bucket in about a dozen lines:

A token bucket, sketched
class TokenBucket { capacity = 20; // max tokens = burst size refillRate = 2; // tokens added per second = sustained rate tokens = 20; // start full last = now(); allow() { // true = let it through, false = 429 const elapsed = (now() - this.last) / 1000; this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.refillRate); // refill this.last = now(); if (this.tokens >= 1) { this.tokens -= 1; return true; } // spend a token return false; // bucket empty → reject (429) } }

Notice there's no background timer refilling the bucket — refill is computed lazily from elapsed time on each call. That's the trick that makes it cheap enough to run per-key for millions of keys. In production this exact logic runs atomically inside Redis (often a Lua script) so all your servers share one bucket per key — more on that in The Hard Parts.

Why You Rate Limit — and What You Count Against

Rate limiting shows up for several distinct reasons, and knowing which one you're solving tells you how to configure it.

Stop abuse & attacks.Brute-force login and credential-stuffing, scrapers, and application-layer DoS all look like "one client sending far too many requests." A limit on /login per IP+account turns a million password guesses into a handful.
Contain accidents.The most common cause isn't malice — it's a bug: a client stuck in a retry loop, a runaway cron job, an infinite scroll gone wrong. A limiter is the backstop that keeps someone else's bug from becoming your outage.
Ensure fairness (the noisy neighbor).On a shared service, one heavy user shouldn't be able to starve everyone else of capacity. Per-tenant limits guarantee each customer a fair slice of a finite resource.
Control cost & protect capacity.Every request costs CPU, DB queries, and sometimes real money (a downstream paid API, an LLM token bill). A limit is a spending cap and a capacity guard rolled into one.
Monetize tiers.Free = 60 req/min, Pro = 1,000, Enterprise = custom. The rate limit is the product boundary — the same mechanism that protects the service also enforces the pricing plan.

The key: who are you counting?

A rate limiter always counts against a key, and choosing it well is half the battle — Farah learned this the hard way. The wrong key is either unfair or trivially bypassed:

Key on…Good forWatch out
API key / user IDThe gold standard for authenticated APIs — fair, precise, and tied to a real account and its tier.Requires the caller to be identified; useless for anonymous traffic.
IP addressAnonymous endpoints (signup, login, public reads) where you have no user yet.Thousands of real users behind one corporate NAT or mobile carrier look like one abuser; attackers rotate IPs cheaply.
Endpoint / routeProtecting one expensive operation (search, export, an LLM call) with a tighter limit than cheap reads.Usually combined with a user/IP key, not used alone.
GlobalA hard ceiling on total load to protect the origin no matter who's calling.Doesn't distinguish good from bad callers — a blunt last-resort backstop.

Real systems layer these: a global cap to protect the fleet, a per-user cap for fairness, and a tighter per-endpoint cap on the few genuinely expensive routes — all at once.

Saying "No" Gracefully — Rejecting vs Throttling

When a client is over the limit, you have a choice about how to refuse, and a responsibility to refuse clearly. A silent drop or a vague 500 turns a well-behaved client into a confused, retrying one.

🚫 Reject (hard limit)

Immediately return 429 Too Many Requests. The request is not done — the client must back off and retry later. The standard, honest answer for an API.

The token bucket's default behavior.

🐌 Throttle (delay / queue)

Instead of rejecting, slow the client down — hold the request briefly, or queue it and drain at a fixed rate (leaky bucket). Smooths bursts without dropping work.

Good for internal producers; risky if queues grow unbounded.

📉 Shape / degrade

Serve a cheaper response over the limit — cached data, lower resolution, fewer results — instead of a full rejection. Overload-aware graceful degradation (Day 22).

e.g. serve stale search results under heavy load.

🎯 Prioritize (fair queueing)

When you must shed load, shed the right load: drop low-priority or free-tier traffic first, protect paying and critical requests. Not all requests are equal.

Load shedding with a priority order.

Speak the protocol: 429 and the headers

A good rate limiter is a conversation, not a wall. The HTTP contract makes throttling predictable so a well-written client can behave:

SignalMeaning
429 Too Many RequestsThe status code that says "you're over the limit." (Distinct from 503, which means the server itself is unavailable.)
Retry-After: 30Tells the client exactly how long to wait before trying again — the single most important header. Without it, clients guess (badly) and often retry-storm you.
X-RateLimit-Limit / -Remaining / -ResetYour ceiling, how many calls you have left in this window, and when it resets. Lets a good client self-throttle before hitting the wall.

The pairing of 429 + Retry-After is where rate limiting and yesterday's lesson meet: it turns a rejected caller into a calm caller. Without it, every throttled client immediately retries, and your defensive limit becomes the trigger for the very retry storm the circuit breaker exists to stop.

The Traffic-Management Toolkit — Where Limiting Fits

Rate limiting is one lever among several that a service uses to control how much work it accepts. They stack, and a mature system uses them at different layers — the CDN/edge, the API gateway, and the service itself.

🚪 Rate Limiting

Today. Cap requests per key over time; reject the excess with 429. Enforces fairness, stops abuse, and guards capacity per caller.

The bouncer with the clicker.

🪫 Load Shedding

When the server itself is overloaded (regardless of who's calling), proactively drop low-priority work early so the core survives. Rate limiting is per-key; shedding is whole-server self-defense.

Better to serve 80% than crash serving 0%.

🔙 Backpressure

Push the "slow down" signal upstream to producers (a full queue, a blocked write, a 429) so they stop generating work faster than you can handle it. Rate limiting is one way to apply it (Day 18 queues).

Tell the source to ease off.

⚡ Circuit Breaker

Yesterday. The mirror image — it stops you from calling a broken dependency; a rate limiter stops callers from overwhelming you. Together they protect both ends of every call.

Protect the caller and the callee.

🌐 Edge / WAF Limiting

Push limiting to the CDN or firewall (Cloudflare, AWS WAF) so a volumetric flood is absorbed before it ever reaches your origin. The cheapest place to say no is the earliest one.

DDoS defense at the front line.

🧾 Quotas

Rate limiting's slow cousin: a cap over a long window (10,000 calls/day, 1M tokens/month). Same idea, billing-cycle timescale — usage control rather than burst control.

The monthly plan, not the per-second gate.

The pattern is defense in depth: the edge absorbs volumetric floods, the API gateway enforces per-user rate limits and tiers, the service applies load shedding when it's genuinely overloaded, and circuit breakers protect each downstream call. No single layer is enough; together they keep a service standing under traffic it was never provisioned for.

The Hard Parts — What Rate Limiting Costs You

Rate limiting looks trivial in a single-server toy and gets genuinely hard the moment you have a fleet. Here's the honest ledger.

1. Distributed counting is the real problem

A limit of "100/min per user" is only meaningful if it's enforced across all your servers. If each of 10 servers keeps its own in-memory counter, the effective limit is 10× too high (Farah's bug). The fix is a shared, atomic counter — typically Redis (an INCR with a TTL, or a token bucket in a Lua script so the read-modify-write is atomic). But now every request makes a network call to Redis: that adds latency and makes Redis a critical dependency in your hot path. The classic compromise is local + global: approximate limiting in-memory on each node (fast) synced to a shared store (accurate), trading a little precision for a lot of speed.

2. Precision vs. cost is a real dial

A perfectly accurate sliding-window log stores every request timestamp — beautiful and unaffordable at millions of keys. A fixed window is cheap but lets a 2× boundary burst through. Every algorithm is a point on the accuracy-vs-memory-vs-latency triangle, and the "right" one depends on whether a brief overshoot actually hurts you. For protecting a server, approximate is usually fine; for enforcing a strict paid quota, you may need exact.

3. What to key on is a security and fairness decision

Key on IP and you punish everyone behind a shared NAT while attackers rotate IPs for pennies. Key on user and you can't limit anonymous traffic (like the login endpoint that most needs it). Key on something spoofable and it's bypassed. There's no free key; you almost always need several layers, and getting them wrong is either a security hole or a support nightmare of falsely-blocked legitimate users.

4. A limiter can cause the outage it was meant to prevent

Set the limit too low and you throttle legitimate traffic — self-inflicted downtime. Reject without a Retry-After and clients hammer you with immediate retries, turning your 429s into a retry storm. And a naive per-second limit with no burst allowance breaks perfectly reasonable bursty clients (a page loading 15 widgets). A rate limiter is a safety device that, mis-set, becomes the hazard — which is exactly why you must monitor your 429 rate and alert on it (Day 26).

The through-line: rate limiting trades a bit of added latency, a shared-state dependency, and real tuning effort for something essential — the guarantee that no single caller, malicious or merely buggy, can consume the capacity that everyone else depends on. Placed at the edges where untrusted traffic enters, it's one of the highest-leverage protections you can add. Set carelessly — too low, no burst, no Retry-After, per-server counters — it degrades the very users it was meant to serve.

Common Mistakes & Misconceptions

The misconceptionThe reality
"I'll just add more servers instead of rate limiting."A runaway client or attacker can generate load faster and cheaper than you can provision hardware — you'll lose that race and burn money doing it. A limiter caps abuse for near-zero cost; capacity is for real, legitimate growth.
"I put the limiter on each server, so I'm covered."Per-server in-memory counters mean the effective limit is multiplied by your server count (10 servers → 10× the limit), and it resets on every deploy. A fleet-wide limit needs a shared, atomic counter (usually Redis).
"Rate limit by IP — one client, one IP."Thousands of real users share one IP behind corporate NATs and mobile carriers (you'd throttle them all as one "abuser"), while attackers rotate through cheap IPs to dodge it. Prefer keying on API key / user for authenticated traffic.
"A fixed window of 100/min is a clean 100 per minute."Fixed windows allow a boundary burst: 100 requests at 12:00:59 plus 100 at 12:01:00 is 200 in two seconds. Use a sliding-window counter or token bucket if that spike matters.
"Just drop over-limit requests to keep it simple."A silent drop or vague error makes good clients retry blindly and storm you. Return a clear 429 with Retry-After (and remaining/limit headers) so well-behaved clients back off correctly — the difference between defense and self-inflicted retry storm.
"A per-second limit with no burst is the safest setting."Legitimate clients are naturally bursty (a page loading many resources at once). A hard per-second cap with no burst allowance breaks them; the token bucket's capacity exists precisely to permit short, reasonable bursts while still capping the sustained rate.

Active Recall

❓ Your public API is sized for ~150 req/s. One partner ships a buggy client stuck in a retry loop and starts sending thousands of req/s; your servers peg and every customer — including the well-behaved ones — starts getting timeouts. Explain (1) why "add more servers" won't reliably fix this, (2) how a token-bucket rate limiter keyed on API key fixes it, including what the two parameters (capacity and refill rate) do, and (3) two mistakes that would make your rate limiter ineffective or actively harmful. (click to reveal)
(1) Why more servers won't fix it: a runaway or malicious client can generate load faster and far more cheaply than you can provision hardware — it's an unwinnable, expensive race. And the root problem is a noisy neighbor: one caller consuming the shared capacity that everyone else needs. Scaling up just gives the bad client a bigger service to overwhelm; it doesn't restore fairness. (2) The token bucket fixes it: put a rate limiter in front, keyed on API key (so each caller is counted independently and fairly, and tied to their tier). Give each key a token bucket: the capacity C is the burst allowance (how many requests can go through in an instant if tokens have accumulated), and the refill rate r is the sustained requests/second allowed. Each request spends a token; when the bucket is empty, the request gets an instant 429 Too Many Requests with a Retry-After. The buggy partner's key drains its bucket in seconds and gets bounced, while every other customer — with their own full bucket — sails through untouched. The origin now only ever sees traffic up to the limit, safely under its 150/s capacity. (3) Two ways to get it wrong: (a) per-server counters — if the limiter runs in-memory on each of N servers, the real limit is N× too high; the counter must be shared and atomic (Redis). (b) Setting the limit above real capacity, or rejecting without Retry-After — a limit higher than the ~150/s the server can handle protects no one, and a bare rejection makes throttled clients retry instantly, turning your defensive 429s into the retry storm you were trying to prevent. (Keying on IP instead of API key would also unfairly punish users behind shared NATs.) Mantra: decide your capacity, or your callers will decide it for you.

Real-World Engineering

💳 Stripe

Stripe rate-limits its API with a token bucket and publishes the approach openly. They run multiple limiters at once — a request-rate limiter, a concurrency limiter, and per-endpoint "fleet usage" load shedders — and return 429 with clear guidance to back off exponentially. It's a textbook example of layering several limits to keep a critical payments API responsive under abuse.

🐙 GitHub API

GitHub's REST API gives authenticated callers 5,000 requests/hour and returns the state in every response via X-RateLimit-Limit, -Remaining, and -Reset headers, plus Retry-After on a 429. Good clients read those headers and self-throttle before ever hitting the wall — the cooperative model rate limiting is designed for.

☁️ Cloudflare & AWS (edge)

The cheapest place to reject a flood is the earliest. Cloudflare and AWS WAF apply rate limiting and DDoS protection at the edge, absorbing volumetric attacks before they reach your origin — often using approximate, super-fast counters distributed across hundreds of points of presence, accepting a little imprecision for enormous scale.

🔧 Nginx & Redis

You don't need a fancy service: Nginx's limit_req module implements a leaky bucket in a few config lines, and countless teams build custom limiters on Redis with an atomic INCR+TTL or a token-bucket Lua script so the whole fleet shares one counter per key. The algorithms in this lesson are the exact ones these tools implement.

Flashcards (Spaced Repetition)

Q: What problem does rate limiting solve, and how does it relate to the circuit breaker?
A: It protects a service from being overwhelmed by its callers — abuse, a client stuck in a retry loop, a spike, or one noisy neighbor starving everyone — by capping requests per key over time and rejecting the excess with a fast 429. It's the mirror of the circuit breaker: the breaker protects you from a dependency you call; the rate limiter protects a service from the callers hammering it.
Q: How does the token bucket algorithm work, and what do its two parameters mean?
A: A bucket holds up to C tokens (capacity = the burst allowance) and refills at r tokens/sec (the sustained rate). Each request spends one token; a request that finds the bucket empty is rejected. So a client can burst up to C requests instantly if tokens have accumulated, then is limited to the steady rate r.
Q: Why is enforcing a limit across many servers hard, and how is it solved?
A: If each server keeps its own in-memory counter, the effective limit is multiplied by the server count (10 servers → 10× the intended limit). The fix is a shared, atomic counter — usually Redis (an INCR+TTL, or a token bucket in a Lua script so the read-modify-write is atomic) — at the cost of added latency and a new critical dependency. A common compromise is local (approximate) + global (accurate).
Q: Why prefer keying a limit on API key/user over IP address?
A: An IP can hide thousands of real users behind a corporate NAT or mobile carrier (you'd throttle them all as one abuser), and attackers can rotate cheap IPs to dodge the limit. An API key/user ID is a precise, fair identity tied to a real account and its tier. IP is still useful for anonymous endpoints (signup/login) where no user exists yet — often layered together.
Q: When a client is over the limit, what should you return, and why does Retry-After matter?
A: A 429 Too Many Requests with a Retry-After header (plus X-RateLimit-Remaining/Reset when possible). Retry-After tells the client exactly how long to wait — without it, throttled clients retry immediately and en masse, turning your defensive limit into a self-inflicted retry storm. A good limiter is a conversation, not a silent wall.

If you only remember one thing: a service must decide how much load it will accept — because if it doesn't, its callers will, and they'll choose "too much." A rate limiter is a bouncer at the door that counts requests per key (user, API key, IP), lets them through only as fast as the service can safely handle, and turns the excess away with a fast, honest 429 Too Many Requests + Retry-After instead of letting one flood drown everyone. The workhorse algorithm is the token bucket — a bucket of capacity C (burst) that refills at rate r (sustained), spending one token per request — with the sliding window counter as the other common pick. It's the mirror of the circuit breaker: one protects you from a dependency, the other protects you from your callers. The easy version is a counter on one box; the real version needs a shared, atomic counter (Redis) so a whole fleet enforces one limit, the right key for fairness, a burst allowance so legitimate spikes don't break, and monitoring so a too-tight limit doesn't quietly throttle the users you meant to protect.
