gRPC & Protocol Buffers
The Fast Binary Intercom Between Services

REST and GraphQL are the front door — human-readable text over HTTP, built to serve browsers. But behind the walls, your own services call each other millions of times a second, and there JSON's verbosity and parse cost become a tax you pay on every hop. gRPC is the back corridor: you write one typed .proto contract, a compiler generates matching client and server code in any language, and calls travel as compact binary Protocol Buffers over HTTP/2 — small, fast, strongly typed, and able to stream in both directions. It's the intercom the rooms use to talk to each other.

Visual Memory Anchor

📞⚡

Picture this

The hotel's guests all talk to the front desk in full spoken sentences — polite, readable, easy for anyone to follow (that's REST/GraphQL over text). But the staff don't have time for that. Between the kitchen, housekeeping, and the front office there's a private intercom, and both ends share a printed codebook: "beep-two" means table ready, "beep-five" means room needs cleaning. Nobody says whole words — they fire tiny codes back and forth, and because both sides own the exact same codebook, each side knows precisely what every beep means. It's unreadable if you don't have the book — but it's tiny and instant, and the line stays open so both ends can talk at once without redialing. That codebook is a .proto file. The beeps are Protocol Buffers — compact binary, not text. The always-open line is HTTP/2. Picture staff firing coded beeps down a private wire while guests chat in full sentences at the desk — that split is gRPC.

The Story

Backend Ben ran a checkout service that, to complete one order, called four other internal services: inventory, pricing, fraud, and shipping. Every call was REST + JSON, because that's what the team knew. It worked — until traffic grew. Profiling showed something absurd: a big slice of each service's CPU was spent serializing and parsing JSON. Every hop wrote out field names as text — "customerId", "customerId", "customerId", once per record — turned numbers into strings, then the receiver parsed it all back. The payloads were three times bigger than the data they carried, and the machines were burning cycles on nothing but envelope-stuffing.

Worse was the silent breakage. A teammate renamed total to totalAmount in the pricing service. Nothing failed to compile — JSON has no shared schema — so the shipping service just started reading undefined in production at 2 a.m. There was no contract both sides were forced to agree on; the "contract" lived in a wiki page and in everyone's memory, and memory lost.

A staff engineer moved the internal calls to gRPC. First they wrote the contract as a .proto file — every message, every field, every field's number and type. A compiler turned that one file into typed client and server code for Ben's Go service and the pricing team's Java service. Now calling pricing looked like calling a local function: pricing.Quote(cart) — the networking, the encoding, all generated. On the wire, the field names vanished (replaced by one-byte field numbers), numbers became compact binary, and the whole thing flew over a single reused HTTP/2 connection. Payloads shrank by more than half, parse cost collapsed, and when someone tried to change a field's type the build broke immediately, not at 2 a.m. Ben hadn't bought faster machines — he'd stopped speaking in full sentences where a shared codebook would do.

What should stay in your head
gRPC is a contract-first RPC framework: you define your services and messages once in a typed .proto schema, and a compiler (protoc) generates client and server code in whatever languages you use. A remote call then looks like a local function call. On the wire, messages are serialized as Protocol Buffers — a compact binary format where field names are replaced by small field numbers — and shipped over HTTP/2, which multiplexes many calls on one connection and supports streaming in both directions. The result is small, fast, strongly typed service-to-service communication. The price: it's binary (not human-readable, and browsers can't speak it natively), so gRPC is the back-office protocol — REST/GraphQL still answer the front door.

Why gRPC Exists — the JSON Tax on Internal Calls

REST + JSON is a wonderful public contract: readable, debuggable in a browser, universally supported. But inside a system of microservices (Day 26), those same properties become a cost you pay on every single hop:

Text is heavy, and heavy is expensive at scale

JSON writes every field name as a string in every message. Send a million orders and you've sent the word "totalCents" a million times. Numbers become text (140.00 is six characters, not one binary value). Then both sides burn CPU converting objects to text and back — and in a chain where service A calls B calls C, that serialization tax compounds at every link. When two computers you own talk, spelling everything out in English is pure overhead.

No enforced contract means silent drift

JSON has no shared, machine-checked schema by default. One team renames a field or changes a type, and the other side doesn't fail to compile — it fails in production, quietly, reading null. As the number of services grows, "we all agreed on the shape" stops being true.

Request/response only, over fresh connections

Classic REST over HTTP/1.1 is one request, one response, and (historically) a connection per call. There's no clean, built-in way for the server to stream a sequence of results, or for both sides to talk at once.

gRPC — born at Google in 2015 from their internal "Stubby" RPC system — targets exactly these three pains: a binary format to kill the text tax, a compiled schema to make drift a build error, and HTTP/2 streaming to go beyond one-shot request/response. It is not trying to replace the browser-facing API; it's trying to make the wires between your services fast and safe.

Protocol Buffers — the Contract and the Wire

"Protobuf" is really two things at once: a schema language (the contract) and a binary encoding (the wire format). Understand both and gRPC stops being magic.

1. The .proto file is the single source of truth

You describe your data and your service in one file. This is the codebook both sides share:

syntax = "proto3";

message Order {
  int64  id        = 1;
  int64  totalCents = 2;
  string status    = 3;
}
message User {
  int64  id   = 1;
  string name = 2;
  repeated Order orders = 5; # a User has many Orders
}

service Users {
  rpc GetUser(UserRequest) returns (User);
}

From this one file, protoc generates a typed client stub and server interface in Go, Java, Python, C++, Rust, and more. Calling GetUser is a normal function call in each language; the encoding and networking are generated for you. That's contract-first: the schema exists before either side's code, and both sides are compiled against it.

2. Field numbers are the whole trick

See the = 1, = 2, = 5? Those field numbers are what travel on the wire instead of the names. The name totalCents is a compile-time convenience; on the wire it's just field 2. This is why Protobuf is small — and it's also the key to backward compatibility: as long as you never reuse or renumber a field, you can rename fields freely (the number is the identity), add new fields with new numbers (old code ignores numbers it doesn't know), and roll services independently. Break the rule — reuse number 2 for something else — and old and new binaries will silently misread each other. Field numbers are forever.

3. The wire format: tag + value, varints everywhere

Each field on the wire is a one-byte tag — the field number shifted left and OR'd with a 3-bit wire type (0 = varint for ints, 2 = length-delimited for strings and nested messages) — followed by the value. Integers use varints: small numbers take one byte, bigger ones take more, so you only pay for the magnitude you use. Strings are a length byte then the raw UTF-8. There are no field names, no quotes, no braces, no commas — that's the entire savings you watched in the explorer above. The cost: the bytes are meaningless without the .proto. You can't curl a gRPC endpoint and read it; you need the schema (or a tool like grpcurl) to decode it.

The Four Call Types — and Why HTTP/2 Matters

Because gRPC runs on HTTP/2 — which sends data in binary frames, multiplexes many calls over one connection, and keeps that connection open — it isn't limited to one-request-one-response. It offers four call shapes:

UnaryOne request → one response. The ordinary function call: GetUser(id) returns a User. This is 90% of real usage.
Server streamingOne request → a stream of responses. Ask once, get many back over time — "give me every price update for this symbol" or paging a huge result set without buffering it all.
Client streamingA stream of requests → one response. Upload many chunks, get one summary — telemetry, a batch of events, a file in pieces.
Bidirectional streamingBoth sides stream at once over the same open connection — chat, live collaboration, a control channel. Neither side has to wait for the other to finish.

HTTP/2 is the enabler for all of this. On HTTP/1.1, a slow request could block others behind it (head-of-line blocking) and each call tended to need its own connection. HTTP/2 slices the connection into independent streams so hundreds of calls interleave on one socket, and those long-lived streams are exactly what server-push and bidirectional streaming ride on. gRPC didn't invent streaming RPC — it stood it on top of a transport that finally made it cheap.

What gRPC Costs You (Nothing Is Free)

gRPC buys speed and safety by giving up readability and reach. A staff engineer weighs these before reaching for it — especially the first one, which rules gRPC out of a huge category of use.

Browsers can't speak it natively

gRPC needs fine-grained control over HTTP/2 frames and trailers that browser JavaScript simply cannot access. So a web page cannot call a gRPC service directly. The workaround, gRPC-Web, requires a proxy (Envoy or similar) to translate between the browser and the real gRPC backend, and even then streaming is limited. This is the reason gRPC is a back-office protocol: your public, browser-facing API is still REST or GraphQL — gRPC lives behind it, service-to-service.

The wire is opaque — debugging is harder

You can't curl an endpoint and eyeball the JSON, or paste a payload into a chat to a teammate. The bytes mean nothing without the .proto. You need gRPC-aware tooling (grpcurl, reflection, Postman's gRPC mode) to inspect calls, and browser dev-tools won't show you readable bodies. The very compactness that makes it fast makes it invisible.

Load balancing and infrastructure are trickier

gRPC's long-lived HTTP/2 connections defeat naïve connection-level (L4) load balancers: one client pins a single backend for the life of the connection, so new backends get no traffic and load skews. You need an L7 (request-aware) load balancer or client-side load balancing that spreads individual streams across backends. Plenty of older middleboxes, gateways, and logging tools also assume text HTTP and don't understand gRPC out of the box.

More upfront machinery, tighter coupling

You need the .proto files, a code-generation build step, and generated stubs checked in or built in CI. Both sides are coupled to the shared schema — a strength for safety, but real ceremony for a tiny service. For a simple public CRUD API, REST is less to build and far easier for outside developers to consume.

REST vs GraphQL vs gRPC — the Whole Trio

✓ Reach for gRPC when…

• Internal service-to-service calls (microservices) • High throughput / low latency matters • You want a strict, compiled, versioned contract • Polyglot services (Go ↔ Java ↔ Python) sharing one schema • You need real streaming (server/client/bidi)

✗ Avoid gRPC when…

• A browser is the client (use REST/GraphQL, or gRPC-Web + proxy) • A public API third parties must easily consume • You value curl-able, human-readable payloads • A tiny service where the tooling isn't worth it • Your infra can't do L7 / HTTP/2 load balancing yet

The honest picture: these aren't ranked good-to-bad — they answer different questions. Large systems commonly run all three: gRPC for the fast internal mesh, REST for simple public endpoints, and GraphQL as a flexible aggregation layer for rich clients. The rule of thumb — text at the edges, binary in the core: browsers and outside developers get readable REST/GraphQL; your services whisper to each other in Protobuf.

gRPC completes the communication-patterns trio that began with REST (Day 15) and GraphQL (Day 16): all three are ways for programs to talk, but gRPC is the synchronous, internal one. It leans hard on HTTP/2 and TCP (Day 3) as its transport. It's the default wiring inside a microservices architecture (Day 26), where service discovery (Day 28) tells one service where to find another before the gRPC call is even made. And it's a natural contrast to tomorrow's message queues (Day 18): gRPC is a live phone call — both parties present at once — while a queue is leaving a note in a mailbox, so the two ends never need to be online together. Same goal (services communicating), opposite posture (synchronous vs asynchronous).

Common Mistakes & Misconceptions

The misconceptionThe reality
"gRPC replaces REST everywhere — it's just faster."gRPC can't be called from a browser without a proxy, and its binary wire is a poor fit for public APIs. It shines internally; REST/GraphQL still answer the front door. Most systems run both.
"Protobuf is faster because it compresses the data."It isn't compression — it's a compact encoding: field names become one-byte numbers and integers become varints. You can still gzip it on top. The win is no key names, no quotes/braces, and cheap binary parsing.
"I can rename or reuse field numbers freely."Names are free to change; numbers are forever. The number is the field's on-the-wire identity. Reusing a retired number makes old and new binaries silently misread each other's data.
"gRPC and Protobuf are the same thing."Protobuf is the schema + serialization format (usable on its own). gRPC is the RPC framework — service definitions, HTTP/2 transport, streaming — that uses Protobuf as its default payload.
"It's HTTP, so my normal load balancer and tools just work."gRPC needs HTTP/2 end-to-end and its long-lived connections defeat L4 load balancers. You need L7/request-aware balancing, and many text-HTTP middleboxes and logging tools don't understand it.
"Streaming means I should stream everything."~90% of real RPCs are plain unary calls. Streaming is powerful for live feeds, big result sets, and bidirectional channels — but it adds flow-control and lifecycle complexity you don't want for a simple request/response.

Active Recall

❓ A teammate proposes: "Our mobile app is slow talking to the backend — let's switch the whole thing, browser included, to gRPC since it's so much faster and smaller." What's wrong with this plan, and what would you actually do? (click to reveal)
The plan hits a wall immediately: browsers cannot call gRPC natively. gRPC needs low-level control of HTTP/2 frames and trailers that browser JavaScript can't reach, so a web (or the JS layer of a mobile) client can't just speak gRPC to the backend. The only path is gRPC-Web, which requires a translating proxy (e.g. Envoy) in front of the gRPC service and still restricts streaming — real machinery for a client-facing edge. The smarter move is the text-at-the-edges, binary-in-the-core pattern: keep the client ↔ backend edge on REST or GraphQL (readable, cacheable, browser-native), and adopt gRPC for the calls between your internal services, where both ends are servers you control, throughput is high, and a compiled .proto contract prevents silent drift. gRPC's speed is real — but it's earned in the back office, not at the front door.

Real-World Engineering

🔎 Google

gRPC is the open-source descendant of Google's internal Stubby, which has carried the vast majority of RPCs between Google's services for years. Protobuf is the default data language across nearly all of Google's internal systems — the "text tax" problem solved at planetary scale.

☸️ Kubernetes / etcd

Kubernetes' control plane and etcd (its distributed config store) communicate over gRPC, and Kubernetes API objects are defined with Protobuf for fast internal encoding. The plumbing of modern cloud infrastructure runs on it.

🚗 Uber / Netflix

Both moved swathes of their microservice meshes from JSON/HTTP to gRPC to cut latency and serialization cost at massive request volumes, and to get a compiled contract across thousands of services in many languages.

📦 Dropbox / Cloudflare

Dropbox rebuilt performance-critical internal services on gRPC for the throughput win. Cloudflare and many infra vendors expose gRPC APIs for control planes — anywhere machines talk to machines and every millisecond and byte counts.

Flashcards (Spaced Repetition)

Q: In one sentence, what is gRPC?
A: A contract-first RPC framework where you define services and messages in a typed .proto schema, generate client/server code in any language, and send compact binary Protocol Buffers over HTTP/2 — making remote calls look local, small, fast, and strongly typed for service-to-service communication.
Q: Why is Protobuf so much smaller than JSON?
A: It replaces every field name with a one-byte field number (a tag), encodes integers as varints (small numbers = 1 byte), and drops all quotes, braces, and commas. It isn't compression — it's a compact binary encoding — and it costs you readability: the bytes are meaningless without the .proto.
Q: Why do field numbers matter for compatibility?
A: The number, not the name, is the field's identity on the wire. So you can rename fields freely and add new fields with new numbers (old code ignores unknown numbers) — enabling independent service rollouts — but you must never reuse or renumber a field, or old and new binaries will silently misread each other.
Q: Name gRPC's four call types.
A: Unary (1 request → 1 response), server streaming (1 → many), client streaming (many → 1), and bidirectional streaming (both stream at once). All four ride on HTTP/2's multiplexed, long-lived streams.
Q: Why can't a browser call a gRPC service directly?
A: gRPC needs low-level control of HTTP/2 frames and trailers that browser JavaScript can't access. The workaround is gRPC-Web + a translating proxy (e.g. Envoy). This is why gRPC is a back-office, service-to-service protocol while REST/GraphQL face the browser.

If you only remember one thing: gRPC is the fast binary intercom between your services. You write one typed .proto contract, generate matching client and server code in any language, and calls fly as compact Protocol Buffers over HTTP/2 — field names replaced by one-byte numbers, integers as varints, four streaming modes, remote calls that look local. The bill: it's binary (unreadable without the schema, un-curl-able), browsers can't use it without a proxy, and your load balancers must understand HTTP/2. So the rule is text at the edges, binary in the core — REST/GraphQL face the browser, gRPC wires your services together behind them.
