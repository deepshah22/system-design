gRPC & Protocol Buffers
The Pneumatic Tube Behind the Wall

REST (Day 15) and GraphQL (Day 16) are the front door — human-readable text for browsers and partners. But behind the wall, your own services call each other millions of times a second, and there JSON's readability is dead weight: verbose to send, slow to parse, and nobody's reading it anyway. gRPC is the staff-only pneumatic tube: a typed .proto contract compiled into real function calls, tiny binary messages, and HTTP/2 streaming. Blazing fast, strongly typed — and not meant for human eyes at all.

Visual Memory Anchor

📮💨

Picture this

Out front, guests read menus and fill in order slips — the Reception Desk (REST) and the Concierge Booth (GraphQL). But behind the wall, the kitchen, the pantry, and the cellar pass messages to each other through a pneumatic tube: you drop a small sealed capsule into a slot, a puff of air, and it lands in the exact machine on the other side. The capsule isn't a hand-written note — it's a tightly packed binary cartridge stamped with numbered slots (slot 1 = amount, slot 2 = table), no field names spelled out, no wasted air. Both ends were built from the same blueprint (the .proto file), so each knows that slot 1 is a number and slot 2 is text — they don't need labels. It's silent, tiny, and instant, and the tube can carry a stream of capsules back and forth without re-connecting. That's gRPC: binary Protocol-Buffer capsules, a shared typed blueprint on both ends, flying over an HTTP/2 tube between your own services. Hold that image: numbered capsules in a pneumatic tube, blazing fast, and not meant for a human to read.

The Story

Platform-team Priya ran the checkout service. To place one order it called five other services — inventory, pricing, payments, fraud, and shipping — each over an internal REST/JSON API. It worked, but the numbers were ugly. Every hop serialized a fat JSON object, shipped the field names along with the values ("customerId" repeated a million times an hour), opened a fresh HTTP/1.1 connection, and the receiver re-parsed text into objects. At peak, half the CPU on those boxes was spent turning JSON into structs and back. And when someone renamed a field from qty to quantity in the pricing service, checkout silently started reading 0 — there was no shared, enforced contract, just two teams and a wiki page that had drifted.

A staff engineer replaced the internal calls with gRPC. First she wrote a single .proto file — the contract — declaring the messages and the methods: "a PriceRequest has these numbered fields, and getPrice takes one and returns a PriceResponse." Running protoc against it generated real, typed code in every team's language: checkout got a client stub where calling pricing.getPrice(req) looked exactly like a local function, and the pricing team got a server skeleton with one method to fill in. Nobody hand-wrote HTTP, URLs, or JSON parsing again.

The payoffs stacked up. On the wire, messages were binary Protocol Buffers — field numbers, not names — so a payload that was 1,100 bytes of JSON became ~250 bytes, and parsing got an order of magnitude cheaper. Everything rode one long-lived HTTP/2 connection with many calls multiplexed over it, no per-request handshake. When fraud detection needed to stream hundreds of signals as they arrived, gRPC did that natively over the same channel. And the rename that once caused a silent bug? Now impossible: the .proto is the enforced contract, field 3 is field 3 forever, and you evolve it by adding new numbered fields, never renumbering old ones. Priya hadn't just made calls faster — she'd given her services a typed language to talk to each other in, one that no human was ever meant to read.

What should stay in your head
gRPC is a contract-first RPC framework: you write a typed .proto file, and protoc generates a client stub and server skeleton in any language, so a remote call looks like a plain local function call. On the wire it uses Protocol Buffers — a compact binary format that sends field numbers instead of names — over HTTP/2, which gives multiplexed calls on one connection and four kinds of streaming. The win is speed, small payloads, strong typing, and cross-language codegen; the cost is that it's not human-readable, not natively callable from browsers (you need grpc-web + a proxy), and the .proto is a schema you must share and version. gRPC is built for service-to-service calls behind the wall — not the public front door.

How gRPC Works — Contract, Codegen, HTTP/2

gRPC ("gRPC Remote Procedure Calls") was open-sourced by Google in 2015, based on the internal system ("Stubby") they'd used for over a decade to glue thousands of microservices together. The whole idea of RPC — Remote Procedure Call — is old and beautiful: make calling a function on another machine look and feel like calling one in your own process. gRPC modernizes that with three moving parts.

1. Contract-first: the .proto file

You don't start with URLs — you start with a contract. A .proto file declares your messages (the data shapes, each field with a fixed number) and your service (the methods, each with a request and response type). This one file is the single source of truth both sides agree on, checked into version control and shared between teams.

syntax = "proto3"; message PriceRequest { int64 sku = 1; // each field has a permanent number int32 quantity = 2; string currency = 3; } message PriceResponse { int64 total_cents = 1; bool in_stock = 2; } service Pricing { rpc GetPrice(PriceRequest) returns (PriceResponse); }

2. Codegen: protoc builds stubs and skeletons

You run the compiler, protoc, against the .proto. Out comes real, strongly-typed source code in your language (Go, Java, Python, C++, Rust, TypeScript…). The client gets a stub: an object whose method GetPrice(req) you call like any local function — it secretly serializes the request, ships it, and deserializes the reply. The server gets a skeleton: an interface with one method to implement. Nobody writes HTTP handling, routing, or parsing by hand. This is why gRPC is polyglot: a Go service and a Python service generated from the same contract can call each other with zero manual glue.

3. The wire: Protocol Buffers over HTTP/2

When the stub sends the call, two technologies do the heavy lifting. Protocol Buffers serialize the message into compact binary (next section). HTTP/2 carries it — and HTTP/2 is the reason gRPC can do things REST-over-HTTP/1.1 can't:

Multiplexing.Many calls share one long-lived TCP connection as independent "streams" — no more one-request-per-connection or head-of-line blocking. A service can have thousands of in-flight calls over a single socket.
Binary framing + header compression (HPACK).HTTP/2 is binary under the hood and compresses repeated headers, so even the metadata is cheap — a natural fit for high-volume internal traffic.
Bidirectional streaming.Because a stream is a two-way pipe, gRPC can stream messages from client to server, server to client, or both at once over the same call — impossible with plain request/response REST.

Protocol Buffers & the Wire — Why It's So Small

Protocol Buffers (protobuf) is the serialization format, and understanding its trick is understanding gRPC's speed. Recall the Try It Yourself widget: JSON sends {"quantity": 3} — that's the word "quantity" spelled out in text, every single time, on every message. Protobuf never sends field names. Instead, each field is written as a tiny tag byte that packs the field's number and its type, followed by the value encoded as compactly as possible (small integers use a varint — one byte for values under 128).

Field numbers, not names.The .proto says quantity = 2, so on the wire quantity is just "field 2." Both ends share the contract, so they agree what field 2 means — no need to ship the string "quantity".
Binary, tightly packed.Numbers aren't ASCII digits, booleans are one byte, and there are no braces, quotes, colons, or whitespace. Typical payloads are 3–10× smaller than the equivalent JSON and much faster to parse.
Schema evolution built in.You can add new fields with new numbers forever; old code simply ignores fields (numbers) it doesn't recognize, and new code fills in defaults for fields an old message omits. This is forward- and backward-compatibility by design.

That last point comes with the single most important protobuf rule, and it's a favorite interview trap: never reuse or renumber a field number. If you delete field 3, you reserve the number 3 so nobody accidentally recycles it for a different type later — because somewhere an old client may still send or read "field 3" and expect the old meaning. The field name is just a label for humans and codegen; the number is the real, permanent identity on the wire.

message User { reserved 3, 7; // numbers we deleted — never reuse them string name = 1; string email = 2; string phone = 8; // added later — safe, it's a new number }

Four Kinds of RPC — Not Just Request/Response

Because HTTP/2 streams are two-way pipes, gRPC methods come in four flavors. You pick one per method right in the .proto by adding the keyword stream to the request, the response, or both.

TypeShapeUse it for
Unary1 request → 1 responseThe classic call. GetPrice(req). 90% of methods.
Server streaming1 request → many responsesClient asks once, server sends a stream: a live price feed, search results as they're found, a large file in chunks.
Client streamingmany requests → 1 responseClient sends a stream, server replies once: uploading metrics or a large file in chunks, then getting one summary.
Bidirectionalmany ⇄ manyBoth stream at once over one call: a chat, a live multiplayer sync, a two-way telemetry channel.
service Chat { rpc Send(Message) returns (Ack); // unary rpc Subscribe(Room) returns (stream Message); // server streaming rpc Upload(stream Chunk) returns (Summary); // client streaming rpc Live(stream Message) returns (stream Message); // bidirectional }

This is a genuine capability REST doesn't have natively. It's also why gRPC and WebSockets (Day 20) get compared — both give you streaming — but gRPC brings typed messages, codegen, and a contract on top, whereas WebSockets is a raw two-way byte pipe you design yourself.

The Hard Parts — What You Give Up

gRPC's speed and typing aren't free. Three costs are what separate "we use gRPC" from "we understand when not to."

1. Browsers can't speak it directly

This is the big one. gRPC needs fine control over HTTP/2 frames and trailers that browser fetch() APIs don't expose, so you cannot call a gRPC server straight from a web page. You need grpc-web plus a proxy (commonly Envoy) that translates between the browser and the real gRPC backend. That's why gRPC lives behind the wall, between your own services, and a REST or GraphQL gateway usually sits at the edge for browsers and public partners.

2. Not human-readable — debugging is harder

You can't curl a gRPC endpoint and eyeball the JSON, and you can't read a captured packet without the .proto to decode it. The binary that makes it fast also makes it opaque. You lean on tooling — grpcurl, server reflection, Postman/BloomRPC-style clients, and good tracing — to see what's flowing. The readability REST gave you for free is now a tool you have to reach for.

3. The .proto is a schema you must manage

The contract is a strength and an operational burden. It has to be shared across teams (often via a schema registry or a shared repo), versioned carefully, and evolved by the strict rules — add fields, never renumber, reserve deleted numbers. Get it wrong and you break every service compiled against it. There's also a real learning curve (codegen toolchains, HTTP/2, streaming semantics) and weaker out-of-the-box support in some environments compared to plain HTTP/JSON.

The through-line: gRPC trades human friendliness and universal reach for machine efficiency and strong contracts. That trade is a clear win between your own services and a clear loss at the public edge — which is exactly why most large systems use it internally and something else out front.

REST vs GraphQL vs gRPC — Choosing a Communication Style

REST

Many resource URLs, HTTP verbs, human-readable JSON, free HTTP/CDN caching, works everywhere including browsers. Verbose, and rich screens need multiple round-trips.

Best for: public APIs, CRUD, cache-friendly reads, broad reach. (Day 15)

GraphQL

One endpoint, typed schema, client picks exact fields in one trip. Kills over/under-fetching; caching, cost-control, and resolver efficiency become your job.

Best for: rich/varied clients, many related entities, mobile. (Day 16)

gRPC

Contract-first codegen, binary Protocol Buffers over HTTP/2 — tiny, fast, strongly typed, four kinds of streaming. Not browser-native, not human-readable.

Best for: internal service-to-service, low latency, streaming. (today)

The rule of thumb: gRPC shines behind the wall, between your own services, where raw speed, strong typing, and streaming beat human readability, and where both ends can share a .proto. REST shines at the public edge, where universal reach, browser support, and free caching matter most. GraphQL shines at the edge too, when diverse clients each need a different slice of a richly-connected graph. Very large systems run all three: gRPC internally between microservices, and a REST or GraphQL gateway at the front door. As always, it's rarely "which one" — it's "which one where."

Common Mistakes & Misconceptions

The misconceptionThe reality
"gRPC is just a faster REST."It's a different model: contract-first RPC with codegen (calls look like local functions), binary Protocol Buffers, and HTTP/2 streaming. Speed is a symptom, not the definition. And it's a poor fit at the public edge where REST wins.
"Browsers can call gRPC directly."No. Browser HTTP APIs don't expose the HTTP/2 control gRPC needs. You need grpc-web plus a proxy (e.g. Envoy) to translate — which is why gRPC lives between backend services, not at the browser.
"Protocol Buffers are self-describing / human-readable."They're opaque binary. The wire carries field numbers and packed values, not names — you need the .proto to decode a message at all. That opacity is the price of the small size.
"I can rename or renumber fields freely."The number is the permanent wire identity; renaming is fine (it's just a label), but never renumber or reuse a number. Delete a field and you reserve its number so it's never recycled — otherwise you silently corrupt old clients.
"gRPC means no schema to manage."The opposite — the .proto is your schema, and it must be shared across teams, versioned, and evolved by strict rules. It's less schema ceremony than nothing, but more than "just POST some JSON."
"gRPC replaces message queues for async work."No. gRPC is synchronous request/response (even streaming keeps the call open). For fire-and-forget, buffering, and decoupling, you want a queue (Day 18) — a fundamentally different pattern.

Active Recall

❓ A team deletes an unused field (number 4) from a widely-shared .proto, and a month later adds a brand-new field, reusing number 4 for it because "4 was free." Soon some services start reading garbage values for the new field. What went wrong, and what's the rule? (click to reveal)
They reused a field number, which is the one thing you must never do. On the wire, Protocol Buffers identify every field by its number, not its name — both ends share the .proto, so field 4 means "field 4" and nothing else. When they recycled number 4 for a new field of a possibly different type, any old client or old stored message that still had the original field 4 got interpreted as the new field 4 — right number, wrong meaning — producing garbage or type-mismatch errors. The rule: deleting a field means reserve-ing its number (and ideally its name) so it can never be recycled, and adding a field always means picking a fresh, never-before-used number. Field names are for humans; field numbers are the permanent contract. This is exactly how protobuf gives you forward/backward compatibility — but only if you respect the numbers.

Real-World Engineering

🔷 Google

Invented the pattern: internally, ~all service-to-service traffic ran over "Stubby" for a decade, and gRPC is its open-sourced successor (2015). Protocol Buffers are Google's default serialization for storage and RPC alike — the whole company talks in numbered binary messages.

☸️ Kubernetes & etcd

The control plane speaks protobuf, and etcd — the cluster's brain — exposes a gRPC API with streaming watches so components get pushed updates the instant cluster state changes. Server-streaming RPC is the backbone of "watch for changes."

🚗 Netflix & Uber

Both run enormous fleets of microservices and lean on gRPC for internal calls where JSON's parsing cost and payload size actually show up on the bill. Strong typing across dozens of languages and teams is as valuable to them as the raw speed.

🌐 Cloudflare & CockroachDB

Cloudflare uses gRPC between edge and core services; CockroachDB nodes gossip and replicate over gRPC. Anywhere machines talk to machines at high volume and low latency, the binary-contract-over-HTTP/2 combination keeps winning.

Flashcards (Spaced Repetition)

Q: In one sentence, what is gRPC?
A: A contract-first RPC framework where a typed .proto file is compiled into client stubs and server skeletons, so a remote call looks like a local function — sending compact binary Protocol Buffer messages over HTTP/2, with support for four kinds of streaming.
Q: Why are Protocol Buffer messages so much smaller than JSON?
A: Protobuf sends field numbers (a one-byte tag) instead of spelling out field names as text, packs values in compact binary (varints, no quotes/braces/whitespace), and relies on both ends sharing the .proto to know what each number means. Result: typically 3–10× smaller and much faster to parse.
Q: What are the four gRPC method types?
A: Unary (1→1), server streaming (1→many), client streaming (many→1), and bidirectional streaming (many⇄many). HTTP/2's two-way streams make the last three possible.
Q: Why can't a browser call a gRPC server directly?
A: gRPC needs low-level HTTP/2 frame/trailer control that browser fetch() doesn't expose. You need grpc-web plus a proxy (e.g. Envoy) to translate — which is why gRPC lives between backend services, and REST/GraphQL sits at the public edge.
Q: What is the one unbreakable rule about protobuf field numbers?
A: Never renumber or reuse a field number. The number is the permanent wire identity; renaming is safe, renumbering corrupts old clients. When you delete a field, reserve its number so it can't be recycled — this is what gives protobuf forward/backward compatibility.

If you only remember one thing: gRPC is the pneumatic tube behind the wall. You write one typed .proto contract, protoc turns it into client stubs and server skeletons so a remote call feels local, and messages fly as tiny binary Protocol Buffers — field numbers, not names — over an HTTP/2 connection that multiplexes calls and streams both ways. You gain speed, small payloads, strong cross-language typing, and native streaming; you give up human readability, direct browser support, and a schema you must share and version carefully (never renumber a field). It doesn't replace REST or GraphQL — it's what your services use to talk to each other, while something friendlier faces the public.
