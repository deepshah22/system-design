gRPC & Protocol Buffers
The Pneumatic Tube Behind the Wall

REST (Day 15) and GraphQL (Day 16) both hand people and browsers readable JSON text at the front door. But behind the wall — where one of your services calls another millions of times a second — that text is pure waste: verbose, re-parsed every call, loosely typed. gRPC is the pneumatic tube back there. You and the other service agree on a .proto contract up front, a compiler generates typed client and server code, and messages fly as tiny binary Protocol Buffers over HTTP/2 — with streaming built in. It makes a call to a machine across the datacenter look like a plain local function call.

Picture this

At the front of the building, the Reception Desk (REST) and the Concierge Booth (GraphQL) both hand you a paper order slip written in plain English — anyone can read it, which is exactly what you want when the public walks in. But between the back rooms, staff don't pass paper. There's a pneumatic tube: a sealed capsule shoots down a pipe in a blink. And the capsule isn't full sentences — because both rooms already share the same pre-printed form, the sender just drops values into numbered slots ("slot 1 = 42, slot 2 = Ada"). No field names travel down the tube, only numbers and values, packed into the smallest possible bundle. The receiver has the identical form, so it unpacks the capsule instantly and hands the clerk a fully-filled-in object — as if the value had been sitting on their own desk the whole time. That tube is gRPC: a shared contract agreed in advance (Protocol Buffers), tiny binary capsules instead of text, and a call across the datacenter that feels like a local function call. Hold the image: a sealed capsule with numbered slots, whistling through a tube nobody outside the building was ever meant to read.

The Story

Backend Bala owned the Checkout service. Every time a customer clicked "Buy," Checkout had to ask the Inventory service one blunt question — "is item 5573 still in stock?" — and it asked it eighteen thousand times a minute. The call was a plain REST GET /inventory/5573 returning JSON. It worked. It was also quietly expensive: each response was a fat text blob with field names spelled out ("quantityAvailable", "warehouseRegion"…), the receiver re-parsed those strings on every single call, and because JSON is untyped, the day Inventory changed quantity from a number to the string "12", Checkout didn't crash — it silently added the wrong amount to a cart for six hours before anyone noticed.

None of REST's strengths were helping Bala here. There was no browser on this path, no human reading the payload, no need for a bookmarkable URL. This was machine talking to machine, and the machine was drowning in ceremony: text it didn't need, names it re-parsed a billion times, and a "contract" that existed only in a wiki page nobody kept current.

A staff engineer replaced the path with gRPC. First she wrote a .proto file — a few lines declaring an InventoryService with a CheckStock method, and the exact shape of its request and reply, each field pinned to a number. She ran the Protobuf compiler, and out came a ready-made, strongly-typed client in Checkout's language and a matching server stub in Inventory's — different languages, one contract. Now Checkout called inventory.CheckStock(req) like a local function; under the hood the request serialized to a few dozen binary bytes (no field names on the wire — just field numbers) and flew over a single reused HTTP/2 connection. Payloads shrank by more than half, CPU spent parsing collapsed, and the "quantity is suddenly a string" bug became impossible — the compiler wouldn't let either side send the wrong type. Bala hadn't just made the call faster. He'd turned a fragile wiki-page handshake into a contract the compiler enforces.

What should stay in your head
gRPC is a contract-first RPC framework: you define your services and messages once in a .proto file, a compiler generates strongly-typed client and server code in many languages, and calls to a remote service look like ordinary local function calls. Messages travel as compact Protocol Buffers — binary, with field numbers instead of names on the wire — over HTTP/2, which adds connection reuse, multiplexing, and first-class streaming. The wins are size, speed, strong typing, and built-in streaming; the costs are that it's not browser-native, not human-readable, and binds both sides to a shared generated contract. Rule of thumb: gRPC lives behind the wall, between your own services — not at the public edge, where REST and GraphQL belong.

How gRPC Works — Four Moving Parts

gRPC came out of Google in 2015 as the open-source cousin of Stubby, the internal system Google had used for over a decade to let thousands of services call each other. The "g" officially stands for different words in different releases (a running joke), but the important letters are RPC — Remote Procedure Call: the old, powerful idea that a call to another machine should look and feel like calling a function in your own code. gRPC has four parts, and their combination is the whole story.

1. Contract first — the .proto file

You don't start with a URL; you start with a schema. In a .proto file you declare your messages (the data shapes) and your services (the callable methods). This file is the single source of truth both sides share — the pre-printed form from the anchor.

2. Code generation — the compiler writes the boilerplate

You run protoc (the Protobuf compiler) against the .proto, and it generates code: a ready-to-call client stub and a server skeleton in whatever languages you target — Go, Java, Python, C++, Rust, and more, all from the same contract. Nobody hand-writes serialization or HTTP plumbing. Change the .proto, regenerate, and both sides get a new typed API. This is why a Go service and a Java service can talk with zero glue code.

3. Protocol Buffers — the compact binary wire format

Messages don't go over the wire as JSON; they're serialized as Protocol Buffers. The trick you saw in the simulator: instead of sending "name":"Ada", gRPC sends a one-byte tag that packs the field number and its wire type, followed by the raw value. Field names never travel — both sides already know that field 2 is name from the shared contract. Unset fields are simply skipped. The result is a payload that's typically 3–10× smaller than the equivalent JSON and far cheaper to parse (no scanning quotes and commas — just read a tag, read a value).

4. HTTP/2 transport — one connection, many multiplexed calls, and streaming

gRPC runs on HTTP/2 (Day 3's HTTP, grown up). That buys three things REST on HTTP/1.1 struggled with: a single long-lived connection reused for thousands of calls (no reconnect-per-request tax), multiplexing (many in-flight calls interleaved on that one connection without head-of-line blocking), and native streaming — the server, the client, or both can send a continuous flow of messages, not just one-shot request/response. Streaming is the feature you can't cleanly get from plain REST, and it's why gRPC is a natural fit for live feeds and chatty internal pipelines.

The .proto Contract & Backward Compatibility

Everything hinges on this file. Read it once and the whole model clicks — a service is a set of callable methods; each method takes one message and returns one message; each field carries a number that is the real identity of that field on the wire.

syntax = "proto3"; message CheckStockRequest { int64 item_id = 1; string region = 2; } message CheckStockReply { bool in_stock = 1; int32 quantity = 2; } service InventoryService { // one request in, one reply out — a plain function call rpc CheckStock(CheckStockRequest) returns (CheckStockReply); }

The field numbers are not decoration — they are the contract. Because the wire format identifies fields by number, not name, gRPC gets clean backward and forward compatibility, which is how it does "versioning" without cutting a /v2:

Adding a field is safe.Give it a brand-new number. Old clients simply don't know field 7 exists and ignore it; new clients read it. No coordinated deploy needed — the counterpart to REST evolution and GraphQL's @deprecated.
Never reuse or renumber a field.If you delete quantity = 2 and later add price = 2, an old client will read new price bytes as a quantity — silent corruption. Mark retired numbers reserved so no one can ever reassign them.
Names are free to change; numbers are forever.Rename region to region_code and the wire doesn't care — only the number 2 is transmitted. This is the mirror image of JSON, where the name is the contract.

Four Kinds of Call — Not Just Request/Response

REST gives you exactly one shape: one request, one response. HTTP/2 lets gRPC offer four, and picking the right one is a real design decision.

Unary1 request → 1 response. The classic function call — CheckStock(req). 90% of calls. This is the direct REST equivalent.
Server streaming1 request → a stream of responses. "Subscribe me to this order's status" and the server pushes each update as it happens, over the one open call. Great for live prices, progress, log tails.
Client streaminga stream of requests → 1 response. The client sends many messages — chunks of a file upload, a batch of metrics — and the server replies once at the end with a summary.
Bidirectional streamingstream ↔ stream, both directions at once over a single connection. Chat, multiplayer game state, a live sync protocol — each side sends whenever it has something to say.

Those bottom three are the superpower plain REST can't match without bolting on WebSockets (Day 20). gRPC bakes streaming into the same contract and the same generated code, so a stream is just a method whose signature says stream.

The Hard Parts — Why gRPC Isn't the Front Door

gRPC's speed and typing are real, but they're bought with trade-offs sharp enough that you almost never expose it directly to the public. Four things pay the bill.

1. It isn't browser-native

A browser can't open a raw gRPC call — it can't fully control HTTP/2 framing from JavaScript, and it can't speak the binary trailer format gRPC needs. To reach a browser you need gRPC-Web plus a proxy (like Envoy) that translates between the browser's limited dialect and real gRPC. That's why the public edge stays REST/GraphQL and gRPC hides behind it. Machine-to-machine, not human-to-machine.

2. It isn't human-readable — debugging is harder

You can't curl a gRPC endpoint and eyeball the JSON. The payload is opaque binary; a packet capture shows bytes, not {"name":"Ada"}. You lean on special tools — grpcurl, server reflection, and gRPC-aware proxies — and your logs need decoding. The readability that made REST so easy to poke at is exactly what gRPC traded away for size.

3. Client and server are welded to the same contract

Both sides depend on generated code from the same .proto. That's a feature (the compiler catches mismatches) and a tax: you need a place to store and version .proto files, a build step that regenerates stubs, and discipline about the field-number rules above. A loose, schin-less JSON API is easier to start; a typed contract is safer to scale.

4. Load balancing needs to be gRPC-aware

Remember Day 5's load balancers spreading requests across servers? gRPC breaks the naive version. Because it reuses one long-lived HTTP/2 connection for thousands of calls, a simple connection-level (L4) balancer pins all that traffic to a single backend — the other replicas sit idle. You need an L7, gRPC-aware balancer (or client-side load balancing, or a service mesh — Day 27) that spreads individual calls, not connections. It's a classic "the fast path broke my old assumptions" surprise.

None of this says "don't use gRPC." It says gRPC is a specialist: put it where speed, typing, and streaming between your own services matter, and keep a REST or GraphQL layer at the edge for everyone else.

REST vs GraphQL vs gRPC — Choosing a Door

REST

Many resource URLs, JSON text, HTTP verbs, free HTTP/CDN caching, dead simple and universal. Over-/under-fetches; one shape only (request/response).

Best for: public APIs, CRUD, cache-friendly reads. (Day 15)

GraphQL

One endpoint, typed schema, client picks the exact fields in one trip. Kills over/under-fetching; caching and query-cost control become your job.

Best for: rich/varied clients, related entities, mobile. (Day 16)

gRPC

Contract-first, binary Protobuf over HTTP/2 — tiny, fast, strongly-typed, four streaming modes. Not browser-native, not human-readable, needs shared .proto.

Best for: internal microservices, low latency, streaming. (today)

The rule of thumb from Day 16 completes here: REST shines for simple, cacheable, public resources. GraphQL shines at the edge, where diverse clients each want a different slice of a connected graph. gRPC shines behind the wall, between your own services, where speed, strong typing, and streaming beat human readability. A large system runs all three at once: gRPC internally between services, and a REST or GraphQL gateway out front for browsers and partners. It's never "which one" — it's "which one where."

Common Mistakes & Misconceptions

The misconceptionThe reality
"gRPC replaces REST — it's just the faster version."It's a specialist, not a successor. gRPC wins behind the wall for machine-to-machine speed and streaming; REST/GraphQL win at the public edge where you need browsers, caching, and human-readable payloads. Most systems run both.
"Protocol Buffers is a compression algorithm."No. Protobuf is a serialization format — a compact way to lay out typed fields as bytes. It's small because it drops field names and uses binary, not because it runs a compressor. (You can still gzip it on top.)
"I can just call my gRPC service from the browser's fetch()."You can't call raw gRPC from a browser. You need gRPC-Web and a translating proxy (e.g. Envoy). Native gRPC assumes full HTTP/2 control the browser doesn't give JavaScript.
"Field names in my .proto matter for compatibility."The field number is the contract on the wire — rename freely, but never reuse or renumber. Deleting field 2 and later adding a different field 2 silently corrupts old clients. Use reserved.
"gRPC load-balances like any HTTP service."It reuses one long-lived HTTP/2 connection, so an L4 balancer pins all calls to one backend. You need an L7, gRPC-aware balancer (or client-side LB / service mesh) that spreads individual calls.
"Binary means it's insecure / obscure = secure."Binary is not encryption. gRPC's security comes from running over TLS like anything else; the Protobuf bytes are trivially decodable by anyone with the .proto. Never confuse "not human-readable" with "protected."

Active Recall

❓ A team moves an internal service to gRPC and it's beautifully fast in local tests. In production behind their load balancer, one backend replica is pegged at 100% CPU while the other four sit nearly idle — even though every replica is healthy. What went wrong, and how do you fix it? (click to reveal)
Their load balancer is balancing connections, not calls. gRPC runs over a single long-lived HTTP/2 connection that multiplexes thousands of requests. A connection-level (L4) balancer opens that one connection, pins it to whichever backend it picked, and every subsequent call rides the same connection to the same replica — so one box gets all the traffic and the rest starve. The fix is to balance at layer 7, gRPC-aware: use an L7 proxy/mesh (Envoy, a service mesh — Day 27) that distributes individual calls across backends, or client-side load balancing where the gRPC client itself holds connections to several replicas and round-robins calls. The deeper lesson: gRPC's biggest performance win — reusing one connection — is exactly what breaks the load-balancing assumptions REST-on-HTTP/1.1 let you take for granted.

Real-World Engineering

🔍 Google

Ran Stubby — gRPC's internal ancestor — for over a decade to wire together thousands of services across its datacenters, and open-sourced the distilled version as gRPC in 2015. Protocol Buffers has been Google's default data interchange format since 2001.

☸️ Kubernetes / CNCF

gRPC is a CNCF project and the nervous system of cloud-native infra: etcd, the kubelet↔container-runtime interface (CRI), and countless controllers speak gRPC. When your cluster's control plane talks to itself, it's almost always over gRPC.

🚗 Uber / Netflix

Both run vast internal microservice fleets where services call each other billions of times a day. gRPC's tiny binary payloads and strong typing cut latency and CPU at that scale, and its streaming powers real-time internal pipelines that plain REST couldn't carry cleanly.

📦 Dropbox / Cloudflare

Dropbox migrated performance-critical internal RPC off custom formats onto gRPC/Protobuf for speed and multi-language stubs. Cloudflare and many others pair gRPC with Envoy as the L7, gRPC-aware proxy that makes load balancing and gRPC-Web translation work.

Flashcards (Spaced Repetition)

Q: In one sentence, what is gRPC?
A: A contract-first RPC framework where you define services and messages in a .proto file, a compiler generates typed client/server code in many languages, and calls travel as compact binary Protocol Buffers over HTTP/2 — making a remote call feel like a local function call.
Q: Why is a Protobuf message so much smaller than the equivalent JSON?
A: It's binary and sends a one-byte tag carrying the field number + wire type instead of spelling out field names as text, and it omits unset fields entirely. Both sides already know the names from the shared .proto, so names never travel.
Q: What are the four gRPC call types?
A: Unary (1→1), server streaming (1→many), client streaming (many→1), and bidirectional streaming (many↔many) — all over one HTTP/2 connection.
Q: Why can't you call a gRPC service straight from a browser, and what's the workaround?
A: Browsers can't fully control HTTP/2 framing or gRPC's binary trailers from JS. Use gRPC-Web plus a translating proxy (e.g. Envoy). It's why gRPC stays behind the wall and REST/GraphQL sit at the public edge.
Q: Why does gRPC break naive load balancing, and how do you fix it?
A: It multiplexes thousands of calls over one long-lived HTTP/2 connection, so an L4 balancer pins them all to one backend. Fix with an L7, gRPC-aware balancer, a service mesh, or client-side load balancing that spreads individual calls.

If you only remember one thing: gRPC is the pneumatic tube behind the wall. Both services agree on a .proto contract up front, a compiler generates typed client and server code, and messages fly as tiny binary Protocol Buffers — field numbers, not names — over a multiplexed, streaming HTTP/2 connection, so a call across the datacenter feels like a local function call. You pay for that speed with readability and reach: it's not browser-native, not human-readable, welds both sides to a shared contract, and breaks connection-level load balancing. So gRPC lives between your services, while REST and GraphQL greet the public at the edge.
