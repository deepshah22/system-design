Apache Kafka Deep Dive
The Log That Never Forgets

Yesterday (Day 18) a queue was a mailbox: a message is read once and then it's gone. Kafka rewrites that rule. It's not a mailbox that empties — it's an append-only logbook that keeps every message for days, hands out a permanent page number (offset) to each one, and lets many independent readers move through it at their own pace and even rewind. That one change — keep the messages instead of deleting them — is why Kafka became the backbone of event streaming at LinkedIn, Uber, Netflix and almost every large system you use. Let's see exactly how it works.

Visual Memory Anchor

📖🔢

Picture this

Imagine a giant library that keeps a ledger — a bound book where every event in the town gets written on the next blank line, in the order it happened, and nothing is ever erased. Line 1, line 2, line 3… each line has a permanent number. Because one enormous book would be a bottleneck, the librarian splits it into several volumes — Volume A, Volume B, Volume C — and decides which volume an event goes into by a rule (all events about customer 42 always go in Volume B, so customer 42's story stays in order). Now the clever part: readers don't take pages away. Each reader just keeps a bookmark — "I've read Volume B up to line 5,120" — and reads forward from there whenever they like. A new reader can start from line 1 and replay the town's entire history. The accountant, the historian, and the fraud investigator each keep their own bookmark in the same book and never interfere with each other. That ledger is Kafka: an append-only, numbered, replayable log, split into partitions (volumes), read by many via offsets (bookmarks). Hold that image: the log that never forgets.

The Story

Streaming Sana ran data at a fast-growing ride-share company. Every trip produced a flood of events — RideRequested, DriverMatched, RideStarted, RideEnded, PaymentCharged — and a dozen teams wanted them. Pricing wanted them for surge. Fraud wanted them live. The data-science team wanted to reprocess a whole month of history to train a new model. Finance wanted a nightly batch. On Day 18's mailbox queue, this was a nightmare: once the fraud consumer read a RideEnded message, it was gone — the data scientist couldn't go back and read last Tuesday, because last Tuesday had already been deleted the instant someone consumed it.

So Sana kept spinning up a separate queue for every team, and the producer had to publish the same event to all of them. Twelve teams meant twelve copies, twelve places to fall out of sync, and still no way to replay history when a consumer had a bug and processed a day's worth of events wrong. The system was drowning not in traffic, but in copies and lost history.

Then Sana moved to Kafka, and the shape of the problem changed. The producer now writes each event once to a topic — say rides — which Kafka stores as an ordered, append-only log retained for seven days. Every team is its own consumer group reading the same log independently, each tracking its own offset (its bookmark). Fraud reads the tail in real time. Finance's nightly batch reads from where it left off. And when the data scientist wants last month? Because Sana bumped retention on a dedicated topic, she just resets her group's offset to zero and replays — no re-publishing, no special pipeline, just reading the same immutable history again. One write, many readers, full history, replay for free.

To make one topic handle a million events a second, Kafka splits it into partitions spread across a cluster of machines (brokers). Sana partitioned rides by rider_id, so every event for one rider lands in the same partition and stays in order — while different riders' events fan out across partitions for parallelism. She'd stopped thinking of messaging as "send and delete" and started thinking of it as an immutable stream of facts the whole company can read, re-read, and rewind. That mental shift — events as a replayable log, not messages that vanish — is the whole reason Kafka exists.

What should stay in your head
Kafka is a distributed, append-only commit log. Producers append records to the end of a topic; the topic is split into partitions (each an ordered, immutable sequence) spread across brokers for scale and replicated for durability. Every record in a partition gets a monotonically increasing offset — its permanent address. Unlike a queue, reading does not delete: records stay for a retention window (time or size), and each consumer tracks its own offset, so many independent consumer groups can read — and replay — the same stream. Within a group, each partition is owned by exactly one consumer, so parallelism is capped by the partition count, and ordering is guaranteed only within a partition — which is why you choose a partition key (e.g. user_id) to keep related events together and in order. The price: it's a heavyweight distributed system to operate, only ordered per-partition, and the wrong tool when you just want a simple task queue or a request/response answer.

Try It Yourself — Partitions & Consumer Groups

Here's the single most important — and most misunderstood — rule in Kafka: within one consumer group, each partition is read by exactly one consumer. That means your parallelism (how many consumers can work at once) is capped by the number of partitions, not the number of consumers you throw at it. The Core Machinery — Topics, Partitions, Offsets, Brokers

Kafka has a small vocabulary, and once these five words click, everything else is detail. Learn them in order — each builds on the last.

Record.The unit Kafka moves: a key, a value (the payload — JSON, Avro, protobuf, bytes), a timestamp, and headers. The key is special: it decides which partition the record lands in.
Topic.A named stream of records — rides, payments, clicks. It's the thing producers write to and consumers read from. A topic is a category, not a single file: under the hood it's split into partitions.
Partition.The real engine. Each topic is divided into N partitions, and each partition is an ordered, append-only log — records are only ever added to the end, never inserted or changed. Partitions are what let one topic scale across many machines and be read in parallel. Order is guaranteed within a partition, never across partitions.
Offset.Every record in a partition gets a sequential ID — 0, 1, 2, 3… — called its offset. It's the record's permanent address and also the consumer's bookmark: "consumer group fraud is at offset 5,120 in partition 2." Reading is just "give me everything after my offset." Rewinding is just "set my offset back."
Broker & cluster.A broker is one Kafka server; a cluster is several of them. Partitions are distributed across brokers so the load and storage spread out, and each partition is replicated to other brokers so a machine can die without losing data. Add brokers → more capacity.

Put it together: a producer sends a record with key rider_42; Kafka hashes the key to pick a partition (say partition 2), appends it at the next offset, and replicates it. Any number of consumer groups can later read partition 2 from any offset they choose. The record isn't deleted when it's read — it sits in the log until retention (e.g. 7 days, or 100 GB per partition) expires and old segments are dropped from the front. That "keep it, don't delete it on read" is the entire difference from a Day 18 queue.

A producer and a consumer, in spirit
# PRODUCER — write once to the topic, keyed for ordering producer.send( topic="rides", key="rider_42", # same key → same partition → in order value={"event": "RideEnded", "fare": 18.50} ) # CONSUMER — many groups read the SAME log independently consumer = KafkaConsumer( "rides", group_id="fraud-detection" # finance, pricing use different group_ids ) for record in consumer: handle(record.value) # offset is tracked per group, auto-committed or manual

Consumer Groups — Kafka's Trick for Being Both a Queue and Pub/Sub

Day 18 forced a choice: a work queue spreads one message across competing workers, while pub/sub copies each message to every subscriber. Kafka does both at once with a single elegant idea: the consumer group.

Within a group: it behaves like a work queue

A consumer group is a set of consumers with the same group_id that cooperate to read a topic. Kafka assigns each partition to exactly one consumer in the group. So if a topic has 6 partitions and the group has 3 consumers, each consumer owns 2 partitions and they split the work — competing consumers, just like a work queue. This is also why adding consumers beyond the partition count does nothing (you saw it in the simulator): there are no free partitions to hand them, so they sit idle. Parallelism = min(partitions, consumers).

Across groups: it behaves like pub/sub

Now run a second group with a different group_id on the same topic. It gets its own full copy of the assignment and its own offsets. Group fraud and group analytics both read every record in rides, independently, without affecting each other — that's pub/sub fan-out. One topic feeds unlimited groups, and each group internally load-balances across its own consumers. That's the whole magic: work-queue inside a group, pub/sub across groups.

When a consumer joins, leaves, or crashes, Kafka triggers a rebalance: it reassigns partitions across the surviving consumers so every partition still has an owner. Rebalances are essential (they make the group fault-tolerant) but they briefly pause consumption, so a group that rebalances constantly — because consumers keep timing out — is a common production headache.

Replication & Durability — Why Kafka Doesn't Lose Data

A log is only trustworthy if it survives a dead machine. Kafka's answer is per-partition replication with a leader and followers.

Leader & followers.Each partition has one leader replica (on one broker) and a configurable number of follower replicas on other brokers (replication factor, commonly 3). All reads and writes go to the leader; followers continuously copy the leader's log.
In-Sync Replicas (ISR).The set of replicas that are fully caught up with the leader. If the leader dies, Kafka promotes one of the ISR followers to be the new leader — no data lost, because an ISR replica had everything. A replica that falls behind drops out of the ISR until it catches up.
Producer acks.The durability dial. acks=0: fire and forget (fastest, can lose data). acks=1: wait for the leader only (fast, but a leader crash before followers copy loses the record). acks=all: wait until all ISR replicas have it (safest, slightly slower). Production systems that can't lose data use acks=all.
min.insync.replicas.The safety floor. With replication factor 3 and min.insync.replicas=2, a write with acks=all needs at least 2 replicas to accept it — so you tolerate one broker down and still never lose an acknowledged write. This is the classic durable configuration.

The through-line: Kafka lets you pick where you sit on the speed-vs-durability curve, per producer. A clickstream that can afford to lose a few events runs acks=1 for throughput; a payments stream runs acks=all with min.insync.replicas=2 so an acknowledged event is truly safe. (Modern Kafka manages this cluster metadata with a built-in Raft-based controller — KRaft — replacing the old ZooKeeper dependency; we'll meet Raft itself on Day 32.)

Why Kafka Is So Fast — Sequential Disk, Zero-Copy, Batching

Newcomers assume Kafka must keep everything in memory to hit millions of messages a second. It doesn't — it writes to disk, and it's fast because of how it uses the disk, not in spite of it. Three ideas do the heavy lifting:

Sequential, append-only writes.Because a partition is only ever appended to, Kafka writes to disk in one long sequential stream. Sequential disk I/O is hundreds of times faster than the random seeks a database does — a spinning disk or SSD is happiest writing in order, and the OS page cache turns most reads into memory reads anyway.
Zero-copy transfer.To send data to a consumer, Kafka uses the OS sendfile call to move bytes straight from the page cache to the network socket, without copying them up into the application and back down. Fewer copies, less CPU, more throughput.
Batching & compression.Producers group many records into a single batch and compress it; consumers fetch in big chunks. Amortizing the per-message overhead across a batch is what turns "one network round-trip per message" into "one round-trip per thousand messages."

The lesson worth carrying beyond Kafka: an append-only log is a beautiful data structure. Writes are sequential (fast), reads are sequential (fast), history is preserved (replayable), and there's nothing to update in place (simple). Half the systems in Phase 2 — write-ahead logs, replication logs, event sourcing (Day 76) — are the same idea wearing different clothes.

The Hard Parts — What Kafka Costs You

Kafka is astonishingly capable, which is exactly why it gets misused. "We'll just put Kafka in front of it" is a real over-engineering trap. Four costs separate "we run Kafka" from "we know when not to."

1. It's a heavyweight distributed system to operate

A production Kafka cluster is brokers, replication, partitions to size, retention to tune, consumer lag to monitor, and rebalances to tame. It is far more to run than a single SQS queue or a Redis list. Managed options (Confluent Cloud, AWS MSK) absorb a lot of this, but the conceptual weight — partitions, offsets, groups, ISR — never goes away. For a small app that just needs a task queue, Kafka is a cannon aimed at a mosquito.

2. Ordering is only per-partition — and partition count is sticky

You get order within a partition and nowhere else. If global ordering matters you're funneled to a single partition (killing parallelism), so most designs settle for per-key ordering via the partition key. And the partition count is hard to change later — increasing partitions reshuffles which key goes where (breaking the "same key → same partition" promise for existing data), so you must plan capacity up front. It's one of the few genuinely one-way doors in a Kafka design.

3. At-least-once by default; exactly-once is narrow

Same physics as Day 18: by default a consumer that processes a record then crashes before committing its offset will re-read it — duplicates. Kafka does offer exactly-once within Kafka (idempotent producers + transactions across topics), but the moment your consumer touches an external system (charges a card, writes to another database) you're back to needing idempotent consumers (Day 24). Assume duplicates, design so they don't hurt.

4. It's the wrong tool for the wrong job

Kafka is built for high-throughput streams you want to retain and replay. It's a poor fit for: a simple background task queue (SQS/RabbitMQ are lighter and give per-message acks and easy priorities), tiny low-traffic apps (the operational cost dwarfs the benefit), and anything request/response where a caller needs an answer now (that's still gRPC/REST). Reach for Kafka when history and replay and scale are the point — not as a default message bus.

The through-line: Kafka trades operational simplicity and per-message flexibility for durability, replayability, and enormous ordered throughput. A brilliant trade for an event backbone the whole company reads; a needless tax for a modest task queue.

Kafka vs the Field — When Each One Wins

Apache Kafka

The distributed log standard. Partitioned, replicated, retained topics; huge throughput; replay; a rich ecosystem (Connect, Streams, ksqlDB). The default when events are a first-class, long-lived asset.

Best for: event streaming, event sourcing, log aggregation, stream processing at scale.

RabbitMQ / SQS

Classic queues (Day 18). Delete-on-ack, per-message acks, priorities, easy routing. Lighter to run and simpler when you just need to offload tasks and don't need history or replay.

Best for: task queues, RPC-style work distribution, "run this job later."

Apache Pulsar

A newer log+queue hybrid that separates serving (brokers) from storage (BookKeeper), aiming for easier scaling and multi-tenancy. Overlaps heavily with Kafka; smaller but growing ecosystem.

Best for: teams wanting log semantics with tiered storage and geo-replication built in.

Redpanda / Kinesis

Redpanda is a Kafka-API-compatible engine in C++ (no JVM, no ZooKeeper) chasing lower latency. AWS Kinesis is a managed Kafka-like stream — same shard/partition ideas, less to operate, locked to AWS.

Best for: "Kafka semantics, less ops" — either self-hosted (Redpanda) or managed (Kinesis).

The headline: if the question is "who does this one job?" a queue is simpler. If the question is "what happened, who all needs to know, and can we replay it later?" you want a log — and Kafka is the one everyone else is measured against.

Common Mistakes & Misconceptions

The misconceptionThe reality
"Kafka is just a faster message queue."It's a log, not a queue. A queue deletes a message when it's read; Kafka keeps records for a retention window and lets many groups read and replay the same stream. That difference — persistence + replay — is the whole point, not speed.
"Add more consumers to a group and it goes faster."Only up to the partition count. Each partition is owned by exactly one consumer in a group, so consumers beyond the number of partitions sit idle. Parallelism = min(partitions, consumers). To scale further you must add partitions.
"Kafka guarantees global ordering."Order is guaranteed only within a single partition. Across partitions there is no ordering. You keep related events in order by giving them the same partition key (e.g. user_id), which routes them to the same partition.
"Reading a message removes it (so two consumers can't both get it)."Reading never removes anything. Consumers just advance their own offset. Two different consumer groups both read every record independently; a message only disappears when retention expires, regardless of who has or hasn't read it.
"Kafka gives you exactly-once for free."Exactly-once exists only within Kafka (idempotent producer + transactions). The instant a consumer writes to an outside system, you're back to at-least-once and must make processing idempotent. Assume duplicates.
"Kafka must keep everything in RAM to be that fast."It writes to disk. It's fast because partitions are append-only (sequential I/O), it uses zero-copy sendfile to the network, and it batches + compresses — not because of a giant memory buffer.

Active Recall

❓ You run a Kafka topic payments with 3 partitions. A teammate says throughput is too low, so they scale the consumer group from 3 consumers up to 9 consumers — and see no improvement at all. Two questions: (1) why didn't it speed up, and (2) they also notice that payments for a single account sometimes get processed out of order — what likely caused that, and how do you fix both problems together? (click to reveal)
(1) No speed-up because within one consumer group each partition is owned by exactly one consumer, so with only 3 partitions just 3 of the 9 consumers get work — the other 6 sit idle. Parallelism is capped at min(partitions, consumers) = min(3, 9) = 3. Adding consumers past the partition count does nothing; you must add partitions to raise the ceiling. (2) Out-of-order account events happen because ordering is guaranteed only within a partition, and if records aren't keyed by account, one account's events scatter across all 3 partitions and get processed in parallel with no ordering between them. The fix ties both problems together: partition by account_id (so every event for one account lands in the same partition and stays ordered) and increase the partition count (say to 12) so you can run up to 12 consumers in parallel. One decision — a good partition key plus enough partitions — buys you both ordering and scalable throughput. Mantra: order lives inside a partition; parallelism is capped by partition count.

Real-World Engineering

💼 LinkedIn

Kafka was born at LinkedIn (2011) to unify a tangle of point-to-point data pipelines into one central log every system could publish to and read from. It now moves trillions of messages a day there — the original "central nervous system for data" that the whole industry copied.

🚗 Uber

Uber runs one of the largest Kafka deployments on earth — trip events, driver locations, pricing, fraud signals and analytics all flow through Kafka. It's the backbone that lets dozens of independent teams react to the same stream of real-world events without calling each other.

🎬 Netflix

Netflix pipes a firehose of playback, UI and operational events through Kafka into its real-time analytics and monitoring (the Keystone pipeline) — powering everything from A/B tests to instant detection of a stream that's buffering for too many members.

🏦 Banks & retail

Payment networks, exchanges and retailers use Kafka as an ordered, replayable ledger of transactions and inventory changes — with acks=all and replication for durability, and replay to rebuild downstream views or recover after a bad deploy.

Flashcards (Spaced Repetition)

Q: In one sentence, how is Kafka different from a traditional message queue?
A: A queue deletes a message once it's read; Kafka is an append-only log that keeps records for a retention window, so many independent consumer groups can read — and replay — the same ordered stream, each tracking its own offset.
Q: What are a topic, a partition, and an offset?
A: A topic is a named stream of records. It's split into partitions, each an ordered, append-only log spread across brokers for scale and parallelism. An offset is the sequential ID of a record within a partition — its permanent address and the consumer's bookmark.
Q: How does a consumer group make Kafka act like both a queue and pub/sub?
A: Within a group, each partition is owned by one consumer, so the group splits the work like a work queue. Across groups, each group has its own offsets and reads every record independently — pub/sub fan-out. Work-queue inside, pub/sub across.
Q: Why is parallelism capped by partition count, and how do you get ordering?
A: Each partition is consumed by exactly one consumer in a group, so at most min(partitions, consumers) work in parallel — extra consumers idle. Ordering is guaranteed only within a partition, so you route related records to the same partition using a partition key (e.g. user_id).
Q: What do replication factor, ISR, and acks=all give you?
A: Each partition is replicated to several brokers (leader + followers); the ISR is the set fully caught up. With acks=all and min.insync.replicas=2, a write isn't acknowledged until enough replicas have it — so a broker can die without losing any acknowledged record.

If you only remember one thing: Kafka is the log that never forgets. Instead of a mailbox that deletes a message when it's read, Kafka appends every event to an ordered, immutable partitioned log and keeps it for a retention window, so many consumer groups can read — and replay — the same stream, each with its own offset. Learn the two rules cold: ordering lives inside a partition (so you pick a partition key to keep related events together), and parallelism is capped by the partition count (each partition is owned by one consumer per group, so extra consumers idle). Replication + ISR + acks=all make acknowledged writes durable; sequential disk I/O, zero-copy and batching make it blazing fast. And remember the cost: it's a heavyweight system to operate, only per-partition ordered, at-least-once by default, and the wrong tool for a simple task queue or a request/response answer. Reach for Kafka when events are a durable, replayable asset the whole company reads.
