WebSockets & Server-Sent Events
When the Server Speaks First

Every protocol so far — REST, GraphQL, gRPC — shares one silent assumption: the client speaks first, the server answers, and then it goes quiet. That's fine for "load this page." It's hopeless for a chat message that should appear the instant your friend sends it, a stock price that ticks on its own, cursors gliding in a shared document, or an AI answer streaming word-by-word. For those, the server needs to speak first — to push. Today we meet the two tools that let it: WebSockets, a permanent two-way phone line, and Server-Sent Events, a one-way live broadcast. Both start life as an ordinary HTTP request — and then refuse to hang up.

Picture this

Picture three ways two people can stay in touch. The first is a restless kid in the back seat: every few seconds, "Are we there yet? … Are we there yet? … Are we there yet?" Ninety-nine times out of a hundred the answer is "no." That's HTTP polling — the client keeps asking, most answers are empty, and real news still arrives late (only on the next ask). The second is picking up a phone and leaving the line open: you dial once, and after that either person can just speak the moment they have something to say — no redialing, no asking permission. That's a WebSocket: one connection, held open, both directions, instant. The third is a radio station: you tune in once, and the station broadcasts news to you as it happens — you only listen, you never talk back on that channel. That's Server-Sent Events: one connection, held open, but one-way (server → you). Burn in the image: polling is asking over and over; WebSocket is an open phone line; SSE is a radio you tune into. The whole lesson is knowing which one to reach for.

The Story

Realtime Rhea was building a live-ops dashboard and chat for a food delivery app. Support agents needed to see orders update live and chat with couriers in real time. Her first version used what she already knew: plain HTTP. The browser asked the server "any new messages? any order updates?" every 3 seconds. It technically worked — but it was quietly awful. With 5,000 agents online, the server was pounded with ~1.6 million requests an hour, and the overwhelming majority came back empty: "nope, nothing new." Worse, a courier's "I'm at the door" message could sit invisible for up to 3 seconds, because that's how long until the browser next bothered to ask. Fast and cheap were both impossible: poll more often and the server melts; poll less often and the app feels laggy.

She tried a clever patch called long-polling — the browser asks, and the server just holds the request open until it actually has news, then answers and the browser immediately asks again. Latency got much better. But it was fiddly: every message meant tearing down and re-establishing a request, timeouts to manage, and it was still fundamentally the client doing all the asking. It felt like forcing a one-way street to carry two-way traffic.

Then Rhea split her problem in two and picked the right tool for each half. For chat — where both sides send messages constantly — she used a WebSocket. The browser opens one connection with a quick HTTP "upgrade" handshake, and from then on the agent and the courier send messages over the same open line, in either direction, arriving in milliseconds. For the order-status feed and notifications — where data only flows one way, server to browser — she used Server-Sent Events: the browser opens one long-lived HTTP request, and the server streams updates down it as they happen, with automatic reconnection for free when the Wi-Fi hiccups.

The result: the server went from millions of pointless "anything new?" requests to a handful of connections that stayed quiet until there was actually something to send. Latency dropped from seconds to milliseconds, and load dropped through the floor. Rhea had learned the core lesson of real-time systems: stop making the client ask — let the server speak the moment it has something to say. The only new cost was that those open connections are stateful, and stateful connections, as she'd soon discover, are their own kind of hard.

What should stay in your head
Plain HTTP is half-duplex request/response: the client must ask before the server can say anything, so "live" data is faked by polling (ask repeatedly — most answers empty, news always a poll-interval late). WebSockets and Server-Sent Events both start as a normal HTTP request and then keep the connection open so the server can push. A WebSocket performs an HTTP Upgrade handshake (101 Switching Protocols) that turns the connection into a persistent, full-duplex channel — either side sends frames anytime, over ws:///wss://, binary or text. SSE is simpler and one-way: a single never-ending HTTP response of text/event-stream that the server writes updates into, with built-in auto-reconnect and event IDs. Use WebSockets when both sides talk (chat, games, collaborative editing); use SSE when only the server talks (notifications, live feeds, streaming AI tokens). The price of both: open connections are stateful — they eat memory and file descriptors, need heartbeats and reconnection logic, resist load balancers, and to scale past one server they need a pub/sub backplane so a message arriving on one node reaches a user connected to another.

Try this: in Short Polling, drag the poll interval down to 1s to chase low latency — requests explode and most are still wasted. Now push updates up to 120/min: waste drops to zero (data changes faster than you poll) but latency is still half your interval, and you silently miss every update between polls. Then flip to Push: requests collapse to one handshake per client, zero waste, near-instant latency — you just now hold one open connection per client, which is the whole cost you're trading for.

The WebSocket Handshake — How an HTTP Request Becomes an Open Line

The clever thing about a WebSocket is that it doesn't need a new port or a separate protocol negotiation with the firewall — it borrows an ordinary HTTP connection and then asks to be promoted. That promotion is the handshake.

1. The client asks to upgrade.The browser sends a normal GET request with special headers: Upgrade: websocket, Connection: Upgrade, a random Sec-WebSocket-Key, and Sec-WebSocket-Version: 13. It's still plain HTTP at this point — which is why it sails through the same ports (80/443) and proxies as any web request.
2. The server switches protocols.If it agrees, the server replies 101 Switching Protocols with a Sec-WebSocket-Accept header (a hash of the client's key, proving it understood). That 101 is the moment the connection stops being HTTP and becomes a raw, persistent WebSocket — wss:// when it's over TLS, which it should always be.
3. Both sides now exchange frames.The same TCP connection stays open and carries lightweight frames instead of requests. A frame has a tiny header (a few bytes) and a payload — text or binary. Either side sends whenever it wants: full-duplex. No more headers-per-message, no more "ask first."
4. Heartbeats keep it alive.Idle connections get silently killed by proxies and NAT boxes, so the two sides exchange ping/pong control frames to prove they're still there. If pongs stop coming, you know the connection died and can reconnect.
5. Either side can close.A close frame (with a status code) ends it cleanly. In practice the client also reconnects — with backoff — whenever the line drops, because on real networks it will drop.

The payoff: after one handshake, a message is just a frame with a few bytes of overhead flying down an already open pipe — versus a fresh HTTP request (headers, cookies, maybe a new TLS handshake) every single time with polling. That's why WebSockets are both faster (lower latency) and cheaper (less overhead) once data is flowing frequently in both directions.

Client side — a WebSocket in the browser
const ws = new WebSocket("wss://chat.example.com/socket"); ws.onopen = () => ws.send("hello from the courier"); // I can speak first now ws.onmessage = (e) => render(e.data); // server pushed something — instantly ws.onclose = () => reconnectWithBackoff(); // networks drop; always reconnect

Server-Sent Events — The One-Way Radio

Half the time you don't actually need two-way traffic. Notifications, a live scoreboard, a price ticker, a progress bar, an AI answer streaming in — the data only ever flows server → client. For that, WebSockets are overkill, and Server-Sent Events are the elegant, boring, wonderful answer.

SSE isn't a new protocol at all — it's just an HTTP response that never ends. The client opens a normal request; the server replies with Content-Type: text/event-stream and then simply keeps writing to the response, one event at a time, forever. The browser exposes this as a one-line API, EventSource, that hides all the plumbing.

The wire format is dead simple.Each message is text: data: {...} followed by a blank line. Optional fields make it powerful: id: tags each event, event: names a type your client can listen for, and retry: tells the browser how long to wait before reconnecting.
Reconnection is automatic — and resumable.If the connection drops, the browser reconnects on its own, and sends the last id it saw in a Last-Event-ID header. A well-written server uses that to replay only what was missed. You get "don't lose messages across a blip" nearly for free — something you'd have to hand-build on a WebSocket.
It's just HTTP, so it's friendly.SSE flows over normal HTTP(S), so it works through proxies, CDNs, and corporate firewalls that sometimes block WebSockets, and it inherits HTTP auth, cookies, and compression with no special handling.
The limits.One-way only (no client → server on this channel — you still use a normal request for that), text only (UTF-8, no binary), and on old HTTP/1.1 a browser caps you at ~6 concurrent connections per domain — a real gotcha that HTTP/2 multiplexing removes.
SSE — one line on the client, plain text on the wire
// CLIENT — the whole API is one object const es = new EventSource("/orders/stream"); es.onmessage = (e) => updateOrder(JSON.parse(e.data)); // auto-reconnects for free # SERVER — the response literally never ends Content-Type: text/event-stream id: 1042 data: {"order": 42, "status": "picked_up"} id: 1043 data: {"order": 42, "status": "delivered"}

Here's the modern twist that makes SSE suddenly everywhere: every streaming LLM answer you've seen — ChatGPT, Claude — arrives over SSE. The model produces tokens one at a time and the server streams each down an text/event-stream response, which is exactly why the text appears to type itself. One-way, server-push, resumable: a perfect fit.

The Scaling Problem — Why Open Connections Are Hard

Everything above is easy on one server. The difficulty — and the reason this is a system design topic, not a frontend trick — shows up the moment you have more than one server, which you always do.

Plain HTTP is stateless: any request can hit any server, because the server remembers nothing between requests (Day 2's whole point). WebSockets and SSE are the opposite — a connection is pinned to one specific server for its entire life. That breaks two things at once:

1. Load balancers must route by connection, not by request

A normal load balancer sprays each request wherever it likes. But a WebSocket's frames must all reach the same server that holds the connection, so you need connection-aware (Layer 4 / sticky) routing and a balancer that understands the HTTP upgrade. And every open connection consumes memory and a file descriptor on that server, so "how many concurrent connections can one box hold?" (the famous C10K → C10M problem) becomes a real capacity question — you tune the OS, not just the app.

2. You need a pub/sub backplane to fan messages across servers

Here's the classic bug, and it's worth burning in. Alice is connected to Server 1. Bob is connected to Server 2. Alice sends a chat message — it arrives at Server 1. But Bob's connection lives on Server 2, which never saw it. Bob gets nothing. The fix is a message backplane: every server publishes incoming messages to a shared pub/sub layer (Redis Pub/Sub, or Kafka from Day 19), and every server subscribes and pushes to whichever of its connections care. Server 1 publishes Alice's message; Server 2 receives it from the backplane and forwards it down Bob's socket.

Notice how this reuses exactly the pub/sub idea from Day 18 and the durable log from Day 19 — the realtime edge (WebSockets/SSE) is the last hop to the user, but behind it sits the same event backbone you've already been building. Real-time systems are pub/sub with a live delivery layer bolted onto the front.

The Hard Parts — What Persistent Connections Cost You

Push feels magical, so teams reach for WebSockets by reflex. But "hold a connection open forever" is a bill that comes due in four ways.

1. State is expensive and fragile

A stateless HTTP server can be killed and replaced freely — no request cares. A WebSocket server holds thousands of live connections, each with memory and a file descriptor; a deploy or crash drops all of them at once (a "reconnect storm" as everyone rushes back). You now own heartbeats, timeouts, graceful draining on deploy, and backpressure when a slow client can't keep up. None of that existed with request/response.

2. Reconnection, missed messages, and ordering

On a real network, connections drop constantly — phones change towers, laptops sleep, Wi-Fi blips. So you must assume disconnects and design for them: reconnect with exponential backoff, and figure out what the client missed while it was gone. SSE hands you Last-Event-ID for this; with WebSockets you build your own cursor/sequence-number scheme. Skip it and users silently lose messages.

3. Load balancers, proxies, and firewalls fight you

Long-lived connections irritate infrastructure built for short requests: proxies impose idle timeouts (hence heartbeats), some corporate firewalls block WebSocket upgrades entirely (a reason to prefer SSE, or keep a long-polling fallback), and sticky routing complicates otherwise-simple load balancing. The realtime layer needs infrastructure that's aware of it.

4. It's the wrong tool when you don't need push

If data changes rarely, or the client only needs it when it acts, don't hold a socket open — a plain request is simpler, cacheable, and stateless. If updates are one-way, prefer SSE over a WebSocket (less to operate, free reconnection). Reserve full WebSockets for genuinely bidirectional, high-frequency interaction. Reaching for a WebSocket to occasionally refresh a number is the real-time equivalent of Day 19's "put Kafka in front of everything."

The through-line: WebSockets and SSE trade statelessness — the thing that made HTTP so easy to scale — for instant, server-initiated delivery. A brilliant trade when liveness is the product; a self-inflicted operational wound when it isn't.

WebSockets vs the Field — When Each One Wins

WebSockets

One handshake, then a persistent full-duplex channel. Both sides push text or binary frames anytime, lowest latency. The most powerful and the most to operate.

Best for: chat, multiplayer games, collaborative editing, live cursors, trading terminals.

Server-Sent Events

A never-ending HTTP response — one-way server→client, text only, with auto-reconnect and event IDs built in. Simplest push, and firewall-friendly because it's just HTTP.

Best for: notifications, live feeds/dashboards, progress, streaming LLM tokens.

HTTP Long-Polling

The client asks, the server holds the request until it has news, then answers and the client re-asks. Works everywhere with no special support — the universal fallback, but clumsy and higher overhead.

Best for: a compatibility fallback when WebSockets/SSE are blocked.

Socket.IO / SockJS

Libraries that wrap WebSockets with automatic fallbacks (to long-polling), reconnection, rooms, and heartbeats. Convenience and robustness at the cost of a non-standard protocol on both ends.

Best for: teams wanting "just works" realtime without hand-building reconnection/fallbacks.

gRPC streaming

From Day 17 — server/client/bidirectional streaming over HTTP/2. Great service-to-service, but no direct browser support (needs grpc-web + a proxy), so rarely the browser-facing choice.

Best for: streaming between backend services, not browser ↔ server.

WebTransport (HTTP/3)

The emerging successor: bidirectional streams and unreliable datagrams over QUIC/HTTP-3, no head-of-line blocking. Still maturing and unevenly supported, but where low-latency realtime is heading.

Best for: the future — games and media needing UDP-like speed with web security.

The decision tree is short: Does only the server talk? → SSE. Do both sides talk, often? → WebSocket. Does data change rarely, or only when the user acts? → you didn't need push at all; use a plain request.

Common Mistakes & Misconceptions

The misconceptionThe reality
"WebSockets are a totally separate protocol from HTTP."They start as an ordinary HTTP request and are upgraded via a 101 Switching Protocols handshake — which is exactly why they reuse ports 80/443 and pass through the same infrastructure. After the handshake they're their own frame-based protocol.
"Just poll faster and it'll feel real-time."Faster polling means more load and more waste, and latency is still ~half your interval — you're always a poll behind, and you miss updates between polls. Push (WebSocket/SSE) removes both the load and the latency at once.
"WebSockets are always better than SSE."Only when you need two-way traffic. For server→client-only feeds, SSE is simpler, is plain HTTP (proxy/firewall friendly), and gives auto-reconnect + resumability for free. Reaching for a full WebSocket there is over-engineering.
"If it works on one server, it'll work at scale."A connection is pinned to one server. With multiple servers a message arriving on Server 1 never reaches a user on Server 2 unless you add a pub/sub backplane (Redis/Kafka) to fan messages across nodes — plus sticky, connection-aware load balancing.
"An open connection is basically free to keep around."Each one holds memory and a file descriptor for its whole life, needs heartbeats to survive proxy timeouts, and all of them drop at once on a deploy/crash (reconnect storm). Statefulness is the real cost you're paying for instant delivery.
"The connection will just stay up."On real networks it will drop — phones roam, laptops sleep, Wi-Fi blips. You must assume disconnects: reconnect with backoff and recover missed messages (SSE's Last-Event-ID, or your own sequence numbers on a WebSocket).

Active Recall

❓ You ship a chat feature over WebSockets. It's flawless in testing, so you scale to 3 app servers behind a round-robin load balancer. In production, users complain that messages sometimes reach some people and not others — seemingly at random. Two questions: (1) what's the root cause, and (2) what two changes fix it? Bonus: a teammate then asks why you used SSE, not a WebSocket, for the separate "order status" feed. (click to reveal)
(1) Root cause: each WebSocket is pinned to one server for its lifetime, and round-robin scatters users across all three. When Alice (on Server 1) sends a message, it arrives only at Server 1 — but Bob's connection lives on Server 2, which never saw the message, so Bob gets nothing. Whether a message "works" depends entirely on whether sender and recipient happen to share a server, which looks random. (2) Two fixes, together: first, add a pub/sub backplane (Redis Pub/Sub or Kafka) — every server publishes incoming messages to it and subscribes to it, so Server 1 publishes Alice's message and Server 2 receives it and pushes it down Bob's socket; second, make the load balancer connection-aware / sticky so a connection's upgrade and all its frames land on the same server. Bonus — SSE for order status: that feed is one-way (server→client only), so a full bidirectional WebSocket is unnecessary weight; SSE is plain HTTP (passes proxies/firewalls cleanly) and gives you automatic reconnection and Last-Event-ID resume for free. Mantra: WebSocket when both sides talk, SSE when only the server does — and either way, one server's connection can't reach another's user without a backplane.

Real-World Engineering

💬 Slack & Discord

Both use WebSockets as the live spine of messaging — the moment someone types, presence changes, or a reaction lands, it's pushed down an open socket. Behind it sits a fan-out layer so a message in a busy channel reaches thousands of connected clients across many servers.

🎨 Figma

Multiplayer design runs on WebSockets: every cursor move, selection, and edit streams bidirectionally in real time so a dozen designers see each other's changes instantly. It's a textbook case of genuinely two-way, high-frequency interaction where nothing but a WebSocket will do.

🤖 ChatGPT & Claude

The word-by-word "typing" effect of a streaming AI answer is Server-Sent Events: the model emits tokens one at a time and the server streams each down a text/event-stream response. One-way, resumable, plain HTTP — SSE's perfect use case, now used by the whole AI industry.

📈 Trading & live scores

Brokerages and sports apps push price ticks and score updates over WebSockets (or SSE for pure one-way feeds), where a half-second of staleness is unacceptable. The backends front the socket layer with a market-data pub/sub bus to fan the same tick to millions of screens at once.

Flashcards (Spaced Repetition)

Q: In one sentence, what problem do WebSockets and SSE solve that plain HTTP can't?
A: Plain HTTP is request/response — the client must ask first — so "live" data is faked by wasteful, laggy polling. WebSockets and SSE keep a connection open so the server can push the instant it has something, with no re-asking.
Q: How does a WebSocket connection get established?
A: Via an HTTP Upgrade handshake: the client sends a GET with Upgrade: websocket/Connection: Upgrade/Sec-WebSocket-Key; the server replies 101 Switching Protocols. The same TCP connection then carries full-duplex text/binary frames (wss:// over TLS).
Q: WebSocket vs SSE — when do you pick each?
A: WebSocket when both sides talk often (chat, games, collaborative editing) — full-duplex, binary-capable. SSE when only the server talks (notifications, feeds, streaming LLM tokens) — one-way, plain HTTP, auto-reconnect + Last-Event-ID resume for free.
Q: Why can't you scale WebSockets across servers by just adding boxes?
A: A connection is pinned to one server, so a message arriving on Server 1 won't reach a user connected to Server 2. You need a pub/sub backplane (Redis/Kafka) so every server publishes and subscribes, plus connection-aware/sticky load balancing.
Q: Why is polling a bad way to fake real-time?
A: It forces a lose-lose trade: poll often → huge load and mostly-empty responses; poll rarely → high latency (news is always up to one interval late) and missed updates in between. Push removes both the load and the latency at once.

If you only remember one thing: WebSockets and SSE exist so the server can speak first. Plain HTTP makes the client ask, so real-time gets faked with polling — wasteful and laggy. Both real answers begin as an HTTP request that refuses to close: a WebSocket upgrades (101 Switching Protocols) into a persistent full-duplex channel where either side sends frames anytime — use it when both sides talk (chat, games, collaborative editing). SSE is a never-ending, one-way text/event-stream HTTP response with free auto-reconnect and resume — use it when only the server talks (notifications, live feeds, streaming AI tokens). The price you pay is state: open connections cost memory and file descriptors, need heartbeats and reconnection, fight load balancers, and require a pub/sub backplane to fan messages across servers — the same Day 18/19 pub/sub and log, now with a live delivery layer on the front. And when you don't need push at all, a plain request still wins. Tomorrow (Day 21) we step back to the pattern all of this enables: Event-Driven Architecture.
