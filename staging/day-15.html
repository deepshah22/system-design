REST API Design
The Front Door of Your System

For two weeks you built the back of the house — replicas, shards, hash rings, indexes. None of it matters if the outside world can't talk to it. Today you design the front door: the API. REST is a small, powerful discipline — expose your system as a menu of nouns (resources like /users/42) that a fixed set of verbs (GET, POST, PUT, PATCH, DELETE) act on. Get this right and any developer — or any machine — can use your service without reading a manual. Get it wrong and every endpoint becomes a special case your teammates have to memorize.

Visual Memory Anchor

🍽️📋

Picture this

Imagine walking into a well-run restaurant. There's a menu of dishes — the nouns: "Table 12," "Order #42," "the fish." And there's a tiny, fixed set of things you're allowed to do to them — the verbs: look at a dish, order a new one, replace your whole order, tweak one item, or cancel it. You never invent new actions like "please-flambé-my-order"; you combine the same few verbs with different dishes. Every guest already knows how it works because the interface is uniform — the menu changes, the rules never do. That restaurant is a REST API: GET reads the dish, POST orders a new one, PUT replaces it, PATCH tweaks it, DELETE cancels it. Picture the menu of nouns and the five waiters who each know exactly one verb — that image is REST.

The Story

API Amara inherited a codebase where every action was its own endpoint. To read a user you called POST /getUser. To update one, POST /updateUserName. To delete, POST /deleteUserById. There were 340 endpoints, all POST, each with its own hand-rolled request shape. New hires took weeks to find anything. Caching was impossible — everything was a POST, so nothing could be cached. When the mobile team needed to "archive" a user, someone added a 341st endpoint: POST /archiveUserAndSendEmailV2. The API had become a pile of verbs with no grammar.

A staff engineer sketched a different idea on the whiteboard. "Stop thinking in actions," she said. "Think in things — resources — and let a fixed set of HTTP verbs act on them." She drew one line: /users/42. "That's the user. GET it to read. PUT it to replace. PATCH it to change one field. DELETE it to remove. To list them all, GET /users. To create one, POST /users. Six operations, one noun, zero new endpoints to memorize." Amara stared at it. Three hundred forty endpoints had just collapsed into a pattern.

She rebuilt the API around resources. Suddenly things she'd fought for months came for free. Browsers and CDNs could cache the GETs because GET means "just read, nothing changes." When the mobile network dropped mid-request and retried a PUT, nothing broke — because PUT is idempotent, doing it twice is the same as doing it once. New engineers guessed endpoint names correctly on day one. The API even documented itself: given /users/42/orders, anyone could infer /users/42/orders/7. Amara hadn't added a single feature — she'd added a grammar, and the grammar did the work.

What should stay in your head
A REST API models your system as resources (nouns with URLs like /orders/42) and acts on them with a small, uniform set of HTTP verbs. The verbs carry a contract: GET is safe (read-only) and cacheable; PUT and DELETE are idempotent (doing them twice equals doing them once); POST is neither (it creates something new each time). Because the interface is predictable, the whole ecosystem — browsers, caches, proxies, client libraries — already knows how to work with it, and humans can guess your endpoints. Nouns in the URL, verbs in the method, meaning in the status code.

The Uniform Interface — Why REST Feels Effortless

REST (REpresentational State Transfer) was described by Roy Fielding in 2000 as a set of constraints, not a library. The single most important one is the uniform interface: every resource is manipulated the same way, so nobody has to learn a bespoke API for each thing. Four ideas make it click.

1. Resources are nouns; methods are verbs

A resource is any "thing" worth addressing: a user, an order, a photo, even a search result. It gets a URL — its permanent address. You never put the action in the URL (/deleteUser is wrong); the action lives in the HTTP method. DELETE /users/42 already says "delete," so the URL just names the thing.

2. Safe methods never change anything

GET, HEAD, and OPTIONS are safe — they only read. This is a promise the whole web relies on: a crawler, a browser prefetch, or a "retry on timeout" is harmless because a GET can't create, charge, or delete. The classic disaster is putting a delete behind a GET link (GET /deleteAll) — then a search-engine crawler wipes your database just by following links. Safe means safe.

3. Idempotent methods can be retried without fear

An operation is idempotent if doing it once or five times leaves the system in the same state. PUT /users/42 {name:"Sam"} sets the name to Sam — run it ten times, still Sam. DELETE /users/42 removes the user; the 2nd–10th calls just find it already gone. This matters enormously in distributed systems, where a request can time out after the server acted but before the response arrives. The client doesn't know if it worked, so it retries — and idempotency makes that retry safe. POST is the odd one out: each POST creates a new thing, so a retried POST can create a duplicate. (Tomorrow-you fixes that with an idempotency key — a Day 24 topic.)

MethodMeansSafe?Idempotent?Typical body
GETRead a resource / list✅ yes✅ yesnone
POSTCreate a new sub-resource❌ no❌ nothe new thing
PUTReplace a resource entirely❌ no✅ yesfull resource
PATCHModify part of a resource❌ no➖ usually*the changed fields
DELETERemove a resource❌ no✅ yesnone

*PATCH is idempotent if it sets absolute values ({"status":"paid"}) but not if it describes a relative change ({"balance":"+10"}), which compounds on every retry.

4. Statelessness — every request stands alone

REST is stateless: the server keeps no memory of previous requests between calls. Each request carries everything needed to serve it (auth token, parameters, body). This is what lets you put any server behind a load balancer (Day 5) and have it handle any request — no "sticky" session pinning a user to one machine. Statelessness is the quiet enabler of horizontal scaling (Day 2). Session data doesn't vanish; it just moves to a shared store (Redis, Day 7) or into a signed token the client carries (JWT, Day 29).

Designing Good URLs

Good REST URLs read like a filing system a stranger could navigate. A few rules cover almost every case:

✗ Endpoints as verbs

POST /getUser?id=42 POST /createNewOrder POST /user/42/setStatusActive GET /listAllProductsForCategory

✓ Resources as nouns

GET /users/42 POST /orders PATCH /users/42 {"status":"active"} GET /categories/9/products
Use plural nouns for collections./users is the collection; /users/42 is one member. Consistency beats cleverness — pick plural everywhere.
Nest to show relationships./users/42/orders reads as "user 42's orders." Don't nest more than ~2 levels deep — /a/1/b/2/c/3/d/4 is a smell; link to the sub-resource instead.
Keep verbs out of the path.The method is the verb. If an action truly isn't CRUD (e.g. "publish," "cancel"), it's acceptable to model it as a sub-resource state change (PATCH /articles/9 {"state":"published"}) or, pragmatically, a controller-style endpoint (POST /articles/9/publish) — used sparingly.
Filter, sort & paginate with query params.GET /products?category=books&sort=price&page=2. Query strings are for how you want the collection sliced, never for identifying the resource itself.
Lowercase, hyphenated, no trailing slash./order-items not /OrderItems or /order_items/. Tiny consistency, big cumulative sanity.

Status Codes — The Server's Body Language

The HTTP status code is how the server tells the client what happened in one number. Returning 200 OK for everything (even errors, with {"error": true} hidden in the body) is one of the most common REST sins — it blinds every proxy, cache, and monitoring tool that reads the status line. Learn the five families; you rarely need more than a dozen specific codes.

2xx Success — it worked. 200 OK, 201 Created (after POST), 204 No Content (after DELETE).
3xx Redirect — go look elsewhere. 301 Moved Permanently, 304 Not Modified (your cached copy is still good).
4xx Client error — you messed up. 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests.
5xx Server error — we messed up. 500 Internal Server Error, 503 Service Unavailable.

The two most useful distinctions in practice: 4xx vs 5xx answers "whose fault is it?" — a 4xx means the client should fix its request and not just blindly retry; a 5xx means the server failed and a retry (with backoff) might succeed. And 401 vs 403: 401 means "I don't know who you are" (log in), 403 means "I know exactly who you are and you still can't" (permission denied) — a distinction we'll lean on hard in Authentication & Authorization (Day 28–29).

Pagination, Versioning & the Grown-Up Concerns

Never return an unbounded list

GET /events on a table with 40 million rows will melt your server and the client. Always paginate. Two common styles: offset/limit (?page=3&limit=50) — simple, but slow and unstable on huge, changing datasets; and cursor-based (?after=eyJpZCI6MTIzfQ) — you hand back an opaque pointer to "where you left off," which is stable even as new rows arrive. Big feeds (Twitter, Slack) use cursors precisely because rows shift under offset pagination — the same problem you'll design around in the Social Media Feed (Day 45).

Version so you can change without breaking callers

Once a mobile app in the wild depends on your response shape, you can't just change it. Version the API so old clients keep working: URL versioning (/v1/users → /v2/users) is the most common and most visible; header versioning (Accept: application/vnd.api.v2+json) is cleaner but harder to test in a browser. The rule that matters more than the mechanism: additive changes (new optional fields) don't need a new version; removing or renaming fields does.

A few finishing touches that separate senior APIs

Consistent error bodies.Every error returns the same shape: {"error":{"code":"out_of_stock","message":"...","request_id":"abc"}}. Machine-readable code, human message, and a request_id to grep your logs (Day 26).
Support conditional requests.ETag + If-None-Match lets a client say "only send it if it changed," returning a cheap 304 otherwise — this is caching (Day 6) wired straight into the protocol.
Rate-limit, and say so.Return 429 with a Retry-After header and X-RateLimit-Remaining so well-behaved clients can back off instead of hammering you (Day 24).
Document with OpenAPI.A machine-readable spec (OpenAPI / Swagger) generates docs, client SDKs, and mock servers from one source of truth — the uniform interface is what makes this automation possible at all.

REST & Its Cousins (REST Isn't the Only Front Door)

REST / JSON over HTTP

Resource-oriented, uses HTTP verbs and status codes, cacheable, human-readable. The default choice for public web and mobile APIs because the whole ecosystem already speaks it.

Great for: public APIs, CRUD-shaped services. Used by: Stripe, GitHub, almost everyone.

GraphQL

One endpoint; the client writes a query describing exactly the fields it wants. Kills over-fetching and under-fetching, but caching and rate-limiting get harder. Tomorrow's lesson.

Great for: rich clients, many related entities. Used by: GitHub v4, Shopify. (Day 16)

gRPC

Binary protocol over HTTP/2 using Protocol Buffers. Tiny, fast, strongly-typed, great for service-to-service calls inside your own network — less friendly to browsers.

Great for: internal microservices, low latency. Used by: Google, Netflix internals. (Day 17)

WebSockets / SSE

REST is request/response — the client always asks first. When the server needs to push (chat, live scores, notifications), you need a persistent connection instead.

Great for: real-time, server push. Used by: Slack, live dashboards. (Day 20)

The through-line: REST optimizes for a uniform, cacheable, human-legible interface over the public web. Its cousins each trade some of that away for a specific win — precise field selection (GraphQL), raw internal speed (gRPC), or server-initiated push (WebSockets). Knowing REST cold makes every one of those trade-offs legible.

Common Mistakes & Misconceptions

The misconceptionThe reality
"Any JSON-over-HTTP API is RESTful."Only if it follows the constraints: resource nouns, correct verbs, meaningful status codes, statelessness. POST /doEverything returning 200 with an error inside is HTTP, but it isn't REST — and it loses caching, retries, and guessability.
"Return 200 and put the error in the body."This blinds every cache, proxy, load balancer, and alerting tool that reads the status line. Use the real code: 404, 400, 409. The status line is the API's most-read piece of metadata.
"POST and PUT are basically the same."POST creates a new resource (server picks the URL) and is not idempotent — retrying can duplicate. PUT replaces a resource at a known URL and is idempotent. On a flaky network that difference is the gap between one charge and two.
"Put the verb in the URL so it's clear."/getUser, /createOrder throw away the entire point. The HTTP method already is the verb; doubling it means clients can't rely on GET being safe or PUT being idempotent.
"Versioning is premature; we'll change the JSON later."The moment a client you don't control depends on your response, its shape is frozen. Removing or renaming a field breaks them silently. Plan /v1 from day one, even if you never ship /v2.
"REST is always the right choice."REST shines for public, cacheable, CRUD-shaped APIs. For chatty internal service calls (gRPC), precise field selection (GraphQL), or server push (WebSockets), a cousin fits better. Uniformity is a feature and a constraint.

Active Recall

❓ A mobile client sends POST /payments to charge a customer $50. The request succeeds on the server, but the response is lost to a dead cell connection, so the client retries the same request. What happens, why, and how would you redesign this so the customer is charged exactly once? (click to reveal)
Because POST is not idempotent, the retry creates a second payment resource — the customer is charged twice. The server did its job both times; the problem is that "create a new thing" repeated is two things. Two fixes: (1) If the resource has a natural, client-known identity, model it as an idempotent PUT to a specific URL (PUT /payments/{clientGeneratedId}) — the second call just overwrites the same resource, no duplicate. (2) The general pattern: have the client send an idempotency key (a unique header per logical operation); the server records the key on first success and, on any retry with the same key, returns the original result instead of acting again. This is exactly why understanding safe vs idempotent isn't trivia — on unreliable networks, retries are inevitable, and idempotency is what makes them safe. (We build the idempotency-key machinery properly in Day 24.)

Real-World Engineering

💳 Stripe

Widely held up as the gold standard: clean resource nouns (/v1/charges, /v1/customers), correct status codes, cursor pagination, and first-class idempotency keys so a retried payment never double-charges. Their API design is a big part of why developers chose Stripe.

🐙 GitHub

GitHub's REST API is a textbook of good URL design — /repos/{owner}/{repo}/issues/{n}/comments reads like a filing path. They also run a parallel GraphQL API (Day 16), a real-world case study in when each style wins.

☁️ Amazon / AWS

Legend (from Jeff Bezos's ~2002 "API mandate") holds that every Amazon team was ordered to expose its data only through service interfaces — no back doors. That discipline of clean, uniform APIs between teams is widely credited as the seed of AWS itself.

🐦 Twitter / X

Their timeline endpoints use cursor-based pagination rather than page numbers — with millions of new tweets arriving constantly, offset pagination would skip and repeat items. A concrete case of choosing the pagination style to match the data's volatility.

Flashcards (Spaced Repetition)

Q: In one sentence, what is REST?
A: An architectural style that models a system as addressable resources (nouns with URLs) acted on by a small, uniform set of HTTP verbs (GET, POST, PUT, PATCH, DELETE), using status codes for meaning and staying stateless so any server can serve any request.
Q: What's the difference between "safe" and "idempotent"?
A: Safe = doesn't change server state at all (GET, HEAD) — pure read. Idempotent = may change state, but doing it N times equals doing it once (PUT, DELETE). All safe methods are idempotent; not all idempotent methods are safe. POST is neither.
Q: Why does statelessness matter for scaling?
A: If the server keeps no per-client memory between requests, every request is self-contained, so a load balancer can route any request to any server. That's what makes horizontal scaling (adding servers) trivial — no session pinning. Session data moves to a shared store or a client-held token.
Q: What status code for a successful POST that creates a resource, and for a successful DELETE?
A: 201 Created for the POST (ideally with a Location header pointing at the new resource). 204 No Content for a DELETE with nothing to return (or 200 if you return the deleted body).
Q: 401 vs 403 — what's the difference?
A: 401 Unauthorized = "I don't know who you are" — you're not authenticated, log in. 403 Forbidden = "I know who you are, and you still can't do this" — authenticated but not permitted. Auth-N vs Auth-Z.

If you only remember one thing: REST turns your system into a menu of nouns acted on by a fixed set of verbs. Put the thing in the URL (/orders/42) and the action in the method — GET to read (safe, cacheable), POST to create (not idempotent), PUT/DELETE to replace/remove (idempotent, safe to retry) — and let status codes carry the meaning. Because the interface is uniform and stateless, the whole ecosystem and every future teammate already knows how to use it.
