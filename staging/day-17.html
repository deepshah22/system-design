gRPC & Protocol Buffers
The Staff-Only Pneumatic Tubes

REST (Day 15) and GraphQL (Day 16) are the friendly front doors your users' browsers walk through — text, human-readable, forgiving. But behind the wall, your own services call each other millions of times a second, and there, spelling out "isActive": true in text on every message is pure waste. gRPC is the building's staff-only pneumatic-tube system: a strongly-typed .proto contract compiles straight into client and server code, messages fly as tiny binary Protocol Buffers over HTTP/2, and a single call can even be a two-way stream. Blazing fast — and not meant for human eyes at all.

Visual Memory Anchor

🛰️📦

Picture this

Out front, guests order at the Reception Desk (REST) and the Concierge Booth (GraphQL) — everything in plain words, so any visitor can read it. But staff never carry messages by hand between the back rooms. Instead there's a wall of pneumatic tubes: you drop a message into a sealed capsule, it's sucked through the tube, and it thunks out the other side in milliseconds. The capsule isn't a hand-written note — it's a coded slug: no field labels, just "slot 1 = 42, slot 2 = 'Ada', slot 4 = yes", because both ends already share the same blueprint (the .proto file) that says what each slot means. The tubes run in both directions at once — one capsule out, a stream of capsules back, no waiting. It's unreadable to a passing human, and that's the point: it's built for machines talking to machines, as small and fast as physically possible. That tube wall is gRPC: a shared binary contract, capsule-tight messages, and a connection that streams both ways.

The Story

Platform-team Priya ran the checkout path at a fast-growing shop. One POST /checkout from the app fanned out, behind the wall, into a storm of internal calls: the order service asked the inventory service, the pricing service, the fraud service, and the shipping service — and each of those asked two or three more. A single customer tap became forty service-to-service calls. Every one of them spoke REST over JSON, exactly like the public API.

At their traffic, that was quietly expensive. Each internal message spelled out the same field names as text on every request — "customerId", "warehouseId", "isExpressEligible" — millions of times a second. Each hop opened a fresh HTTP/1.1 connection, parsed JSON with a schema nobody had actually written down, and prayed the other team hadn't renamed a field. When the fraud team shipped "score" as a string instead of a number one Friday, three downstream services broke in production and nobody caught it until the pager did. The "contract" between services lived only in a wiki page and in everyone's memory.

A staff engineer moved the internal calls to gRPC. Now every service pair shared a single .proto file — a real, checked-in, strongly-typed contract. Run one compiler and it generated the client and server code in Go, Java, and Python alike, so calling a remote service felt like calling a local function: fraud.Score(order). The messages went out as binary Protocol Buffers — no field names on the wire, just numbered slots — riding one long-lived HTTP/2 connection that multiplexed all forty calls without reopening sockets. Payloads shrank by more than half, p99 latency dropped, and the fraud team couldn't ship a string where a number belonged — the schema wouldn't compile. Priya hadn't just made the calls faster. She'd turned an unwritten handshake into a contract the compiler enforces.

What should stay in your head
gRPC is a contract-first RPC framework: you write a .proto schema describing your messages and service methods, and a compiler generates client + server code in many languages so a remote call looks like a local function call. Messages travel as Protocol Buffers — a compact binary format that drops field names and ships numbered, varint-packed slots — over HTTP/2, which multiplexes many calls on one long-lived connection and enables streaming (unary, server-, client-, and bidirectional). The trade: it's tiny, fast, and strongly typed, but not human-readable, not natively browser-friendly (you need a gRPC-Web proxy), and harder to poke at with curl. That's why gRPC lives behind the wall — service-to-service — while REST/GraphQL greet the outside world.

How gRPC Works — Call a Remote Service Like a Local Function

gRPC (the "g" originally stood for Google, which built and open-sourced it in 2015; today it's a CNCF project) is an RPC framework — Remote Procedure Call. The old dream of RPC is simple: make calling code on another machine feel exactly like calling a function in your own program. gRPC delivers that with four moving parts.

1. Contract-first: the .proto file is the source of truth

You don't start with a URL, you start with a schema. A .proto file declares your message shapes and your service methods. That file is the single, version-controlled contract both sides agree on — no wiki page, no guessing.

2. Code generation: the compiler writes the boring parts

You run the Protobuf compiler (protoc) once, and it generates a typed client stub and a server skeleton in whatever languages you need — Go, Java, Python, C++, Rust, and more, all from the same contract. Calling the remote service becomes stub.GetUser(request): the stub serializes your message to bytes, ships it, waits, and hands you back a typed reply. Serialization, networking, and type-checking are generated, not hand-written.

3. Protocol Buffers on the wire: small and binary

The messages are encoded as Protocol Buffers (covered next) — a compact binary format that's typically 3–10× smaller and much faster to parse than the equivalent JSON, because it never puts field names on the wire and packs numbers tightly.

4. HTTP/2 as the transport: one pipe, many calls, both directions

Multiplexing.HTTP/1.1 handled one request at a time per connection (or juggled a pool). HTTP/2 sends many independent streams down a single long-lived connection at once — so gRPC's forty internal calls share one socket instead of opening forty.
Header compression.HTTP/2's HPACK compresses repeated headers, so the metadata overhead per call is tiny — a big deal when you make billions of small calls.
Full-duplex streaming.Because HTTP/2 streams are bidirectional, gRPC can keep a call open and push messages in either direction — the foundation of the four call types you'll see below.

Put together: you think in functions, the compiler generates the plumbing, the bytes are tiny, and the transport is a fast multiplexed pipe. That's why an internal gRPC call can be an order of magnitude cheaper than the same call over REST+JSON.

Protocol Buffers — the Schema & the Wire Format

Protocol Buffers ("protobuf") are the heart of gRPC, and they're useful on their own too. A .proto file defines messages (data shapes) and services (the methods, i.e. the RPCs). Here's the contract behind our story:

syntax = "proto3"; message User { int32 id = 1; # the number is the field's slot on the wire string name = 2; string email = 3; bool is_active = 4; string bio = 5; # added later — old clients just skip slot 5 } message GetUserRequest { int32 id = 1; } service Users { # the methods = the RPCs rpc GetUser(GetUserRequest) returns (User); rpc ListUsers(ListRequest) returns (stream User); # server streaming }

The one idea that explains everything: field numbers, not field names

See the = 1, = 2 after each field? Those aren't defaults — they're the field's tag number, its permanent slot on the wire. This is the whole trick. JSON writes the field name as text in every single message ("is_active":true is 16 characters). Protobuf writes only the number — field 4 becomes a single byte. The name lives once, in the shared .proto, never on the wire.

Each field on the wire is a tiny (tag, value) pair. The tag byte packs the field number and a wire type (is this a varint? a length-delimited blob?). Small integers use varints — a variable-length encoding where a number under 128 takes just one byte, so you don't pay 4 or 8 bytes for the number 42. Strings are length-delimited: one length byte, then the raw UTF-8. That's it. No braces, no quotes, no commas, no repeated names — which is exactly why the encoder above shows Protobuf landing so much smaller.

Schema evolution: how you change the contract without breaking anyone

Because the wire uses numbers, not names, the compatibility rules are refreshingly mechanical:

Adding a field is safe.Give it a brand-new number. Old code that doesn't know field 5 simply ignores the unknown slot; new code reads it. This is how bio got added without a flag day.
Never reuse or renumber a field.The number is the identity. Renaming a field in the .proto is harmless (names aren't on the wire); changing its number, or reusing an old number for new data, silently corrupts messages. Retired numbers are marked reserved so nobody grabs them.
Renaming is free; retyping is not.You can rename is_active to active freely. But you can't turn slot 4 from a bool into a string — the wire type changes and old bytes misparse.

This is the same "add fields, deprecate the old, never break the shape" discipline GraphQL uses — but here the compiler enforces it, and the field number is the anchor.

The Four Call Types — Because HTTP/2 Streams Both Ways

REST is one-shot: request in, response out, done. Because gRPC rides HTTP/2's long-lived bidirectional streams, a single RPC can be any of four shapes — and picking the right one is a real design decision.

Unary

→  •  ←

One request, one response — the classic function call. e.g. GetUser(id) → User. The workhorse; most RPCs are this.

Server streaming

→   ←←←←

One request, a stream of responses. e.g. "give me all users" or a live price feed — the server pushes results as they're ready instead of one giant payload.

Client streaming

→→→→   ←

A stream of requests, one response. e.g. uploading a large file in chunks, or shipping a batch of metrics, then getting one summary back.

Bidirectional

→→ ⇄ ←←

Both sides stream at once over one open call. e.g. a live chat, collaborative editing, or a two-way telemetry channel — send and receive independently.

This is gRPC's superpower over plain REST: real-time, long-lived, two-way communication is a first-class, strongly-typed feature — not something you bolt on with WebSockets (Day 20) and a hand-rolled message format.

The Hard Parts — Why gRPC Isn't Your Public API

Everything that makes gRPC fast behind the wall makes it awkward at the front door. Knowing these is what separates "we use gRPC" from "we know where to use gRPC."

1. Browsers can't speak it directly

gRPC needs fine-grained control over HTTP/2 frames that browser fetch() doesn't expose. So you can't call a gRPC service straight from a web page — you need gRPC-Web plus a proxy (like Envoy) that translates between the browser and the real gRPC backend. That's friction most public APIs would rather avoid, which is why the edge usually stays REST or GraphQL and gRPC lives internally.

2. Not human-readable — debugging is harder

You can't curl a gRPC endpoint and eyeball the JSON, because there is no JSON — it's binary capsules. Reading traffic needs special tooling (grpcurl, protobuf-aware proxies, reflection). The very compactness that saves bytes on the wire costs you the "just look at it" debuggability REST gives away for free.

3. Load balancing needs to be HTTP/2-aware

gRPC keeps one long-lived connection and multiplexes many calls over it. A dumb L4 (connection-level) load balancer will happily pin all of a client's traffic to one backend and leave the others idle — because it balances connections, and gRPC opens almost none. You need L7, request-aware balancing (Envoy, a service mesh, or client-side balancing) to spread the calls, not just the sockets. It's a classic gRPC-in-production gotcha.

4. The contract is a shared dependency

The .proto file is fantastic and it's now a coupling point: both teams depend on it, so you need a way to share and version it (a proto registry, a shared repo). Get the evolution rules wrong — reuse a field number — and you get silent data corruption instead of a loud error.

None of this says "don't use gRPC." It says gRPC trades human-friendliness and browser reach for speed, strong typing, and streaming — a trade that's a clear win between your own services and a clear loss for a public, browser-facing API.

REST vs GraphQL vs gRPC — One Last Look at the Three Doors

REST

Many resource URLs, text/JSON, free HTTP/CDN caching, works everywhere, trivially debuggable. Verbose on the wire; one-shot request/response only.

Best for: public APIs, CRUD, cache-friendly reads. (Day 15)

GraphQL

One endpoint, typed schema, client picks exact fields in one trip. Great for diverse clients over a rich data graph; caching & query-cost become your job.

Best for: rich/varied clients, mobile, many related entities. (Day 16)

gRPC

Contract-first, binary Protobuf over HTTP/2, code-generated stubs, four streaming modes. Tiny & fast & strongly typed; not browser-native, not human-readable.

Best for: internal service-to-service, low latency, streaming. (today)

The clean mental split: REST is the public reception desk, GraphQL is the concierge who assembles exactly the slice each client wants, and gRPC is the pneumatic-tube network the staff use behind the wall. Big systems run all three at once — gRPC internally between microservices, with a REST or GraphQL gateway translating to the outside world. As always, it's not "which one" — it's "which one where."

Common Mistakes & Misconceptions

The misconceptionThe reality
"gRPC is just a faster REST — use it everywhere."It's for service-to-service. Browsers can't call it directly (you need gRPC-Web + a proxy), you can't curl it, and it loses free HTTP caching. Public, browser-facing APIs usually stay REST/GraphQL; gRPC lives behind the wall.
"Protobuf is small because it compresses the data."No compression required — it's small because it never puts field names on the wire (just numbers) and packs integers as varints. The names live once, in the shared .proto. (You can still gzip on top.)
"The field number is just cosmetic / a default value."The number is the field's identity on the wire. Rename freely; never reuse or change a number — doing so silently corrupts messages. Retired numbers get marked reserved.
"gRPC load-balances like any HTTP service."It holds one long-lived HTTP/2 connection and multiplexes calls over it, so an L4 balancer pins all traffic to one backend. You need L7 / request-aware balancing (Envoy, service mesh, or client-side).
"gRPC only does request/response like REST."It has four call types — unary, server-streaming, client-streaming, and bidirectional — because HTTP/2 streams both ways. Real-time streaming is first-class, not bolted on.
"Changing the .proto is a deploy-everyone-at-once event."Not if you follow the rules: add new fields with new numbers and old clients ignore them. gRPC is designed for rolling, backward-compatible schema evolution.

Active Recall

❓ A team moves 40 internal microservices from REST+JSON to gRPC and payloads shrink by 60% — but under load, one backend pod is on fire at 100% CPU while its four identical replicas sit nearly idle. Traffic is hitting the service. What happened, and what's the fix? (click to reveal)
Their load balancer is balancing connections (L4), not requests. gRPC keeps one long-lived HTTP/2 connection per client and multiplexes all its calls over that single socket. An L4 balancer sees one connection, pins it to one backend, and there it stays — so every request from that client lands on the same pod while the replicas starve. REST over HTTP/1.1 accidentally spread load because it opened many short connections; gRPC's efficiency removes that accident. The fix is L7 (request-aware) load balancing: an HTTP/2-aware proxy like Envoy, a service mesh, or client-side load balancing that distributes individual calls across backends rather than whole connections. The deeper lesson: gRPC's one-connection efficiency is a feature and a load-balancing trap — you must balance at the request layer, not the socket layer.

Real-World Engineering

🔍 Google

Built gRPC from its internal "Stubby" framework, which has carried the majority of Google's inter-service traffic for years — tens of billions of calls per second across the fleet. Protocol Buffers are the lingua franca of nearly every internal API there.

🎬 Netflix

Adopted gRPC for internal service-to-service communication, generating typed clients so hundreds of microservices share strongly-typed contracts instead of hand-written REST clients — cutting integration bugs and boilerplate across teams.

🚗 Uber

Runs thousands of microservices and leaned into gRPC + Protobuf for the low-latency, high-throughput internal calls behind a ride request, where JSON's parsing cost and payload size were real money at their scale.

☸️ Kubernetes & etcd

The control plane you'll meet later is gRPC all the way down: etcd (Kubernetes' brain) exposes a gRPC API, and components stream cluster changes over it — a textbook case of internal, streaming, machine-to-machine RPC.

Flashcards (Spaced Repetition)

Q: In one sentence, what is gRPC?
A: A contract-first RPC framework where a .proto schema generates typed client/server code, and messages travel as compact binary Protocol Buffers over HTTP/2 — making a remote call look like a local function and supporting streaming both ways.
Q: Why is a Protobuf message so much smaller than the equivalent JSON?
A: It never puts field names on the wire — each field is a numbered slot (a tag) plus a tightly-packed value (small ints as varints, strings length-prefixed). The names live once in the shared .proto, not in every message; and there are no braces, quotes, or commas.
Q: What are the four gRPC call types?
A: Unary (one→one), server streaming (one→many), client streaming (many→one), and bidirectional (many⇄many). They exist because gRPC rides HTTP/2's long-lived bidirectional streams.
Q: Why doesn't gRPC work directly from a web browser?
A: It needs low-level control over HTTP/2 frames that browser fetch() doesn't expose. You bridge it with gRPC-Web and a proxy (e.g. Envoy). That's a big reason gRPC stays internal while REST/GraphQL face the public.
Q: What's the golden rule of evolving a .proto?
A: Add fields with new numbers; never reuse or change an existing field number. Old clients ignore unknown fields (safe additions); renaming is free (names aren't on the wire), but reusing a number silently corrupts data — retired numbers are marked reserved.

If you only remember one thing: gRPC is the pneumatic tube behind the wall. A shared, strongly-typed .proto contract compiles into client and server code, so a remote call feels like a local function; messages fly as tiny binary Protocol Buffers — field numbers, not names, on the wire — over a multiplexed HTTP/2 connection that can stream in either direction. The price is that it's not human-readable and not browser-native, which is exactly why it lives internally, between your own services, while REST and GraphQL greet the outside world.
