gRPC & Protocol Buffers
The Language Services Speak to Each Other

REST and GraphQL are the hotel's front desk — English spoken at a counter, for the outside world. But behind the wall your own services call each other thousands of times a second, and they don't need English, or politeness, or human-readable words. gRPC is the staff pneumatic-tube system: both ends share one blueprint (a .proto file), messages travel as tiny numbered binary capsules (Protocol Buffers), and the pipe is HTTP/2 — multiplexed and streaming. Calling a machine across the data center starts to feel like calling a function next to you.

Visual Memory Anchor

📜🚀

Picture this

The front desk (REST/GraphQL) is where guests speak English. But walk through the staff door and the hotel runs on something else entirely: a network of pneumatic tubes connecting the back rooms. Nobody writes sentences here. Instead, both ends of every tube keep the same one-page blueprint pinned to the wall — it says "slot 1 is the guest ID, slot 2 is the name, slot 3 is whether they're a VIP." So to send a guest's details you don't mail a labeled form ("name": "Ada", "vip": true); you drop a tiny capsule holding just the values with one-byte number tags — 1→Ada, 3→true — and it whooshes across in a fraction of the size, read instantly because the other end already knows what each slot means. One fat pipe carries many capsules at once, in both directions. That pipe is gRPC: a shared .proto blueprint, Protocol Buffers as the numbered binary capsules, and HTTP/2 as the multi-lane tube. Hold that image: pinned blueprint, numbered slots, no wasted words.

The Story

Platform-team Priya ran the checkout path at a growing store. One customer tap fanned out into a dozen internal calls: cart asked pricing, pricing asked inventory, inventory asked tax, and so on — all of them her own services, all speaking REST and JSON to each other. It worked, but two things quietly hurt. First, every hop paid a JSON tax: each service serialized a fat object to text, sent it, and the next parsed it back — multiplied across a dozen hops and millions of checkouts, the CPU spent just packing and unpacking words was enormous. Second, there was no contract. When the pricing team renamed amount to amountCents, nothing stopped them — and checkout started reading undefined in production at 2pm on a Friday. The "agreement" between services lived only in a wiki page nobody had read.

A staff engineer moved the internal calls to gRPC. She wrote one pricing.proto file — the single source of truth for what a pricing request and response look like — and ran the compiler. Out came ready-made client and server code in Priya's language and the pricing team's (different languages, same blueprint). Now Priya's code just called pricingClient.Quote(cart) as if it were a local function; under the hood the arguments were packed into a compact binary Protocol Buffers message, streamed over a persistent HTTP/2 connection, and unpacked on the other side. The payloads shrank to a fraction of the JSON. And the rename? The compiler wouldn't let it happen silently — the field had a number, the number was the contract, and changing the shape broke the build on both sides before it ever reached production.

The last win surprised her. The fraud service needed a live stream of checkout events, not a request-and-reply. Over REST that meant polling every second or bolting on a separate system. In gRPC it was one line in the .proto: stream. The same connection now pushed a continuous flow of events. Priya hadn't just made her calls faster — she'd swapped a pile of English forms for a typed, binary, streaming tube that the machines actually enjoyed talking through.

What should stay in your head
gRPC is a framework for calling a function on another machine as if it were local (a Remote Procedure Call). The contract is a Protocol Buffers schema (a .proto file), compiled into typed client + server code in any language. Messages are serialized to compact binary using numbered fields, and the transport is HTTP/2 — one persistent connection, many multiplexed requests, and first-class streaming in both directions. You trade human-readability and browser-nativeness for speed, tiny payloads, a strict enforced contract, and streaming — which is why gRPC dominates service-to-service traffic while REST/GraphQL stay at the public edge.

How gRPC Works — Call a Function Across the Network

gRPC was open-sourced by Google in 2016, distilled from an internal system called Stubby that had been wiring Google's services together for over a decade. The "g" is often read as Google; officially it just stands for gRPC. The core idea is old and powerful: a Remote Procedure Call — make talking to a machine across the network look like calling a normal function, so the network mostly disappears from your code. It has three moving parts.

1. The .proto file — one blueprint, two sides

You describe your service and its messages in a small language-neutral file. This is the contract — the only place the shape of the data is defined, shared by every service that speaks it.

syntax = "proto3"; service UserService { rpc GetUser (GetUserRequest) returns (User); } message GetUserRequest { int32 id = 1; } message User { int32 id = 1; string name = 2; bool active = 3; }

2. The compiler generates the boring code for you

You run protoc (the Protocol Buffers compiler) over that file and it emits, in whatever language you asked for, a ready-made client stub and a server skeleton. The client stub exposes GetUser() as a real method; the server skeleton gives you a function to fill in with the actual logic. All the serializing, framing, and network plumbing is generated — you never write it. Two teams in two different languages generate from the same file and are instantly compatible.

3. The call lifecycle

Client calls a local method.Your code runs userClient.GetUser({id: 9}). It looks and feels like an ordinary function call.
Marshal → binary.The stub serializes the request into a compact Protocol Buffers byte string (next section shows exactly how).
Travel over HTTP/2.The bytes are sent as an HTTP/2 request on a persistent, multiplexed connection to the server.
Server unmarshals, runs, replies.The server decodes the bytes back into an object, runs your handler, and marshals the User response back down the same connection — where the client stub decodes it and returns it to your code.

From your program's point of view, you called a function and got an object back. The network, the encoding, and the language boundary all vanished behind the generated stub. That illusion — comfortable and dangerous — is the whole point of RPC (and its famous risk: a "function call" that can be slow or fail is very different from a local one, which is why the reliability lessons in Week 4 exist).

Protocol Buffers — Why the Bytes Are So Small

Protocol Buffers (protobuf) is the serialization format underneath gRPC — the thing that turns an object into those tiny capsules. Its trick is simple and profound: field names never travel on the wire. In JSON, every message re-sends the string "active" and "email" every single time. In protobuf, the blueprint already assigns each field a number, and only the number goes on the wire.

The wire format, byte by byte

Each field is written as a one-byte tag — the field number combined with a wire type (is this a varint? a length-prefixed string?) — followed by the value. Here's name = "Ada" (field #2, a string):

0x12 0x03 0x41 0x64 0x61 ↑ ↑ ↑ tag len "A" "d" "a" (field #2, type=string)

Three bytes of overhead-plus-value versus JSON's "name":"Ada" at twelve characters. A number-and-value beats a name-and-value every time — and across billions of messages, that's real CPU, bandwidth, and latency saved. Integers use an even cleverer scheme called varint: small numbers take one byte, larger ones grow only as needed, so id = 9 is a single byte after its tag.

Field numbers are the contract — treat them as sacred

Because only numbers travel, the numbers are the entire agreement between sender and receiver. This gives protobuf its superpower — safe schema evolution — and its sharpest footgun:

✅ Adding a field is safe.Give it a brand-new number. Old code that doesn't know field #7 simply ignores the unknown bytes; new code reads it. No coordinated deploy, no /v2.
✅ Renaming a field is safe.The name is only a local label in your code — the wire cares about the number. Rename amount to amountCents freely, as long as it keeps number #4.
❌ Reusing or changing a number is catastrophic.If you delete field #4 and later hand #4 to a different field, every old client now silently misreads new data as the old shape. This is the #1 protobuf disaster. The fix is a keyword — reserved 4; — that permanently retires a number so no one can reuse it.

This is the mirror image of REST versioning: instead of cutting a whole new API version, you evolve one schema forever by only ever adding numbered fields and retiring old numbers — never repurposing them.

Four Call Types & the HTTP/2 Engine

REST really only does one shape: one request, one response. Because gRPC rides on HTTP/2 — which can keep a stream open and send many messages over one connection — it offers four shapes, and the streaming three are what REST simply can't do cleanly.

UnaryOne request → one response. The ordinary function call: GetUser(id) returns a User. This is 90% of calls.
Server streamingOne request → a stream of responses. Ask once, get a flowing feed: a live price ticker, search results as they're found, a large file in chunks.
Client streamingA stream of requests → one response. Upload a flow of data and get a single summary back: telemetry, a file uploaded in chunks.
Bidirectional streamingTwo independent streams over one connection, both sides sending whenever they like. Real-time chat, multiplayer state, a live collaboration session.

Why HTTP/2 is the secret ingredient

gRPC didn't invent streaming; it inherited it from HTTP/2, the transport it runs on. Three HTTP/2 properties make gRPC what it is:

Multiplexing.Many requests share one TCP connection at the same time, each on its own "stream." Old HTTP/1.1 could send only one request at a time per connection (or opened a pile of connections). gRPC clients keep one warm connection and fire thousands of calls down it.
Bidirectional streams.A stream can carry a flow of messages in both directions — exactly the primitive the four call types are built on.
Binary framing + header compression.HTTP/2 is already binary and compresses repeated headers (HPACK), so gRPC's small binary bodies travel on an efficient binary pipe end to end.

That one persistent, multiplexed connection is a gift for throughput — and, as we'll see, a trap for load balancers.

The Hard Parts — What You Give Up

gRPC's speed and typing aren't free. Four costs decide whether it belongs at a given boundary, and knowing them is what separates "we use gRPC" from "we understand gRPC."

1. It isn't browser-native

Browsers can't speak raw gRPC — the JavaScript in a web page has no access to the low-level HTTP/2 frames and trailers gRPC needs. So a browser can't call a gRPC service directly. The workarounds are gRPC-Web plus a proxy (like Envoy) that translates, or simply keeping REST/GraphQL at the public edge and using gRPC only behind it. This is the single biggest reason gRPC lives service-to-service and not client-to-server.

2. It isn't human-readable

You can't curl a gRPC endpoint and eyeball the JSON, because there is no JSON — just bytes that mean nothing without the .proto. Debugging needs special tools (grpcurl), and your logs and traces can't just print the payload. The readability you loved in REST is gone; you traded it for size and speed.

3. Load balancing quietly breaks (the classic trap)

gRPC keeps one long-lived HTTP/2 connection and multiplexes everything over it. A normal connection-level (Layer 4) load balancer picks a backend when the connection opens and then pins every future request to it. Result: a client hammers a single server forever, and adding more servers spreads no load at all. The fix is request-level (Layer 7) load balancing — a gRPC-aware proxy like Envoy or Linkerd, or client-side load balancing — that distributes individual requests, not connections. This surprises teams in production constantly.

4. The schema is now an artifact you must manage

The .proto files are a shared source of truth that has to be versioned, distributed to every team, and evolved with discipline (remember: never reuse a field number). That's real governance overhead — a schema registry, code-gen in every build — that REST's looser, name-based JSON never demanded.

REST vs GraphQL vs gRPC — Choosing a Door

REST

Many resource URLs, HTTP verbs, JSON text, free HTTP/CDN caching, dead simple and universal. Verbose, over-/under-fetches, one-request-one-response only.

Best for: public APIs, CRUD, cache-friendly reads. (Day 15)

GraphQL

One endpoint, typed schema, client picks exact fields in one trip. Great for rich, varied clients; caching and query-cost control become your job.

Best for: diverse clients over a related data graph. (Day 16)

gRPC

Binary Protocol Buffers over HTTP/2 — tiny, fast, strictly typed, streaming, multi-language stubs. Not browser-native, not human-readable, needs L7 load balancing.

Best for: internal service-to-service, low latency, streaming. (today)

The rule of thumb from Day 16 now completes: REST shines for simple, cacheable, public resources. GraphQL shines at the edge where diverse clients each want a different slice of a connected graph. And gRPC shines behind the wall, between your own services, where speed, a strict contract, and streaming beat human readability — and where nobody needs to curl it. Big systems run all three: gRPC internally, REST or GraphQL at the public edge, often stitched together by an API gateway (Day 27). It's rarely "which one" — it's "which one where."

gRPC is the fourth stop in our communication patterns arc, and the first built for machine-to-machine rather than the public. It stands on HTTP (Day 3), specifically HTTP/2's streams, for its multiplexed pipe. Its streaming call types are cousins of the persistent connections behind WebSockets (Day 20). Its load-balancing trap is why the load balancer ideas (Day 9) must grow up into request-level (L7) balancing, which reappears in the API Gateway and service-mesh lessons (Day 27). And its "call a remote thing like a local function" illusion is exactly what the reliability lessons of Week 4 — timeouts, retries, circuit breakers — exist to make safe.

Common Mistakes & Misconceptions

The misconceptionThe reality
"gRPC replaces REST everywhere."It replaces REST between your own services. At the public edge — browsers, third-party developers, cache-friendly reads — REST/GraphQL usually still win. gRPC isn't browser-native and isn't human-readable.
"Protocol Buffers sends my field names."No — it sends field numbers and values. The names are just labels in your code. That's exactly why the payload is small and why you can rename freely but must never reuse a number.
"I can change a field's number to tidy up the schema."Never. The number is the contract. Reusing or re-assigning a number silently corrupts data for every client on the old shape. Delete a field with reserved, never repurpose its number.
"gRPC load-balances automatically like my REST services."It doesn't. One long-lived HTTP/2 connection pins to one backend under a Layer-4 balancer, so load never spreads. You need L7/request-level balancing (Envoy, Linkerd) or client-side LB.
"A gRPC call is basically a local function, so I can ignore failure."The syntax looks local; the network is still there. Remote calls are slow-sometimes and fail-sometimes. You still need timeouts, retries, and circuit breakers (Week 4).
"HTTP/2 fixes all head-of-line blocking."It fixes it at the HTTP layer (independent streams), but a single dropped TCP packet still stalls every stream on that connection (TCP head-of-line blocking). Solving that needs QUIC / HTTP/3.

Active Recall

❓ A team moves their internal API to gRPC and puts three identical server replicas behind their normal load balancer. Latency is great in testing, but in production one replica sits at 95% CPU while the other two idle near zero — and adding a fourth replica changes nothing. What's happening, and what's the fix? (click to reveal)
They hit the gRPC load-balancing trap. gRPC keeps a single long-lived HTTP/2 connection and multiplexes all its calls over it. Their load balancer works at the connection level (Layer 4): it picks a backend when the connection is opened and then pins every subsequent request to that same replica. So each client's thousands of calls all land on one server, and new replicas get no share of the existing connections. The fix is request-level (Layer 7) load balancing — a gRPC-aware proxy such as Envoy or Linkerd, or client-side / lookaside load balancing — that distributes individual requests across replicas rather than whole connections. The deeper lesson: gRPC's greatest strength (one warm, multiplexed connection) is exactly what defeats naive connection-based balancing.

Real-World Engineering

🔍 Google

gRPC is the open-source descendant of Stubby, the internal RPC system that has connected Google's services — billions of calls per second — for well over a decade. Protocol Buffers is Google's default for almost all internal data interchange and storage.

🎬 Netflix

Runs a vast internal microservice mesh where gRPC carries service-to-service traffic. Their heavy investment in Envoy and service-mesh tooling is driven partly by exactly the L7 load-balancing problem gRPC's long-lived connections create.

🚗 Uber

Migrated large parts of its platform from JSON/HTTP to gRPC + Protocol Buffers to cut serialization cost and latency across thousands of services, and to get a strict cross-language contract for teams writing in Go, Java, and more.

☁️ CNCF / Cloud-native

gRPC is a graduated CNCF project and the lingua franca of Kubernetes-era infrastructure: etcd, Envoy's control plane (xDS), and countless platform components expose gRPC APIs by default.

Flashcards (Spaced Repetition)

Q: In one sentence, what is gRPC?
A: A framework for calling a function on another machine as if it were local (RPC), using a Protocol Buffers .proto schema compiled into typed multi-language client/server stubs, compact binary messages, and HTTP/2 (multiplexed + streaming) as the transport.
Q: Why is a Protocol Buffers message so much smaller than the equivalent JSON?
A: Field names never travel — the shared .proto assigns each field a number, and only a one-byte tag (number + type) plus the raw value goes on the wire. Integers use varints, so small numbers are one byte. JSON re-sends every field name as text on every message.
Q: Why can you rename a protobuf field safely but never reuse its number?
A: The number is the wire contract; the name is only a local code label. Rename freely as long as the number is unchanged. Reusing a number makes old clients misread new data as the old field — corruption. Retire a number with reserved, never repurpose it.
Q: What are the four gRPC call types?
A: Unary (1 request → 1 response), server streaming (1 → many), client streaming (many → 1), and bidirectional streaming (many ↔ many). The streaming three come from HTTP/2's long-lived, multiplexed streams.
Q: Why does gRPC break naive load balancing, and what's the fix?
A: It multiplexes everything over one long-lived HTTP/2 connection; a Layer-4 (connection-level) balancer pins that connection to one backend, so load never spreads. Fix: request-level (Layer-7) load balancing — Envoy/Linkerd or client-side LB — which distributes individual requests.

If you only remember one thing: gRPC is how your services talk to each other. A shared .proto blueprint defines the contract; Protocol Buffers ships only numbered fields as tiny binary capsules (names never travel); HTTP/2 carries many of them — and full streams — over one persistent connection. You call a remote machine as if it were a local function, and pay for it in speed, size, strict typing, and streaming. The price: no browsers, nothing human-readable, a schema you must govern, and a load-balancing trap that needs Layer-7 to solve. gRPC doesn't replace REST — it takes the boundary REST was never built for: the fast, private wall between your own services.
