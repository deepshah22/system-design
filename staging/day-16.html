GraphQL Architecture
Let the Client Draw the Plate

Yesterday's REST reception desk had a fixed menu: each endpoint hands back a fixed plate. That works beautifully — until a phone on a slow train needs three fields but gets forty (over-fetching), or needs one screen's worth of data spread across eight endpoints (under-fetching, eight round-trips). GraphQL flips who's in charge: one endpoint, a typed schema, and the client writes a query describing the exact shape of the data it wants — delivered in a single trip. Power, and a whole new set of trade-offs.

The Story

Mobile-team Mina was rebuilding the app's profile screen. To draw it she needed the user's name and avatar, the titles of their last few posts, and for each post the first two comments with the commenter's name. Simple screen. On the REST API it turned into a nightmare of round-trips: GET /users/9 (which returned 38 fields — she used 2), then GET /users/9/posts, then a GET /posts/{id}/comments for each post, then a GET /users/{id} for each commenter to get their name. On hotel Wi-Fi the screen took four seconds and a spinner to appear. She was simultaneously downloading way too much (36 unused user fields) and making way too many trips.

The backend team's answer had been "we'll add a custom endpoint for the profile screen" — GET /mobile/profile-screen-v2. It worked. Then the web team wanted the same data in a slightly different shape, so they added /web/profile. Then the profile redesign needed one more field, so /mobile/profile-screen-v3. The API was quietly growing a bespoke endpoint for every screen in every client — the exact 340-endpoint sprawl REST had promised to cure, sneaking back in through the side door.

A staff engineer put a single POST /graphql endpoint in front of the same data and handed the clients the pen. Now Mina's app sent one request that literally said: { user(id:9){ name avatarUrl posts(last:3){ title comments(first:2){ text author{ name } } } } } — and got back one JSON object shaped exactly like that query, in one trip. No unused fields. No waterfall of requests. When the web team needed a different shape, they wrote a different query against the same endpoint — no new backend deploy. The API stopped growing an endpoint per screen, because the schema described everything that was possible and each client just asked for the slice it needed. Mina hadn't been given more data — she'd been given a language to ask for exactly what she wanted.

What should stay in your head
GraphQL is a query language for your API plus a typed schema that defines a graph of the data you expose. There is usually one endpoint (POST /graphql); the client sends a query whose shape is the shape of the response, so it fetches exactly the fields it needs, in one round-trip — killing REST's over-fetching and under-fetching. The cost: you move complexity to the server (each field is resolved by a resolver, and a naive one re-introduces the N+1 problem against your database), and you lose easy URL-based HTTP caching, so caching, rate-limiting, and query-cost control all become your job. GraphQL doesn't replace REST — it trades REST's simplicity and free HTTP caching for precise, client-driven fetching.

How GraphQL Works — One Endpoint, Three Operations

GraphQL was created at Facebook in 2012 (open-sourced 2015) to solve exactly Mina's problem: rich mobile screens over slow networks, where every wasted byte and every extra round-trip hurt. It has three moving parts, and the beauty is how few they are.

1. A single endpoint, and the query is the shape

Instead of many URLs, there's typically one: POST /graphql. The request body carries a query — a skeleton of the fields you want, nested to match the relationships. The killer property: the response mirrors the query. Ask for { user { name } } and you get back { "user": { "name": "Ada" } } — no more, no less. There's no guessing what fields an endpoint returns; you declare them, so you always get precisely that.

2. Three operation types

queryRead data (the equivalent of REST's GET). Multiple queries can be batched into one request, and you can ask for several unrelated trees at once.
mutationWrite data — create, update, delete (REST's POST/PUT/PATCH/DELETE). A mutation also returns a shape you choose, so you can read back exactly the fields that changed in the same trip.
subscriptionA long-lived stream: the server pushes updates when data changes (usually over WebSockets — Day 20). This is how GraphQL does real-time, e.g. a live comment feed.

3. The three problems it targets

Everything about GraphQL is aimed at three specific REST pain points:

Over-fetching.REST's GET /users/9 returns the whole user object even if you wanted one field. On mobile, those wasted bytes are latency and battery. GraphQL returns only the fields you name.
Under-fetching (the N+1 waterfall).One REST resource rarely fills a screen, so you make a cascade of dependent calls — user, then posts, then each post's comments. GraphQL walks the whole graph server-side and returns it in one response.
Endpoint sprawl & versioning churn.Every new screen tempted a new bespoke REST endpoint. With GraphQL the schema exposes the graph once; new screens are new queries, not new endpoints or a /v2.

The Schema & Type System — the Contract

The heart of GraphQL is a strongly-typed schema, written in the Schema Definition Language (SDL). It declares every type, every field, and how they connect — a literal graph. The schema is the single source of truth: clients can't ask for a field that doesn't exist, and tooling can autocomplete, validate, and document queries before they ever run.

type User { id: ID! name: String! email: String! avatarUrl: String posts(last: Int): [Post!]! # a User has many Posts } type Post { id: ID! title: String! createdAt: String! likeCount: Int! comments(first: Int): [Comment!]! } type Comment { id: ID! text: String! author: User! # edges point back into the graph } type Query { # the read entry points user(id: ID!): User }

Read the ! as "non-null" and [Post!]! as "a non-null list of non-null Posts." Because User.posts returns Post, and Post.comments returns Comment, and Comment.author returns User again, the types form a graph the client can traverse in any shape it likes — which is exactly where the name comes from. The schema is also how GraphQL replaces versioning: you don't cut a /v2, you add fields (safe) and mark old ones @deprecated, then watch analytics until no client uses them.

Resolvers & the N+1 Trap (where GraphQL bites back)

A schema is just a promise; resolvers keep it. A resolver is a function attached to a field that knows how to fetch that field's value. When a query arrives, the server walks the query tree and calls a resolver for each field: Query.user loads the user, then for each post Post.comments loads its comments, then for each comment Comment.author loads a user. Crucially, GraphQL does not talk to your database — resolvers do, and they can call SQL, a REST service, a cache, or three different microservices. GraphQL is a coordinator, not a datastore.

The catch: you moved N+1 from the client to the server

Here's the twist that surprises people. GraphQL eliminated the client's round-trips — but a naive resolver just relocates the same explosion inside your server. Ask for 50 posts and each post's author, and the author resolver fires 50 separate database queries (1 for the posts + 50 for authors = the classic N+1 query problem). The network looks great; your database is on fire.

The fix: batching with DataLoader.A per-request batching + caching layer collects all the author IDs requested during one tick of execution and issues a single SELECT ... WHERE id IN (…) instead of 50 queries. It also de-dupes: if two comments share an author, that user is loaded once. This turns N+1 into 1+1.
The lesson.GraphQL's convenience is real but not free — it shifts the responsibility for efficient data-loading onto whoever writes the resolvers. "One request" for the client can still be a hundred queries for the DB unless you batch.

This is the deepest idea in the whole lesson: GraphQL doesn't remove the N+1 problem, it moves it. A team that adopts GraphQL for the mobile win and forgets to add batching will trade a slow client for a melting database.

The Hard Parts — What You Give Up

GraphQL's flexibility comes out of a budget, and three things pay for it. Knowing them is what separates "we use GraphQL" from "we understand GraphQL."

1. HTTP caching gets much harder

Remember Day 15: REST rides on free, battle-tested HTTP caching — a GET /users/9 is a cacheable URL that browsers, CDNs, and proxies already understand. GraphQL sends everything as POST to one URL, so that entire free layer evaporates. You get it back only by working for it: persisted queries (register a query, reference it by hash so it can be a cacheable GET), a smart client with a normalized cache (Apollo/Relay cache each object by ID on the client), and server-side caching keyed on the query. Caching moves from "free at the HTTP layer" to "your problem at the app layer."

2. A single query can be arbitrarily expensive

Because clients compose their own queries, a malicious or careless one can ask for posts → comments → author → posts → comments … nested deep enough to try to read your whole database in one request. REST couldn't do this — each endpoint had a bounded cost. GraphQL needs active defenses: query depth limiting, query cost/complexity analysis (assign each field a cost and reject queries over a budget), pagination limits, timeouts, and disabling introspection in production so attackers can't download your whole schema. Rate-limiting by "requests per minute" (Day 24) barely applies when one request can be 10,000× heavier than another.

3. Observability and errors are fuzzier

One URL for everything means your logs, metrics, and traces can't just group by endpoint — every request is POST /graphql. You need GraphQL-aware tracing (per-resolver timing). And errors are odd: a GraphQL response can be partial — HTTP 200 OK with a data object and an errors array, because one field's resolver failed while the rest succeeded. The clean 4xx/5xx status-code story from REST gets muddier.

None of this means "don't use GraphQL." It means the complexity REST spread across many simple endpoints gets concentrated into one powerful, sharp endpoint that you now own end-to-end.

REST vs GraphQL vs gRPC — Choosing a Front Door

REST

Many resource URLs, HTTP verbs, free HTTP/CDN caching, dead simple. Over-/under-fetches, and rich screens need multiple round-trips.

Best for: public APIs, CRUD, cache-friendly reads. (Day 15)

GraphQL

One endpoint, typed schema, client picks exact fields in one trip. Kills over/under-fetching; caching, cost-control, and resolver efficiency become your job.

Best for: rich/varied clients, many related entities, mobile. (today)

gRPC

Binary Protocol Buffers over HTTP/2 — tiny, fast, strongly-typed, streaming. Not browser-native, not human-readable. Built for service-to-service calls.

Best for: internal microservices, low latency. (Day 17)

A useful rule of thumb: GraphQL shines at the edge, where diverse clients (web, iOS, Android, partners) each need a different slice of a richly-connected data graph and you want to stop minting an endpoint per screen. REST shines for simple, cacheable, public resources. gRPC shines behind the wall, between your own services where speed and typing beat human readability. Many large systems run all three: gRPC internally, and a REST or GraphQL gateway at the edge. It's rarely "which one" — it's "which one where."

Common Mistakes & Misconceptions

The misconceptionThe reality
"GraphQL replaces REST — it's just better."It's a trade, not an upgrade. You gain exact fetching and one round-trip; you lose free HTTP caching, simple rate-limiting, and clean per-endpoint observability. For simple, cacheable, public resources, REST is often the better choice.
"GraphQL talks to my database."No — resolvers do. GraphQL is a coordinator over whatever you already have: SQL, REST services, caches, multiple microservices. The schema is a view of your data, not a database engine.
"One request means it's always efficient."One request for the client can be N+1 queries for the database. Without DataLoader-style batching, a naive resolver hammers the DB harder than REST did. GraphQL moves the N+1 problem server-side; it doesn't delete it.
"GraphQL means no more versioning."You still evolve the schema: add fields freely, but you must @deprecate old ones and wait for clients to migrate before removing them. It's continuous, field-level versioning — not the absence of versioning.
"HTTP caching just works like REST."It doesn't. POST-to-one-URL breaks URL-based caching. You rebuild it with persisted queries, normalized client caches (Apollo/Relay), or server-side query caching — all extra work.
"Clients can ask for anything, so we're done."That freedom is an attack surface. Unbounded depth/complexity can DoS you. Production GraphQL needs depth limits, cost analysis, pagination caps, timeouts, and disabled introspection.

Active Recall

❓ A team switches their mobile API from REST to GraphQL to fix slow screens. Client latency drops beautifully — but a week later the database is overloaded and paging on-call at 3am, even though total request count went down. What happened, and what's the fix? (click to reveal)
They hit the server-side N+1 problem. GraphQL collapsed the client's many round-trips into one request — but the resolvers naively fetch each nested field individually. A query for 50 posts and each post's author fires 1 query for the posts and then 50 more for the authors (N+1). Fewer HTTP requests overall, but each one now triggers a storm of database queries. The client got faster by pushing the fan-out onto the server. The fix is a per-request batching + caching layer (DataLoader): it collects all the author IDs needed during one execution tick and issues a single SELECT … WHERE id IN (…), and de-dupes shared authors — turning N+1 into 1+1. The deeper lesson: GraphQL doesn't remove N+1, it relocates it, and adopting GraphQL without batching trades a slow client for a melting database.

Real-World Engineering

📘 Meta / Facebook

Invented GraphQL in 2012 for exactly this reason: the mobile news feed was drowning under over-fetching and round-trips on slow networks. They needed the client to describe precisely the data a screen required — and open-sourced it in 2015.

🐙 GitHub

Runs a public GraphQL v4 API right alongside its REST v3 — the canonical real-world "when each wins" case study. Complex, deeply-related data (a repo → issues → comments → reactions → users) is where GraphQL's one-trip traversal pays off most.

🛍️ Shopify

Their Storefront and Admin APIs are GraphQL-first, and they publicly lean on query cost analysis — each query is assigned a cost and throttled against a budget, precisely because "requests per minute" is meaningless when one query can be 1000× heavier than another.

🎬 Netflix

Pioneered GraphQL Federation: dozens of backend microservices each own a slice of one giant schema, stitched into a single graph at the edge. Clients query one graph; a gateway routes each field to the owning service — GraphQL as an organizational tool, not just an API style.

Flashcards (Spaced Repetition)

Q: In one sentence, what is GraphQL?
A: A query language and typed schema for your API where the client sends a query whose shape is the response shape, letting it fetch exactly the fields it needs — usually through one endpoint (POST /graphql) in a single round-trip.
Q: What two REST problems does GraphQL primarily solve?
A: Over-fetching (an endpoint returns more fields than you need) and under-fetching (one screen needs many dependent round-trips). GraphQL returns exactly the requested fields, traversing the whole graph in one request.
Q: What is a resolver, and what is the N+1 trap?
A: A resolver is the function that fetches one field's value (from SQL, a service, a cache…). The N+1 trap: a naive resolver fetches each nested item separately — 1 query for the list + N for its children. Fix with per-request batching (DataLoader) → a single IN (…) query.
Q: Why is caching harder in GraphQL than REST?
A: REST gets free HTTP/CDN caching because each read is a cacheable GET URL. GraphQL POSTs everything to one URL, so URL-based caching breaks. You rebuild it with persisted queries, normalized client caches (Apollo/Relay), or server-side query caching.
Q: How do you stop a client from sending one catastrophically expensive query?
A: Query depth limiting, cost/complexity analysis (budget per query), pagination caps, timeouts, and disabling introspection in production. Plain "requests-per-minute" rate limiting isn't enough when one query can be 1000× heavier than another.

If you only remember one thing: GraphQL hands the client a blank order slip. Through one endpoint and a typed schema, the client describes the exact shape of the data it wants — nested as deep as it likes — and gets it back in a single trip, ending REST's over- and under-fetching. The price is that all the complexity REST spread across many simple, cacheable endpoints is now concentrated in one powerful endpoint you own: resolvers must batch to avoid N+1, caching must be rebuilt, and query cost must be policed. It doesn't replace REST — it trades simplicity and free caching for precision.
